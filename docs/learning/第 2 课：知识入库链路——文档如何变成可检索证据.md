## 一、教案正文

### 2.1 先说结论

一条完整的知识入库链路：

```
用户上传文件
  → 后端二次校验文件类型
  → SHA-256 内容去重（同内容拒绝，同名不同内容形成新版本）
  → 解析（Markdown/TXT/PDF/DOCX → 纯文本+结构信息）
  → 分块（按标题边界切分，带 overlap 防语义断裂）
  → Embedding（文本→向量，当前默认 BGE-small-zh，测试/无模型环境可降级到 development）
  → 双重索引（pgvector 向量 + PostgreSQL tsvector 全文）
  → 增量目录同步（提取标题路径为 KnowledgeCatalogPoint）
  → 状态变为 READY
```

### 2.2 上传阶段：三个安全措施

关键代码在 `application/knowledge_service.py`：

```python
# 安全措施 1：后端再次校验文件类型
suffix = Path(filename).suffix.lower()
if suffix not in DocumentParser.supported_extensions:
    raise AppError("UNSUPPORTED_DOCUMENT",
        "Only Markdown, TXT, PDF and DOCX are supported.")

# 安全措施 2：防止路径穿越
safe_name = Path(filename).name  # 只用文件名，丢弃路径部分

# 安全措施 3：内容去重
digest = hashlib.sha256(content).hexdigest()
duplicate = await session.scalar(
    select(SourceDocumentModel).where(
        SourceDocumentModel.knowledge_base_id == base_id,
        SourceDocumentModel.content_hash == digest,
    )
)
if duplicate:
    return duplicate, True  # 重复文件，直接返回已有记录
```

#### 面试要能讲清的三点

| 措施              | 防什么                                | 为什么不能只靠前端                 |
| ----------------- | ------------------------------------- | ---------------------------------- |
| 后端校验扩展名    | 上传可执行文件/非预期格式             | 前端校验可被绕过                   |
| `Path(name).name` | 路径穿越攻击（`../../../etc/passwd`） | 直接用原始文件名可能访问预期外路径 |
| SHA-256 去重      | 重复上传浪费存储和索引                | 按文件名覆盖会丢失版本历史         |

补充：面试时可以加一句——"这三个措施不在同层，前端校验可被绕过，后端校验才是最终防线。"

#### 版本管理

同名但内容不同的文件 → **形成新版本，旧版本设为非活跃**

这比简单覆盖更适合知识追踪——可以追溯"某个回答引用的是哪个版本的资料"。

### 2.3 文档状态机

```
                    ┌──────────────┐
    上传完成 →  pending  ──→  processing  ──→  ready
                    │              │
                    │              └──→  failed  ──→  processing（重新索引）
                    │
                    └──→  archived（归档）
```

系统启动时会扫描超时遗留的 `pending/processing` 文档，将其标记为 `failed` 并提示用户点击重新索引——避免界面永远显示"处理中"。这属于中断检测和状态修复，不是从解析中间步骤自动续跑。

### 2.5 分块策略：为什么不是固定字数切割

当前使用 `chunk_sections` 按**标题边界**切分，而不是按固定字数硬切：

```
按标题边界切分（当前做法）：
  "## RRF 公式\nRRF 的基本思想是..."  →  一个完整块
  "## 引用白名单\n引用白名单的作用..."  →  另一个完整块

按固定字数硬切（坏做法）：
  "## RRF 公式\nRRF 的基本思想是[切到一半]..."  →  语义断裂
  "[块2继续]..."  →  上下文丢失
```

#### 为什么还要加 overlap？

标题之间可能有逻辑承接段（如"如上所述"、"因此"），overlap 保证跨标题的上下文不丢失。

### 2.6 Embedding 阶段：当前的真实实现

```python
# infrastructure/embedding.py —— DevelopmentEmbeddingGateway

# 1. 提取特征
words = re.findall(r"[a-z0-9_]{2,}", normalized)            # 英文单词
chinese_segments = re.findall(r"[\u4e00-\u9fff]+", normalized)  # 中文片段
chinese_ngrams = [                                             # 中文 2-gram/3-gram
    segment[index:index + size]
    for segment in chinese_segments
    for size in (2, 3)
    for index in range(max(0, len(segment) - size + 1))
]

# 2. BLAKE2b 哈希映射到固定维度 + L2 归一化
```

#### 它的价值
- 不下载本地大模型
- 资源占用稳定
- 离线可运行
- 测试结果确定

#### 它的限制
- 主要捕获字面和局部 n-gram 相似性
- development fallback 不能等同于 BGE 等语义 Embedding；当前默认 BGE 也不能等同于企业级向量服务
- 复杂中文语义召回能力有限

#### 面试必须准确描述

| ✅ 应该说                                                 | ❌ 不能说                   |
| -------------------------------------------------------- | -------------------------- |
| "当前默认 BGE-small-zh，适合本地 CPU/Docker 演示"        | "已经具备企业级向量检索治理" |
| "保留 development fallback，便于测试和无模型环境运行"    | "所有环境都强依赖本地模型"    |
| "主要捕获字面和局部 n-gram 相似性"                       | "能够理解复杂语义"         |

### 2.7 重新索引时为什么尽量保留 Chunk ID

```python
existing_chunks = {
    chunk.chunk_index: chunk
    for chunk in existing_chunk_rows
}

for draft, vector in zip(drafts, vectors, strict=True):
    chunk = existing_chunks.pop(draft.chunk_index, None)
    if chunk is None:
        session.add(KnowledgeChunkModel(...))     # 新块 → 新建
    else:
        chunk.content = draft.content              # 已有块 → 更新内容
        chunk.embedding = vector                   # 更新向量，保留原 ID
```

#### 为什么这么做

历史面试题和评分可能引用了旧的 Chunk ID。如果每次重建都删除全部 Chunk：
- 历史评估的 `reference_chunk_ids` 会变成悬空引用
- 历史报告中的引用来源会丢失

当前方案优先按 `chunk_index` 更新原记录，从而尽量保持引用稳定。

#### 边界

如果文档大幅重排（段落插入/删除），相同 `chunk_index` 可能已经不是同一语义——这是真实的局限。

面试时可给出递进式改进思路（详见下方疑问记录）。

### 2.8 增量知识目录：新文档如何进入查漏体系

摄入完成后，`coverage_catalog.py::sync_document_catalog` 从结构化 `heading_path` 提取稳定知识点：

```
SourceDocument（新文档）
  → KnowledgeChunk.heading_path（"RAG > 混合检索 > RRF公式"）
  → KnowledgeCatalogPoint（稳定知识点，按标题规范化生成 key）
  → KnowledgeCatalogSource（知识点→文档/Chunk的来源关系）
```

#### 关键规则

| 规则                                 | 目的                               |
| ------------------------------------ | ---------------------------------- |
| 有二级标题时，一级标题只作为主题容器 | 避免"RAG"同时作为主题和具体考点    |
| 标题规范化生成稳定 `point_key`       | 重新索引不重复创建节点             |
| 新文档只增加 `uncovered` 知识点      | 不修改已有画像分数                 |
| 文档归档时删除有效来源关系           | 失去活动来源的知识点不参与覆盖统计 |

因此，重新导入资料不是"清空画像重新训练"，而是给已有知识边界增加新的待验证集合。

## 二、学员疑问与讨论记录

### Q1：当前 RAG 是不是比较 LOW？Embedding 必须改造吗？

**回答：**

#### Embedding 层确实基础，但工程防御层不 LOW

Embedding 弱不等于整个 RAG 弱。当前 RAG 的工程深度体现在**检索之后**：

```
检索（弱） → RRF 融合 → 每文档限额 → 相邻块去重 → 
词汇化证据判断 → 分数阈值门禁 → 证据不足拒答 →
LLM 生成 → 引用白名单校验 → 持久化诊断信息
```

这些环节不依赖 Embedding 质量，它们是对"检索结果不可信"的防御层。恰恰因为 Embedding 弱，这套防御才更有意义——证明了系统不靠"运气好搜到对的东西"来工作。

#### Embedding 是性价比最高的单点提升

| 改造项                                  | 效果提升 | 改造难度                          | 性价比 |
| --------------------------------------- | -------- | --------------------------------- | ------ |
| 🔥 **接入 Reranker / 查询改写**          | 🟢🟢🟢      | 中（额外模型与延迟成本）          | ⭐⭐⭐⭐   |
| 换生产级 LLM（如 DeepSeek）             | 🟢🟢       | 低（已有 OpenAI-compatible 接口） | ⭐⭐⭐⭐   |
| 加 Reranker（如 BGE-Reranker）          | 🟢🟢       | 中（需额外模型+推理时间）         | ⭐⭐⭐    |
| 加 Query Rewrite                        | 🟢        | 中                                | ⭐⭐     |

Embedding 已完成 BGE-small-zh 重建式切换；下一步如果继续提升检索质量，更适合补 reranker、查询改写和更稳定的标注评测集。

#### 面试策略

把"弱 Embedding"转化为论据：

> "当前 Embedding 弱是我故意的设计取舍。这反过来验证了下游防御层（证据门禁、引用校验、拒答）是否真的有效——如果 Embedding 很弱时系统不会乱说，换强 Embedding 后只会更好。这不是'没做'，是'按优先级排期'，Embedding 是第一批优化项。"

### Q2：文档大幅重排问题，面试中怎么回答？没有企业经验会难吗？

**回答：**

面试官问"文档大幅重排怎么办"，可以直接给出递进式回答——不需要企业经验：

#### 方案 1：内容指纹（本地就能做，本质是 Hash 去重的延伸）

```
当前：chunk_index=3 匹配 chunk_index=3
      → 文档中间插入一段后，旧的第3块变成了第4块 → 匹配失败 ❌

改进：对每个 chunk 计算 mini 指纹（SHA-256 前 16 位）
      匹配时：先按 index 找，找不到再用指纹遍历邻近 index
      → 内容没变就能匹配上 ✅
```

#### 方案 2：结构路径匹配（当前已有 heading_path）

```
当前 chunk 已有 heading_path：["RAG", "混合检索", "RRF公式"]

改进逻辑：
  优先匹配：相同的 heading_path + 相近的 chunk_index
  其次匹配：相同的 heading_path（index 不要求精确）
  最后兜底：内容指纹遍历
```

#### 方案 3：版本化引用（企业级方案，说你理解思路即可）

```
每个 KnowledgeChunk 增加字段：document_version

旧逻辑：interview.question.reference_chunk_id → chunk(id=42)
新逻辑：interview.question.reference_chunk_id → chunk(id=42, version=v3)

文档重排后：chunk(id=42, version=v4) 是一块新内容
但历史引用仍然指向 chunk(id=42, version=v3) → 保留在历史快照中
```

#### 面试时这样说的效果

| 层级              | 你说的                                        | 面试官听到的                             |
| ----------------- | --------------------------------------------- | ---------------------------------------- |
| 方案1（内容指纹） | "类似上传阶段的 Hash 去重，延伸到 Chunk 层面" | 他能举一反三，把已有能力延伸到新问题     |
| 方案2（结构路径） | "标题路径已经在采集了，匹配逻辑从一维变二维"  | 他知道自己系统里有什么数据，不是凭空设计 |
| 方案3（版本化）   | "企业级方案是版本化引用，历史绑定版本号"      | 他有架构视野，知道终态应该长什么样       |

#### 核心结论

> 不需要企业经验。面试官要的不是一个生产环境跑过的方案，而是你**能从当前实现出发，递进式推演出改进路径**——每一步都在当前基础上加一层保障。
