## 一、教案正文

### 5.1 先说结论

LLM 只提供结构化评分建议，**应用层是评分的最终裁判：**

```
用户提交回答
    ↓
LLM 返回四维评分 + 置信度 + 引用
    ↓
应用层做五件事：
  ① 校验 Rubric（权重必须和为 100）
  ② 校验引用白名单（chunk_id 必须属于本轮检索上下文）
  ③ 应用层重算总分（不直接读取 LLM 返回的 total）
  ④ 判断评分状态（final / review_pending / disputed）
  ⑤ 控制画像更新权限（只有 FINAL 评分能进入画像；低置信 FINAL 降权，review_pending/disputed 阻断）
```

---

### 5.2 四维评分

| 维度              | 关注内容       | 分数范围 | 常见扣分原因             |
| ----------------- | -------------- | -------- | ------------------------ |
| **correctness**   | 结论与核心事实 | 0-5      | 概念混淆、错误断言       |
| **completeness**  | 必答点覆盖     | 0-5      | 漏掉边界、风险或关键步骤 |
| **reasoning**     | 推理和因果     | 0-5      | 只给结论、因果不成立     |
| **communication** | 面试表达       | 0-5      | 结构混乱、术语堆砌       |

总分 = correctness + completeness + reasoning + communication（0-20 分）。

---

### 5.3 应用层重算总分

```python
def total_score(output: EvaluationOutput) -> int:
    return output.correctness + output.completeness + output.reasoning + output.communication
```

写入数据库时：

```python
evaluation = EvaluationModel(
    correctness=output.correctness,
    ...,
    total=total_score(output),       # ← 应用层重算，不读 LLM 返回的 total
)
```

原因：LLM 可能算错加法——`4+3+2+4=13` 但 LLM 写了 `15`。Python 的 `+` 不会错。

---

### 5.4 三种评分状态

```python
class EvaluationStatus(StrEnum):
    FINAL = "final"
    REVIEW_PENDING = "review_pending"
    DISPUTED = "disputed"
```

#### 判定流程

```
LLM 评分结果
    ↓
should_review() 判断：
  - confidence < 0.70  → 需要复核
  - 四维分差 ≥ 4       → 需要复核
  - 总分 9-12 且有错误断言 → 需要复核
    ↓
  ├── 不需要 → status=FINAL
  └── 需要
        ├── Reviewer 可用 → 复核 → 分差<5? FINAL : DISPUTED
        └── Reviewer 不可用 → REVIEW_PENDING
```

#### Reviewer 什么时候不可用？

当前 `_review_deterministically` 是纯 Python 代码，默认始终可用。`reviewer_available` 参数是为未来预留——当 Reviewer 升级为独立 LLM 模型时，未配置或调用失败则优雅降级为 REVIEW_PENDING。

#### 三种状态对画像的影响

| 状态           | 评分是否写入 | 报告可见       | 能否更新画像 |
| -------------- | ------------ | -------------- | ------------ |
| FINAL          | ✅            | ✅ 正常展示     | ✅            |
| REVIEW_PENDING | ✅            | ✅ 标记"待复核" | ❌ 阻断       |
| DISPUTED       | ✅            | ✅ 标记"争议"   | ❌ 阻断       |

关键：REVIEW_PENDING 不是"丢弃评分"，是**保留证据但阻断传播**——给未来复核留操作空间。

### 5.6 复核路由逻辑

```python
def review_reasons_for(output):
    reasons = []
    if output.confidence < 0.70:
        reasons.append("low_confidence")
    if total_score(output) in {9,10,11,12} and output.incorrect_claims:
        reasons.append("boundary_with_dispute")
    if max(dims) - min(dims) >= 4:
        reasons.append("dimension_conflict")
    return sorted(set(reasons))
```

| 触发条件                 | 含义              |
| ------------------------ | ----------------- |
| `confidence < 0.70`      | LLM 自己都不确定  |
| `总分 9-12 且有错误断言` | 边缘分 + 事实错误 |
| `四维分差 ≥ 4`           | 维度极端不平衡    |

### 5.7 三种状态的完整对比

| 维度         | FINAL  | REVIEW_PENDING  | DISPUTED   |
| ------------ | ------ | --------------- | ---------- |
| 评分是否写入 | ✅      | ✅               | ✅          |
| 报告可见     | ✅ 正常 | ✅ 待复核标记    | ✅ 争议标记 |
| 进画像       | ✅      | ❌               | ❌          |
| 进复习任务   | ✅      | ❌               | ❌          |
| 可被复活     | —      | ✅（未来复核后） | ❌          |

---

### 5.8 同源模型偏差

#### 能缓解的

| 手段            | 降低什么风险           |
| --------------- | ---------------------- |
| Rubric 权重校验 | 模型随意分配权重       |
| 应用层重算总分  | 模型算错总分           |
| 引用白名单      | 模型编造引用           |
| 复核路由        | 低置信/边缘分/维度冲突 |

#### 消除不了的

| 偏差                       | 为什么                   |
| -------------------------- | ------------------------ |
| 模型偏爱自己生成的参考答案 | 出题和评分同一模型       |
| Rubric 遗漏其他正确解法    | Rubric 也是同一模型生成  |
| 表达风格偏好               | 模型可能偏好某种写作风格 |

---

### 5.9 报告：逐题解析比总分更重要

逐题报告需要回答：
- 为什么得这个分？
- 覆盖/缺失了哪些知识点？
- 存在哪些错误断言？
- 是否建议追问或复习？

核心区分：**报告表示某场表现，画像表示跨多次可信证据的渐进估计。**

## 二、学员疑问与讨论记录

### Q1：什么情况下 Reviewer 判定为不可用？

当前 `_review_deterministically` 是纯 Python 代码，默认始终可用。`reviewer_available=False` 是为未来预留：当 Reviewer 升级为独立 LLM 模型（跨模型交叉校验）时，未配置或调用失败则优雅降级。宁可承认"还不能确认"，也不伪造"已复核"。

### Q2：REVIEW_PENDING 是不是因为没有 Reviewer 就直接被弃用？

不是。评分完整保留（报告可见），但画像更新被阻断。目的是给未来复核留操作空间——如果直接丢弃评分记录，就永远没有"复活"的机会。
