## 一、教案正文

### 7.1 五个最能体现工程能力的专题

#### 专题 1：幂等 ≠ 按钮防抖

| 层级   | 机制                 | 防什么                 |
| ------ | -------------------- | ---------------------- |
| 前端   | 按钮防抖             | 用户快速双击（毫秒级） |
| 应用层 | Idempotency-Key 查询 | 正常重试（秒级）       |
| 数据库 | UNIQUE 约束          | 并发竞态（微秒级）     |

三者不在同一层。只在前端禁用按钮不能处理网络重试和并发请求。

**面试模板：**
> "前端复用同一道题的稳定幂等键，API 传给 InterviewService。服务先查询已有答案，数据库通过唯一约束承担并发下的最终防线。响应丢失后的重试不会重复写入或推进题目。"

#### 专题 2：Checkpoint ≠ 完整工作流引擎

当前 checkpoint 让流程可观测，并为恢复提供轨迹证据；刷新后真正恢复当前题目依赖 GET /interviews/{id} 读取服务端持久化状态、题目和答案数据。当前没有任务租约、分布式调度和节点级补偿。

**面试模板：**
> "我先把状态、节点、幂等和恢复语义做实，当前由 Service 显式编排。流程规模增大后可以迁移到 LangGraph，但不能把当前实现描述成 LangGraph Runtime。"

#### 专题 3：降级必须可观测

无 API Key、LLM 失败或证据不足时，系统仍可用确定性路径完成演示，但必须记录：

- `generation_mode`：llm / deterministic / evidence_guard
- `model_name`：使用的模型名（无 LLM 时为 None）
- `fallback_reason`：llm_not_configured / insufficient_evidence / ConnectionError 等
- `llm_enabled`：运行时当前模式

否则 fallback 会让人误以为真实模型已经调用成功。代码中每次生成回答都持久化 diagnostic 信息到 ChatMessage.retrieval_diagnostics。

#### 专题 4：事务边界比"调用顺序正确"更重要

以下内容需要在同一业务事务内保持一致：

- 答案写入、面试进度和 checkpoint
- Evaluation 与引用记录（EvaluationReference）
- 画像更新与 ProfileUpdateEvent
- 报告创建或更新

如果分开提交，可能出现"业务状态推进了但 checkpoint 还是旧的"——刷新后状态不一致。代码中 `start_interview` 和 `submit_answer` 都将状态推进 + checkpoint 写入 + commit 放在同一个 db session 中。

#### 专题 5：历史可追溯需要稳定标识和版本

| 对象       | 稳定标识机制                                           |
| ---------- | ------------------------------------------------------ |
| 文档       | 内容 SHA-256 + 版本号（同名不同内容形成新版本）        |
| Chunk      | 重建尽量保留 ID（按 chunk_index 匹配，按内容更新）     |
| Evaluation | 保存 model_name + prompt_version（如 "evaluation_v1"） |
| 画像更新   | 保存 hierarchy_version（V2） + 变化详情                |
| 报告       | 保留多轮历史（不覆盖，可追溯趋势）                     |

这些是系统能够解释"这个结果从哪里来"的基础。

### 7.2 八个故障场景：必须会回答

| 场景                | 当前处理                                         | 仍然存在的边界                              |
| ------------------- | ------------------------------------------------ | ------------------------------------------- |
| 重复提交答案        | 幂等键查询 + DB 唯一约束                         | 不代表所有并发操作都自动串行                |
| 页面刷新            | GET /interviews/{id} 服务端恢复                  | 浏览器 localStorage 丢失时需重输 session_id |
| 文档处理中 API 重启 | 启动扫描超时 pending/processing 文档并标记为 failed，提示重新索引 | 不能从解析中间步骤续跑                      |
| LLM 无 Key          | 确定性 fallback，运行态显示降级                  | 只能验证工程链路，不能验证模型质量          |
| 证据不足            | evidence_guard 明确拒答                          | 阈值仍需评测集校准                          |
| 报告重复生成        | 稳定报告关系，事务内更新                         | 高并发仍需依赖数据库约束                    |
| 文档重新索引        | 按 chunk_index 更新，尽量保留 ID                 | 大幅重排需内容指纹+版本引用                 |
| 低可信评分          | pending/disputed 阻断画像，低置信 final 降权     | 独立 Reviewer 和人工校准仍需增强            |

### 7.3 企业级 RAG 演进路线

#### 当前项目的真实边界

| 能力         | 准确表达                                            |
| ------------ | --------------------------------------------------- |
| Agent 工作流 | 显式节点、checkpoint、人机中断；当前由 Service 编排 |
| 画像驱动出题 | 画像推荐训练焦点，用户选择后注入主题                |
| Embedding    | 默认 BGE-small-zh，保留 development fallback；非企业级向量服务 |
| 复杂文档     | 基础文本解析，不含 OCR 与复杂版面                   |
| 故障恢复     | 关键业务幂等和状态恢复，非分布式任务引擎            |
| 可信评分     | 增加确定性约束，不能声称绝对客观                    |
| 用户系统     | 本机默认用户，不是企业多租户系统                    |

#### 企业化五阶段

```
当前个人版闭环
  → ① 身份、租户、权限
       SSO/OIDC + RBAC + 检索前置 ACL + 跨租户越权测试
  → ② 数据连接器与文档治理
       对象存储、Wiki/网盘 Connector、增量同步、OCR、版面、表格
  → ③ 生产 Embedding 与检索评测
       BGE/多语言 Embedding、Reranker、标注集、Recall@K、NDCG
  → ④ 可靠队列与工作流运行时
       消息队列、独立 Worker、任务租约、死信、Trace/指标/日志
  → ⑤ 组织技能矩阵与训练平台
       岗位职级、评分人工复核、团队训练计划、聚合趋势与隐私
```

#### 为什么不能一开始就拆微服务

企业化的优先级应是**权限、数据质量和评测证据**，而不是服务数量。先保持模块边界，通过接口逐步替换基础设施；只有独立扩缩容、故障隔离或团队所有权出现明确需求时再拆服务。

### 7.7 学完整个项目后应该形成的认知

> AgentMentor 的核心价值不是"用大模型生成三道题"，而是把学习资料、可溯源检索、人机工作流、可信评分和长期画像连接成一个受约束的训练闭环。系统通过应用层规则限制 LLM 的权力，通过 checkpoint 和幂等保证流程状态，通过两层画像控制长期记忆粒度，再通过增量知识目录区分"回答得怎么样"和"资料是否考到"，形成补缺与查漏两类训练信号；并在 16GB 本地约束下选择 PostgreSQL、本地 BGE-small-zh 和模块化单体。它已经是一个真实可运行的个人学习系统，但还不是企业级终态；当前已补同知识库最近历史题目冷却，全量语义题库去重、复杂文档、生产检索评测、租户权限和可靠异步任务是明确的演进方向。
