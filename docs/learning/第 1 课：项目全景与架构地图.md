## 一、教案正文

### 1.1 一句话讲清这个项目是什么

> **AgentMentor 是一个面向个人学习者的 AI 面试训练系统。** 它把学习资料变成可检索证据，通过 RAG 支撑问答和面试出题，再用可信评分更新能力画像和复习任务，形成"学习→训练→评分→画像→下一轮"的闭环。整套系统可在 16GB 普通开发机上通过 Docker Compose 运行。

### 关键区分：它不是什么

| ❌ 不是               | ✅ 而是                                   |
| -------------------- | ---------------------------------------- |
| 调个 API 聊天的 Demo | 有状态、有规则、有长期记忆的训练系统     |
| 通用 ChatGPT 替代品  | 把大模型包装为有领域数据约束的训练应用   |
| LangGraph 运行时     | 自己实现显式节点+checkpoint 的人机工作流 |
| 企业多租户平台       | 模块化单体，本机用户优先                 |

### 1.2 六层架构（先建立系统地图）

```
┌──────────────────────────────────────────────┐
│  交互层    React 前端 (知识库/问答/面试/画像)     │
├──────────────────────────────────────────────┤
│  接口层    FastAPI Router (7个路由)              │
│           chat / knowledge / interviews /      │
│           evaluations / profiles / demo        │
├──────────────────────────────────────────────┤
│  应用层    Service (编排中心)                    │
│           AnswerService / InterviewService /   │
│           EvaluationService / ProfileService   │
├──────────────────────────────────────────────┤
│  领域层    Domain (不依赖Web的业务规则)           │
│           interview状态机 / evaluation评分规则   │
│           profile画像更新 / RAG检索算法          │
├──────────────────────────────────────────────┤
│  基础设施  PostgreSQL+pgvector / Embedding /     │
│           LLM Gateway / File Storage           │
├──────────────────────────────────────────────┤
│  部署层    Docker Compose 三容器                │
│           db(pgvector) + api + frontend         │
└──────────────────────────────────────────────┘
```

### 核心规则（面试必背）

> **API 不承担核心业务规则；LLM 不决定最终业务状态；Infrastructure 可以替换；Application Service 是真正的编排中心。**

### 应用层 vs 领域层：一句话区分

> **领域层 = 规则引擎**（只做判断和计算，不依赖外部世界）  
> **应用层 = 流程导演**（把规则、数据库、LLM 串起来演完一场戏）

|              | 领域层（规则引擎）                          | 应用层（流程导演）                                           |
| ------------ | ------------------------------------------- | ------------------------------------------------------------ |
| **定义什么** | 什么是合法状态、什么是合法过渡              | 什么时候该调用这个规则                                       |
| **做什么**   | `can_transition(created, waiting)` → `True` | "用户点了开始面试，我先校验状态，再调 LLM 出题，再写 checkpoint，最后提交事务" |
| **依赖**     | 无（纯 Python）                             | 数据库 session、LLM Gateway、Retriever                       |
| **可测试性** | 单元测试，不需要启动任何服务                | 集成测试，需要真实数据库                                     |

### 为什么这样分层？

1. 业务规则可以脱离 FastAPI 做单元测试
2. LLM、Embedding、Retriever 通过 Port/Gateway 隔离——将来换模型不改业务代码
3. 事务集中在 Service，Router 只管 HTTP 协议
4. 对个人项目来说比微服务更容易运行和解释

### 1.3 核心数据模型（三组实体）

#### 知识数据
```
KnowledgeBase（知识库）
 └── SourceDocument（原始文件、版本、Hash去重）
      └── KnowledgeChunk（分块文本、向量、全文索引）
 └── KnowledgeCatalogPoint（增量知识目录）
      └── KnowledgeCatalogSource（知识点→文档/Chunk来源）
```

#### 面试和评分数据
```
InterviewSession（面试场次）
 ├── InterviewQuestion（题目+参考答案+Rubric）
 │    ├── QuestionReference → KnowledgeChunk（题目引用的资料）
 │    ├── QuestionCoveragePoint → KnowledgeCatalogPoint（题目覆盖的知识点）
 │    └── UserAnswer（用户回答）
 │         └── Evaluation（四维评分+置信度+引用校验）
 ├── WorkflowCheckpoint（流程节点轨迹）
 └── InterviewReport（逐题报告）
```

#### 长期画像数据
```
Evaluation
 └── ProfileUpdateEvent（审计记录：是否应用、为什么跳过）
      ├── AbilityProfile（两层：稳定主题 + 动态子知识点）
      ├── ErrorPattern（重复错误模式）
      └── ReviewTask（复习任务，需两次连续验证才完成）
```

### 面试重点：为什么需要 ProfileUpdateEvent？

它不是多余的日志，而是**画像副作用的审计记录**：
- 同一 Evaluation 是否已经应用（防重复）
- 为什么跳过更新（disputed/review_pending）
- 更新前后掌握度如何变化
- 使用的是哪一版层级模型

### 1.4 核心闭环（整套系统如何串起来）

```
学习资料成为证据
    ↓
证据支撑两条消费路径：
    ├── 路径A：RAG问答（用户提问→检索→证据判断→LLM回答→引用校验）
    └── 路径B：模拟面试（训练主题→检索出题→用户回答→可信评分→画像更新）
    ↓
评分沉淀为能力和错误
    ↓
错误生成复习任务
    ↓
画像推荐下一轮训练主题（当前是"画像推荐+用户确认+主题注入"，非全自主Agent）
```

### 两条消费路径的关键区别

|             | RAG 问答                       | 模拟面试                            |
| ----------- | ------------------------------ | ----------------------------------- |
| **目的**    | 回答"学习资料能否回答当前问题" | 回答"用户是否真正掌握资料内容"      |
| **输出**    | 带引用的答案                   | 题目+参考答案+Rubric→评分→画像      |
| **LLM角色** | 基于证据生成答案               | 出题+评分（但应用层控制评分可信度） |

---

### 1.5 面试必背：三个亮点 + 三个边界

#### 六个亮点

| 亮点           | 不是简单的什么       | 真正体现的能力                           |
| -------------- | -------------------- | ---------------------------------------- |
| **RAG 前置**   | 上传文件后聊天       | 证据召回、引用校验与拒答边界             |
| **面试状态机** | 连续调用三次接口     | 人机中断、checkpoint、幂等推进           |
| **可信评分**   | LLM 随便给一个分     | Rubric、应用层重算、复核路由             |
| **两层画像**   | 展示几个百分比       | 稳定统计节点与动态诊断证据分离           |
| **知识查漏**   | 上传新资料后统一降分 | 增量知识目录、区分"没考到"和"考了但不会" |
| **复习闭环**   | 固定推荐列表         | 错误驱动任务、连续验证后完成             |

#### 三条真实边界

1. **Embedding 默认使用本地 BGE-small-zh**，但不是企业级向量服务，仍保留 development 特征哈希 fallback
2. **工作流是显式节点+checkpoint**，不是 LangGraph Runtime
3. **基础文本解析**，没有 OCR、复杂版面、表格重建

### 为什么面试时不能回避边界？

每条边界都需要能说出对应的生产方案：

| 边界                 | 需要准备的知识                                               |
| -------------------- | ------------------------------------------------------------ |
| 本地 BGE Embedding   | 云 Embedding、Reranker、向量版本治理和企业级检索服务；知道本地小模型与生产治理的边界 |
| 非 LangGraph Runtime | LangGraph 适合什么场景、当前为什么不需用、如何迁移           |
| 基础文本解析         | OCR（扫描 PDF）、版面分析（多栏/表格）、复杂表格重建——不同格式的难点 |





### 1.6 请求如何穿过各层（以 RAG 问答为例）

```
React RagPanel
  → POST /knowledge-bases/{id}/ask
  → api/chat.py（参数校验、协议转换）
  → AnswerService.answer（业务编排）
      → KnowledgeRetriever.retrieve（Port接口）
          → PostgresHybridRetriever（两路检索+RRF）
      → LLMGateway.generate_structured（LLM生成）
      → validate_citations（引用白名单校验）
      → _persist（持久化到ChatSession/ChatMessage/ChatCitation）
  → API Response（答案+引用+诊断信息）
  → React 展示答案与引用
```

## 二、学员疑问与讨论记录

### Q1：为什么不使用 LangGraph？

**学员理解：**
> 自定义 checkpoint 本身就是参考 LangGraph 设计思想实现的，所以迁移是"回归标准"而非"推倒重来"。当前节点按 StateGraph Node 模式设计（纯函数、输入 state 输出 state），迁移只需改工作流节点和面试流程相关的东西，评分、画像等模块零改动——Port/Adapter 分层和单一职责保障了这一点。

**教师补充：**

三层保障使得迁移成本极低：
1. **设计同源**：节点本身就是按 LangGraph Node 模式设计
2. **边已隐含**：`InterviewService` 的调用顺序天然对应 `add_edge(A, B)`
3. **其他模块零改动**：评分、画像只通过领域对象交互，不依赖工作流框架

**面试话术红线：**

| ❌ 绝对不能说                   | ✅ 应该说                                          |
| ------------------------------ | ------------------------------------------------- |
| "LangGraph 太复杂了，我用不来" | "当前规模下自研是更合理的选择"                    |
| "我这个就是 LangGraph 的思路"  | "借鉴了图工作流的思想，显式实现节点和 checkpoint" |
| "自研的比 LangGraph 更好"      | "自研满足了当前需求，LangGraph 适合更复杂的场景"  |

---

### Q2：应用层和领域层的区别？

**学员理解：**
> 应用层用于编排，领域层是工具或规则。RAG 检索算法用于高质量检索，evaluation 让评分更可信，interview 状态机定义面试中的状态（等待回答、完成、取消等）。

**教师精炼：**

|              | 领域层（规则引擎）             | 应用层（流程导演）                     |
| ------------ | ------------------------------ | -------------------------------------- |
| **定义什么** | 什么是合法状态、什么是合法过渡 | 什么时候该调用这个规则                 |
| **依赖**     | 无（纯 Python）                | 数据库 session、LLM Gateway、Retriever |
| **可测试性** | 单元测试，不需要启动任何服务   | 集成测试，需要真实数据库               |

三个领域概念的精确定位：
- **RAG 检索算法** → `rag/retrieval.py`：RRF 融合公式、每文档限额、相邻块去重
- **evaluation 评分规则** → `domain/evaluation.py`：final/pending/disputed 判定、should_review()、total_score()
- **interview 状态机** → `domain/interview.py`：ALLOWED_STATUS_TRANSITIONS、can_transition()

---

### 自测结果：第 3 题需要加强

**原答**："没有 LLM 时，会降级"

**问题**：这说的是 LLM 不可用时的兜底，不是"LLM 输出了结果但我不全信它"。

**正确答案示例：**

> **评分总分不由 LLM 决定。** 代码在 `domain/evaluation.py`：
> ```python
> def total_score(output: EvaluationOutput) -> int:
>  return output.correctness + output.completeness + output.reasoning + output.communication
> ```
> LLM 只返回四个维度的分数，**总分由应用层重算**，保证四维之和与总分严格一致，防止模型算错或"自由发挥"一个总分。
