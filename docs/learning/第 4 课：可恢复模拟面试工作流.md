## 一、教案正文

### 4.1 先说结论

面试不是一次同步 API 调用——用户在出题后可能几分钟甚至更久才回答。三个核心机制：

| 机制           | 解决的问题                             |
| -------------- | -------------------------------------- |
| **状态机**     | 当前面试处于什么阶段？能执行什么操作？ |
| **Checkpoint** | 刷新页面后能否恢复？流程走到哪一步了？ |
| **幂等键**     | 网络重试会不会重复提交同一道题？       |

---

### 4.2 面试状态机

```python
# domain/interview.py

class InterviewStatus(StrEnum):
    CREATED = "created"
    WAITING_FOR_ANSWER = "waiting_for_answer"
    COMPLETED = "completed"
    CANCELLED = "cancelled"

ALLOWED_STATUS_TRANSITIONS = {
    CREATED:           {WAITING_FOR_ANSWER, CANCELLED},
    WAITING_FOR_ANSWER: {WAITING_FOR_ANSWER, COMPLETED, CANCELLED},
    COMPLETED:          set(),     # 终态
    CANCELLED:          set(),     # 终态
}
```

关键：`WAITING_FOR_ANSWER → WAITING_FOR_ANSWER` 合法——表示"答完一题，生成下一题，继续等待"。

### 4.3 面试启动流程

```python
async def create_interview(self, *, knowledge_base_id, topic, difficulty, ...):
    interview = InterviewSessionModel(status=InterviewStatus.CREATED, ...)
    session.add(interview)

    assert_transition(interview.status, InterviewStatus.WAITING_FOR_ANSWER)
    interview.status = InterviewStatus.WAITING_FOR_ANSWER

    await self._checkpoint(db, load_profile(...))
    await self._checkpoint(db, plan_interview(...))
    question = await self._create_question(db, interview, sequence=1)
    await self._checkpoint(db, wait_for_answer(generate_question(...)))

    await db.commit()  # 业务状态 + checkpoint 同一事务
```

### 4.4 Checkpoint：它是什么，能做什么，不能做什么

#### Checkpoint 能做什么

| 能力         | 场景                                         |
| ------------ | -------------------------------------------- |
| 记录流程轨迹 | 知道面试经过了哪些节点                       |
| 辅助恢复当前题目 | 刷新页面 → GET /interviews/{id}，服务端根据持久化状态和题目/答案数据回到当前题，checkpoint 提供流程轨迹证据 |
| 定位流程停滞 | 出问题时知道停在哪一步                       |
| 前端展示轨迹 | 用户可以看见面试进度                         |

#### Checkpoint 不能做什么

| ❌ 不能                     | 为什么                             |
| -------------------------- | ---------------------------------- |
| 从任意 Python 语句自动续跑 | 记录的是业务节点，不是代码执行位置 |
| 分布式任务租约和调度       | 没有 Worker 调度机制               |
| 节点级自动重试和补偿       | 没有通用的失败重试框架             |
| 时间旅行                   | LangGraph 有，当前没有             |

#### 面试必须准确表述

| ✅ 应该说                                      | ❌ 不能说                 |
| --------------------------------------------- | ------------------------ |
| "显式节点+checkpoint 实现可恢复人机工作流"    | "基于 LangGraph Runtime" |
| "借鉴了图工作流思想，当前由 Service 显式编排" | "实现了完整的工作流引擎" |

### 4.5 幂等答题：三层防护

#### 第一层：Idempotency-Key 查询

```python
existing = await db.scalar(
    select(UserAnswerModel).where(
        UserAnswerModel.question_id == question_id,
        UserAnswerModel.idempotency_key == idempotency_key,
    )
)
if existing is not None:
    return await self._snapshot(db, interview)  # 直接返回已有答案
```

#### 第二层：数据库唯一约束

```python
__table_args__ = (
    UniqueConstraint("question_id", "idempotency_key", name="uq_answer_idempotency"),
)
```

#### 第三层：提交前业务校验

问题是否属于当前面试？状态是否正确？是否是当前题目？

#### 三层防护总结

| 层级       | 机制                 | 防什么                 |
| ---------- | -------------------- | ---------------------- |
| **前端**   | 按钮防抖             | 用户快速双击（毫秒级） |
| **应用层** | Idempotency-Key 查询 | 正常重试（秒级）       |
| **数据库** | UNIQUE 约束          | 并发竞态（微秒级）     |

关键理解：应用层查询挡不住两个请求**同时到达**的竞态窗口——第一个还没 commit，第二个 SELECT 也查不到。数据库约束是最终防线。

### 4.6 用户刷新恢复的完整交互

```
浏览器刷新
    ↓
React 从 localStorage 读取 interview_id
    ↓
调用 GET /api/v1/interviews/{interview_id}
    ↓
服务端 InterviewService.get(interview_id)
    │
    ├── 查 InterviewSessionModel（状态、第几题、共几题）
    ├── 查 InterviewQuestionModel（当前题目、参考答案、Rubric）
    ├── 查 QuestionReferenceModel（题目引用的 Chunk）
    ├── 查 UserAnswerModel（已提交的回答）
    └── 返回 InterviewResponse
          { status, current_question_index, current_question, answers }
    ↓
前端重新渲染面试界面
```

### 4.7 状态流全景

```

```

### 4.8 故障场景

| 场景             | 处理方式                        |
| ---------------- | ------------------------------- |
| 用户刷新页面     | GET /interviews/{id} 服务端恢复 |
| 网络重试提交     | 幂等键查询 + DB 唯一约束        |
| 提交已完成的面试 | 状态机拒绝                      |
| 进程重启         | 面试状态已持久化                |

## 二、学员疑问与讨论记录

### Q1：为什么设计成断点重连的思路？面试中断可恢复怎么回答？

**回答：**

分两层。

第一层（问题驱动）：
> 面试的本质是人机交替——系统出题后必须停下来等人。这个"等待"可能几分钟到几小时。同步调用模型无法处理用户离开、网络中断、跨会话恢复。

第二层（方案选择）：
> 借鉴了工作流引擎的节点思想，但自己做是因为当前是三题线性流程，没有条件分支和循环回溯。节点签名天然对齐 LangGraph，将来流程变复杂可平滑迁移。

### Q2：刷新恢复的具体交互是怎样的？

**回答：**

前端用 localStorage 存 interview_id → 刷新后 GET /interviews/{id} → 服务端根据持久化的 InterviewSession、InterviewQuestion、UserAnswer 返回完整状态（当前第几题、题目内容、已提交答案）→ 前端重新渲染。checkpoint 主要提供流程轨迹和排障证据，不是唯一恢复来源。

所有状态都在服务端数据库，localStorage 只存一个 ID，避免浏览器状态与服务端不一致。
