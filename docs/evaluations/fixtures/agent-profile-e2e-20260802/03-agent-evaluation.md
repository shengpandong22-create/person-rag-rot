# Agent 评测与可信评分学习笔记

## 资料来源

- Anthropic Engineering, Demystifying Evals for AI Agents: https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- Anthropic, Building Effective Agents: https://www.anthropic.com/engineering/building-effective-agents

本文为基于官方资料整理的学习笔记，不是原文转载。

## 1. 为什么 Agent 比单轮问答更难评测

Agent 会跨多轮调用工具、修改状态并根据中间结果调整行为。最终答案正确并不能证明过程可靠，因为过程中可能发生无效调用、越权操作、重复副作用或高成本绕路。

Agent 评测应同时考虑：

- 任务是否完成；
- 是否遵守约束；
- 中间过程是否合理；
- 工具参数是否正确；
- 状态是否一致；
- 失败后是否安全恢复；
- 延迟和成本是否可接受。

## 2. 评测集从哪里来

评测集可以来自：

- 产品需求和验收案例；
- 生产失败日志；
- 用户反馈；
- 专家构造的边界条件；
- 安全红队场景；
- 历史回归问题。

高价值评测不是只覆盖常规成功路径，还应覆盖无答案、工具失败、权限不足、输入含糊和重复请求。

## 3. 多种 Grader 组合

不同问题需要不同评测器：

- 确定性规则：状态、格式、引用白名单、数据库副作用；
- 静态分析或代码执行：代码质量和测试是否通过；
- LLM-as-judge：语义质量、完整性和表达；
- 人工专家：高风险、争议和校准样本；
- 用户反馈：实际任务价值。

不能把所有评测都交给 LLM Judge。确定性规则能够判断的问题应优先使用代码判断。

## 4. Rubric 设计

Rubric 应描述可观察的成功标准，而不是抽象地写“回答优秀”。例如技术面试答案可以拆为：

- correctness：事实与结论；
- completeness：关键点覆盖；
- reasoning：因果与权衡；
- communication：结构与清晰度。

每个维度应有明确分值范围、扣分条件和必答点。最终总分由应用层根据维度分计算，可以防止模型返回自相矛盾的总分。

## 5. 置信与复核

低置信结果不应直接产生长期副作用。可以将结果路由为：

- final：可信，可进入报告和画像；
- review_pending：等待复核，暂不更新画像；
- disputed：初评和复核差异显著，阻断画像；
- low-confidence final：允许保存，但以更低权重更新。

复核模型与初评模型相同会产生相关性偏差。高风险场景应使用不同模型、不同提示策略或人工专家校准。

## 6. 过程评测

对工作流可以记录：

- 节点序列；
- 每个节点输入和输出摘要；
- 工具调用及参数；
- checkpoint；
- 重试和 fallback 原因；
- Token、延迟和成本；
- 最终副作用。

只有保留过程 Trace，才能判断失败来自规划、工具、检索、模型还是状态管理。

## 7. 评测驱动开发

先定义失败案例和验收标准，再修改 Prompt、模型或工作流。每次变更都在相同数据集上回归，并按模型、Prompt、工具和策略版本保存结果。

线上监控、用户反馈、A/B 测试、人工 Transcript Review 与离线评测应共同使用。单一自动指标不能覆盖 Agent 的全部质量。

## 8. 常见误区

- 只看最终回答，不看副作用；
- 用生成模型给自己的答案打分，却没有校准；
- 测试样本全部来自开发者预期；
- 只报告平均分，掩盖高风险失败；
- 修改 Prompt 后没有固定集回归；
- 将低置信结果直接写入长期画像。
