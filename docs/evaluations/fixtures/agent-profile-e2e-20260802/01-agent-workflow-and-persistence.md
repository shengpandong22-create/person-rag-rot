## 1. Workflow 与 Agent 的区别

Workflow 按预先定义的代码路径执行，强调可预测性、可测试性和稳定控制。Agent 则让大模型根据环境反馈动态决定过程和工具，适合步骤无法预先完全确定的开放任务。

工程实践中应优先选择满足业务需求的最简单结构。对于步骤固定、合规要求高、需要可靠恢复的流程，显式 Workflow 往往比完全自主 Agent 更合适。只有当路径确实需要根据中间结果动态变化时，才值得增加 Agent 自主性。

## 2. 常见工作流模式

### Prompt chaining

把复杂任务拆成顺序步骤，每一步的输出作为下一步输入。优点是易于校验和定位错误，缺点是链路较长时延迟增加。

### Routing

先识别输入类型，再选择不同处理路径。路由条件必须可观测，并提供无法分类时的默认路径。

### Parallelization

将互不依赖的子任务并行执行，最后聚合结果。适用于多个独立维度分析，但必须处理部分失败和结果冲突。

### Evaluator-optimizer

一个模型生成结果，另一个评估并提出改进，再根据明确标准迭代。它适用于评价标准清晰、改进可以量化的任务，不适合没有停止条件的无限循环。

## 3. Checkpoint 的职责

Checkpoint 保存工作流在某一时刻的状态快照。它通常与 thread 或 session 关联，使后续请求可以读取历史状态并从业务节点继续。

Checkpoint 支持的关键能力包括：

- 多轮状态保持；
- 工作流历史查看；
- 人工审批或用户输入前暂停；
- 故障后的状态恢复；
- 对节点输入和输出进行调试。

Checkpoint 不等于任意代码语句级恢复。要实现可靠恢复，节点本身还需要幂等，外部副作用也需要稳定业务键和事务保护。

## 4. Human-in-the-loop

工作流可以在需要用户回答、人工审批或风险确认时中断。中断前应持久化：

- 当前节点；
- 已完成步骤；
- 等待的输入类型；
- 恢复所需上下文；
- thread/session 标识。

恢复请求必须验证操作者权限和当前状态，避免过期输入推进错误流程。

## 5. 幂等与恢复

网络超时并不能证明服务端没有成功。客户端重试可能重复产生写入、扣费或状态推进。因此应为有副作用的请求提供 Idempotency-Key，并在数据库建立唯一约束。

可靠恢复至少需要区分：

1. 状态快照可读取；
2. 请求重复执行不会产生重复副作用；
3. 节点失败可以重试；
4. 不可逆外部动作有补偿或人工处理入口。

## 6. 工程风险

- 状态无限增长导致存储和上下文成本上升；
- checkpoint 与业务数据分别提交造成不一致；
- 节点重试重复调用外部服务；
- 人工中断长期不恢复形成悬挂任务；
- 过度自主导致路径难以复现和评测。

## 7. 面试回答结构

回答 Agent 工作流问题时，可以按“目标、状态、节点、中断、副作用、恢复、观测、边界”组织。不要只说使用了某个框架，要解释框架帮助解决了什么可靠性问题。
