# AgentMentor 双知识库 20 轮系统验收报告

验收日期：2026-08-02

## 1. 验收目的

本次验收不是单接口冒烟测试，而是从用户完整训练闭环观察系统：

1. AI Agent 与 Java 两个知识库各执行 10 场面试。
2. 每场 3 题，完整经过创建、启动、动态出题、提交答案、评分、报告和画像更新。
3. 不刻意构造低分，统一使用该题动态生成的参考答案，重点观察系统内部一致性、题目随机性、画像收敛、历史隔离和运行稳定性。

原始数据：

- `docs/evaluations/results/agent-10-round-audit-20260802.json`
- `docs/evaluations/results/java-10-round-audit-20260802.json`
- 执行脚本：`scripts/run_knowledge_base_interview_audit.py`

## 2. 测试矩阵

### AI Agent 知识库

覆盖 RAG、LangGraph、LangChain、上下文与记忆、工具调用与 MCP、评估可靠性、Agent 工程化。RAG、LangGraph、Agent 工程化分别设置重复主题场次，用于观察跨场随机性。

### Java 知识库

覆盖 JVM 与 GC、Java 并发、Spring 事务、Java 服务生产化。每个主题设置 2～3 个重复场次，用于观察跨场随机性和画像子主题更新。

## 3. 总体结果

| 指标 | AI Agent | Java |
|---|---:|---:|
| 完整场次 | 10 | 10 |
| 题目数量 | 30 | 30 |
| 失败场次 | 0 | 0 |
| 平均总分 | 56.5/60 | 57.4/60 |
| 最低/最高 | 54/60、60/60 | 56/60、60/60 |
| 平均单场耗时 | 30.18 秒 | 33.17 秒 |

| DeepSeek HTTP 错误 | 0 | 0 |

结论：20 场、60 题均完成闭环，接口和外部模型调用稳定，但单场等待时间偏长，缺少用户可感知的分阶段进度。

## 4. 题目随机性

### 量化结果

| 指标 | AI Agent | Java |
|---|---:|---:|
| 归一化后唯一题目 | 30/30 | 29/30 |
| 完全重复 | 0 | 1 |
| 最高跨场相似度 | 0.932 | 1.000 |
| 确定性模板替换题 | 1 | 2 |

AI Agent 的两场 RAG 第一题只有“六个环节/几个环节”等措辞差异，相似度 0.932；两场 Agent 工程化第一题相似度 0.778。

Java 的第 2、3 场 JVM 第一题完全相同；两场 Spring 事务第一题仅有轻微措辞变化，相似度 0.967。

### 原因定位

- Prompt 会传入“本场已出题目”，所以同一场三题能够避免明显重复。
- 历史场次的题目没有进入下一场 Prompt，也没有跨会话题目指纹或冷却窗口。
- 检索查询由主题、难度和固定题型提示组成，同主题多轮容易召回相同片段。
- 资料规模较小：Agent 60 次引用使用覆盖 15 个唯一切片；Java 60 次引用只覆盖 8 个唯一切片。
- 相似度过高时系统会替换成固定 `[3/3] 请从面试官视角复盘……` 模板，但没有记录成 fallback。

### 评价

当前随机性属于“措辞和场景有变化，但长期训练不足”。适合短期演示，不足以支撑同一主题连续数十轮训练。

## 5. 评分可信性

### 结果

- 60 题均为 `final`。
- Agent：29/30 题正确性和完整性满分；1 题缺少“迁移失败处理与回滚机制”，进入确定性复核。
- Java：30/30 题正确性和完整性满分。
- 没有错误声明。
- 3 题进入复核且完成，复核链路可用。
- 主要扣分来自推理与表达，不是事实错误，符合参考答案作答的预期。

### 局限

题目、参考答案和主要评分均由同一个 `deepseek-chat` 体系产生。本次验证能证明系统内部自洽，但不能独立证明评分具有人类面试官级准确性。要验证外部有效性，需要人工标注答案集、不同模型交叉评审或盲测 Rubric。

## 6. 画像准确性与隔离

### AI Agent

- 画像节点从 5 增长到 32。
- 10 场新增 10 条报告历史。
- RAG 主画像：0.6916 → 0.8299。
- Agent 工程化：0.7182 → 0.8058。
- 各稳定主题单独更新，没有写入 Java 主题。

### Java

- 画像节点从 3 增长到 7。
- 10 场新增 10 条报告历史。
- Java 主画像在连续高分下逐步上升，最终为 0.9383。
- JVM、并发、事务、生产化形成独立子知识点画像。
- 最后几轮 56/60 使主画像从约 0.95 小幅回落到 0.9383。这是指数渐进更新向近期分数收敛，符合当前算法，而不是数据覆盖错误。

### 错误与复习任务

两个知识库的错误模式和复习任务均为 0。本次答案全部较高，没有为了测试而构造错误，这一结果符合规则：总分达到 16/20 时不生成错误类型。

### 隔离

数据库中会话、报告、画像、更新事件全部带独立 `knowledge_base_id`。测试期间没有发现跨库写入，切换知识库取得的是两套独立画像和历史。

审计脚本结束时两边均为“原有 1 份报告 + 本次 10 份报告”。审计结束后，AI Agent 库又新增了一场不属于脚本的 `评估与可靠性` 面试（53/60），因此最终只读检查显示 Agent 12 份、Java 11 份报告；该额外交互没有进入 Java 历史，仍符合隔离预期，也没有污染本次保存的 10 轮原始数据。

## 7. 工作流与可观测性

20 场 Trace 均包含：

- `load_profile`
- `plan_interview`
- `wait_for_answer`
- `persist_answer`
- `finish_interview`

但是 Trace 中没有独立的 `generate_question` Checkpoint。代码虽然调用了 `generate_question` 状态函数，但随即包装成 `wait_for_answer` 后只保存最终节点。这与“每个关键节点均可观察”的文档表达不完全一致。

另外，3 道题因本场相似度过高被替换成确定性模板，但 Trace 的 `is_fallback` 仍为 false，日志中也没有 `interview_question.llm_fallback`。因此当前可观测性无法区分：

1. LLM 正常生成题目。
2. LLM 异常后的确定性降级。
3. 相似度门控触发的模板替换。

日志能够证明请求成功，但没有记录每次模型调用的 Token、成本、分阶段延迟和生成模式，无法回答“20 轮花费多少 Token/费用、慢在哪个阶段”。

## 8. 发现的问题与优先级

### P1：跨场题目去重缺失

表现：Java 出现 1 道完全重复题，RAG、Spring 等出现高度近似题。

建议：按 `knowledge_base_id + topic_key + difficulty` 保存最近题目指纹；生成前把最近 5～10 道核心问法加入 Prompt，生成后使用语义相似度或关键词指纹二次门控，并选择不同切片或题型重试一次。

### P1：下一轮计划错误使用 `low_mastery`

表现：Java 主画像已达到 0.9383，专项训练为 0，但 `/interview-plan` 仍返回 `reason=low_mastery`。

原因：`recommend_interview_plan` 会追加所有主题，只根据分数调整优先级，没有为高掌握度更换推荐理由或停止推荐。

建议：低于阈值才使用 `low_mastery`；高掌握度主题改为 `maintenance_review`、`coverage_expansion`，或在没有复习任务时提示“暂无薄弱项”。

### P1：题目生成模式不可观测

表现：3 道模板替换题没有 fallback 标记，Trace 也缺少 `generate_question` 节点。

建议：题目保存 `generation_mode`、`model_name`、`fallback_reason`、`similarity_score`；单独保存 `generate_question` Checkpoint，再进入 `wait_for_answer`。

### P2：评分缺少独立基准

表现：同一模型体系生成参考答案并评分，容易形成自洽偏差。

建议：增加小规模人工金标集；定期用不同模型或人工盲评校准；记录评分版本与模型版本，比较维度偏差。

### P2：画像样本不足时容易被解释成能力偏低

表现：新子知识点只经历 1 次高分更新时仍可能停留在 0.58 左右，这是先验 0.5 和渐进学习率导致的，但前端容易直接显示为“需要加强”。

建议：同时展示掌握度、证据次数和置信区间；证据少于 2～3 次时标记“样本不足”，不要直接判定薄弱。

### P2：端到端延迟与成本观测不足

表现：单场平均 30～33 秒、最大 44 秒；没有节点级耗时、Token 和费用统计。

建议：分别记录检索、每题生成、评分、复核耗时；采集输入/输出 Token 与估算费用；前端显示明确进度和当前阶段。

### P3：小知识库检索覆盖集中

表现：Java 30 题只使用 8 个唯一切片，限制了题目角度。

建议：补充集合、数据库、Spring IoC/AOP、MySQL、Redis、消息队列等资料；出题检索增加切片多样性约束和最近切片冷却。

## 9. 最终结论

当前工程的核心闭环已经真实可用：两个知识库可独立完成面试、评分、报告、历史和画像更新；20 场连续运行无失败，数据隔离正确，画像在高分下按规则渐进收敛。

但从长期训练产品角度，仍有三个必须在面试演示前说明或修复的问题：跨场题目去重、下一轮推荐语义、题目生成可观测性。它们不推翻现有架构，也不需要大改，适合用小范围增量优化完成。
