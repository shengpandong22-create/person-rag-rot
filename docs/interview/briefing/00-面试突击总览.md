## 1. 口述脚本

### 1.1 三十秒版（背下来）

> AgentMentor 是一个面向「Java 后端转 AI Agent 开发」的个人 AI 面试训练系统。
> 它把学习资料变成**可检索、可引用的证据**，用这些证据支撑两条消费路径：RAG 问答回答"资料能不能答"，模拟面试回答"我到底会不会"。
> 面试有两条互相隔离的路径：**正式画像训练**固定 3 题中等难度，评分沉淀为两层能力画像、错误模式和复习任务，形成闭环；**自定义练习**可以自选题数和难度，能出题、答题、出报告，但**不写画像、不写 coverage**，练习分数永远不会污染训练统计。
> 目录点只有在题目真实引用它的来源切片时才计入覆盖，所以"查漏"是有证据的，不是有个字段就算覆盖。
> 整套系统可以在 16GB 普通开发机上用 Docker Compose 跑通，无 GPU；LLM 相关链路都设计了明确的降级路径，没有模型 Key 也能演示核心闭环，但效果不等同真实模型模式。

### 1.2 两分钟版（在三十秒版基础上加四段）

**第一段 · 技术形态**
> 后端是 FastAPI + PostgreSQL/pgvector 的模块化单体，按 API、Application、Domain、Ports、Infrastructure 分层：API 只做协议与参数校验；Application Service 是真正的编排中心，负责事务、幂等和降级；Domain 层是纯函数规则，不依赖任何框架；Ports 用 Protocol 声明 LLM、Embedding、检索的契约；Infrastructure 实现这些契约，包括数据库访问、LLM 网关和 Embedding 适配器。前端是 React 工作台，只做展示，不承载唯一业务真相。

**第二段 · 两条消费路径的区别**
> 这两条路径的差别是我设计时最在意的一点。RAG 问答的目标是"这份资料能否回答当前问题"，所以它的核心约束是**证据充分性和引用可追溯**，证据不足要敢拒答。
> 模拟面试的目标是"用户是否真的掌握资料内容"，所以它的核心约束是**状态可恢复和评分可信**：题目、参考答案、Rubric 要落库，评分不能由模型决定最终分数，低置信结果不能污染长期画像。
> 面试内部再分两条互相隔离的路径：正式画像训练固定 3 题中等难度，计入画像与 coverage；自定义练习自选题数（1/3/5）和难度（easy/medium/hard），服务层保证它零画像写入、零 coverage 推进——用户练习多少次都不会影响下一轮训练推荐。

**第三段 · 三个我觉得最值得讲的设计**
> 第一，可信 RAG：不是检索分高就回答，而是先判断候选片段是否真的支持问题，生成后还要过引用白名单，不满足就降级或拒答。
> 第二，可验证的 coverage 闭环：目录点必须有真实来源切片，题目只有实际引用该来源才算推进覆盖；我用连续 6 个目标、6/6 引用命中、0 重复目标验证了这条链路，同时明确它只证明链路、不证明掌握。
> 第三，受控面试工作流与双模式隔离：三题面试跨越多次请求，必然有人机中断，所以每步写 checkpoint，答案提交带幂等键并由数据库唯一约束兜底，追问由门禁规则控制；题数和难度则被隔离成独立的练习模式，服务层强制默认训练口径，练习模式零污染。

**第四段 · 边界**
> 它现在是个人学习训练系统，不是企业级平台。几个我必须说清的边界在 §4，包括：练习不计入统计、多模型一致性不等于人工准确率、orphan 目录点保留不是清理失败。

### 1.3 它不是什么的对照表

| ❌ 不是 | ✅ 而是 |
|---|---|
| 调个 API 聊天的 Demo | 有状态、有规则、有长期记忆的训练系统 |
| 通用 ChatGPT 替代品 | 把大模型包装成受领域证据约束的训练应用 |
| LangGraph 运行时 | 自己实现显式节点 + checkpoint 的人机工作流 |
| 企业多租户平台 | 模块化单体，本机单用户优先 |
| 真实招聘评价系统 | 只用于个人学习，不代表正式招聘结论 |

## 3. 三个最强亮点

每点按「一句话 → 机制 → 怎么证明」讲。

### 亮点一 · 可信 RAG（🟢 ON）

- **一句话**：我把"检索分高"和"证据真能支持问题"拆成两件事，回答必须站在能追溯的证据上。
- **机制**：混合检索（全文 + 向量 + RRF 融合）拿到候选后，先做**证据充分性判定**——候选片段必须与问题有词面支持，且受支持候选的最高分要达到阈值；生成后再过**引用白名单**，模型只能引用本次检索上下文里的 chunk，编造引用直接降级；证据不足时明确拒答，而不是把模型常识伪装成资料结论。
- **怎么证明**：有两条用例直接钉住这个边界——"向量分高但无词面支持的片段不能算有效证据"、"模型返回不在上下文里的 chunk_id 时降级为确定性回答"。
- **代码**：`src/agent_mentor/application/answer_service.py` → `AnswerService.assess_evidence_diagnostics()` → 证据判定与诊断；`src/agent_mentor/rag/retrieval.py` → `validate_citations()` → 引用白名单校验。

### 亮点二 · 目录点—真实来源—题目引用—coverage 可验证闭环（🟢 ON）

- **一句话**：我把"有个 coverage 字段"变成"题目真的引用了这个目录点的来源切片"，查漏从记账变成可验证证据链。
- **机制**：入库时把可训练标题抽成稳定目录点，并记录每个点的真实来源 chunk（`knowledge_catalog_sources`）；选点出题时把该来源切片放入引用候选，题目持久化引用与目录点来源**相交**才写 `question_coverage_points`；覆盖统计只认这种 source-provenance 映射，历史不相交记录保留作审计、不推进状态。
- **怎么证明**：固定协议下连续 6 个目录点各跑一次真实模型出题，6/6 引用了各自来源切片、6/6 获得 attempted 记录、0 重复目标；同时明确这**只证明链路可运行，不证明用户已掌握**（`verified` 仍要求可信最终评分）。
- **代码/证据**：`src/agent_mentor/application/coverage_catalog.py` → `sync_document_catalog()` / `map_question_coverage()`；`src/agent_mentor/application/interview_service.py` → `_coverage_gap_focus()` / `_coverage_source_chunk()`；`docs/evaluations/continuous-coverage-training-20261023.md`。

### 亮点三 · 受控面试工作流与双模式隔离（🟢 ON）

- **一句话**：面试是跨多次请求的有状态流程，我显式实现了节点、中断、恢复和幂等；同时把"想换题数/难度练习"和"正式训练"隔离成两条路径，服务层保证练习零污染。
- **机制**：创建 → 启动（写 `load_profile`、`plan_interview` checkpoint）→ 出题（带 Rubric 与覆盖查漏）→ **人机中断等待回答** → 幂等提交 → 受控追问（每题最多一次，且要过回答质量门禁）→ 推进或结束。模式契约在服务层强制：`profile_training` 无论请求传什么都是 3 题 medium；`practice` 只接受 1/3/5 题与三档难度，且不写 `QuestionCoverage`、不走 `apply_interview_evaluations`。
- **怎么证明**：隔离数据库集成测试验证 practice 完成 5 题答题与报告后，画像、profile event、复习任务、coverage 全部零新增，coverage attempted/verified 不变化；同时验证 `profile_training` 传 1 题 hard 仍被写为 3 题 medium 并正常更新画像与 coverage。
- **代码/证据**：`src/agent_mentor/domain/interview.py` → `TrainingMode`；`src/agent_mentor/application/interview_service.py` → `resolve_training_plan()`；`src/agent_mentor/application/profile_service.py` → `apply_interview_evaluations()` 的 practice 只读分支；`docs/evaluations/practice-mode-verification-20261023.md`。

> 另有第四条评审主线（冻结数据集 + 预声明门槛 + 拒绝上线坏候选）压缩在 `02` §5，三个亮点之外不主动展开。

## 7. 代码定位五件套（极简示例）

> `01` 里每条链路都会有完整的五件套卡片；这里先给一个示例，让你熟悉**口述时的定位句式**。
> 五件套 = **入口 API → 编排 Service → 核心领域规则 → 关键持久化模型 → 出问题先看哪里**。

### 示例：面试里"同场追问没有生成"

```text
入口 API：       src/agent_mentor/api/interviews.py → POST /interviews/{id}/answers
编排 Service：   src/agent_mentor/application/interview_service.py → InterviewService.submit_answer()
核心决策：       interview_service.py → _maybe_create_follow_up()
关键持久化模型： InterviewFollowUpModel
出问题先看：     should_follow_up 是否成立、confidence 是否达门槛、会话状态是否 WAITING_FOR_ANSWER
```

**口述示范（被问到实现时照这个说）**：

> 这部分我会先从 `src/agent_mentor/api/interviews.py` 的提交答案入口进来，编排逻辑在 `InterviewService.submit_answer()`：它先做幂等查重和状态校验，再决定是否推进。真正决定要不要创建追问的是 `_maybe_create_follow_up()`，只有回答质量门禁通过、置信度达阈值、且该题还没有追问时才会创建；持久化模型是 `InterviewFollowUpModel`，唯一约束保证每题最多一条。如果现场发现没生成追问，我会按这个顺序排查：状态是不是 `WAITING_FOR_ANSWER`、门禁是否通过、唯一约束是否已存在记录。

这个句式的价值：**你不需要假装背过每一行代码，但能证明你掌握架构、关键路径、边界和排查方式。**

### 7.1 关于"代码是不是你写的"（被问到就照这个说）

> 我主导了问题定义、架构边界、关键策略和验收标准；实现阶段借助 AI 提升效率，但我会对关键链路做源码走读、验证测试和运行态核对。比如追问链路，我能从 API 入口定位到 Service 编排、门禁决策、状态约束与持久化模型，并解释为什么这样设计。

**不要这样说**：不要说"代码全部是我手写的"，也不要说"AI 写的我不太清楚"。前者经不起细节追问，后者直接否定了你的主导作用。
