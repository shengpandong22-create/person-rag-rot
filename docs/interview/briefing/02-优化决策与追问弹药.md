## 1. 主故事一 · 可信 coverage 闭环 🟢 ON

**问题**：早期只要数据库里有 coverage 字段、题目"提到过"某个知识点，就认为查漏成功了。但"有字段"不等于"真的考了"——题目可能根本没有引用这个目录点的来源资料，覆盖统计只是在记账，画像会因此高估用户的真实覆盖。

**约束**：覆盖推进必须**可验证、可审计**：每一行 coverage 都要能回答"这道题到底引用了这个点的哪块来源资料"；同时不能把历史数据全作废重来。

**候选**：
1. 保持字段级记账（题目主题匹配即算覆盖）—— 简单但不可验证；
2. 题目引用与目录点来源 chunk 相交才算覆盖 —— 可验证，但要求目录点带真实来源链接；
3. 让 LLM 判断"这题考了这个点吗"—— 灵活但引入模型不确定性，无法审计。

**指标 / 证据**（固定协议 `continuous-coverage-training-v1`，真实 DeepSeek 模型，6 个不同目录点各一次）：

```text
唯一目标数                          6
重复目标数                          0
generation.mode=llm                 6/6
目标 source chunk 被实际引用        6/6
目标获得至少一次 attempted 记录     6/6
题目生成 P50 / P95（nearest-rank）  3736.93 ms / 5638.34 ms
```

> 来源：`docs/evaluations/continuous-coverage-training-20261023.md`；协议 `docs/acceptance/continuous-coverage-training-contract-v1.md`；首轮实现验收见 `docs/evaluations/coverage-loop-acceptance-20261022.md`。

**决策**：选方案 2。目录点从可训练标题生成并记录真实来源 chunk（`knowledge_catalog_sources`）；选点出题时把来源切片放进引用候选；只有题目持久化引用与来源 chunk 相交才写 `question_coverage_points`；覆盖统计只认这种 source-provenance 映射，历史不相交记录保留作审计、不推进状态。

**当前状态**：🟢 默认启用；⚪ `verified` 仍要求可信最终评分，"题目出现过"只到 `attempted`。

**代码定位**：

```text
src/agent_mentor/application/coverage_catalog.py
  → classify_catalog_candidate()（哪些标题有资格成为目录点）
  → sync_document_catalog()（重建 source link，保留 KB 级稳定点）
  → map_question_coverage()（题目真实引用来源 chunk 才写 coverage）
src/agent_mentor/application/interview_service.py
  → _coverage_gap_focus()（选点；practice 模式恒不选）
  → _coverage_source_chunk()（把目标点的真实来源切片放入引用候选）
src/agent_mentor/application/profile_service.py → get_coverage()（只统计 source-provenance 映射）
```

**三十秒讲法**

> 我发现"有 coverage 字段"不等于真的查漏——题目可能根本没引用这个知识点的来源资料。所以我给每个目录点绑定真实来源切片，题目只有实际引用该来源才算推进覆盖，历史对不上的记录保留作审计但不推进。我用固定协议连跑 6 个目录点，6/6 引用了各自来源、0 重复目标。但我只会说这证明了链路可运行，不会说它证明了掌握——verified 仍然要求可信的最终评分。

## 2. 主故事二 · 安全目录治理 🟢 ON

**问题**：审计发现当前数据库里 195 个历史目录点中，**96 个已经没有来源链接**（orphan）——它们是早期规则或文档结构变化留下的。orphan 不能被选为训练目标，但它们是历史 coverage 映射的一部分，直接删会毁掉审计线索。

**约束**：治理动作必须**可回放、不毁历史**：不能删文档、chunk、历史题目、评分、画像、复习任务或历史 coverage 映射；操作前后必须能对比指标，证明治理没有让覆盖质量退化。

**候选**：
1. 直接批量删除 orphan 点 —— 干净但毁历史映射，且删除不可恢复；
2. 全库重建目录 —— 一致性强但影响面无法逐文档控制；
3. **逐文档安全重索引** —— 只重建 source link，逐份文档进行、每份等 `ready`，前后审计对比，不碰任何历史行。

**指标 / 证据**（BGE 知识库 7 份活动 Markdown 文档，逐文档 `POST /api/v1/documents/{id}/reindex`）：

| 指标 | 重索引前 | 重索引后 | 结论 |
|---|---:|---:|---|
| 可信目录点（source-backed） | 99 | 99 | 未下降 |
| qualified uncovered | 65 | 65 | 未下降 |
| 可信 source-provenance coverage mappings | 267 | 267 | 未下降 |
| provenance mismatch mappings | 16 | 16 | 未扩大 |
| provenance missing-reference mappings | 220 | 220 | 未扩大 |
| 当前规则会新增/解除的标题 | 0 / 0 | 0 / 0 | 无规则漂移 |
| orphan 目录点 | 96 | 96 | **仍然保留（预期结果）** |

> 来源：`docs/evaluations/coverage-catalog-safe-reindex-execution-20261023.md`；机器证据 `docs/evaluations/catalog-reindex-audit-20261023-after.json`（`orphan_catalog_point_count: 96`，`would_add_title_count: 0`，`would_unlink_title_count: 0`）；授权计划 `docs/design/coverage-catalog-safe-reindex-plan-20261022.md`。

**执行细节（被追问"你说安全，具体安在哪"）**：操作前保存只读健康审计与逐文档目录 diff，并保存相关表逻辑备份（`catalog-tables-before.sql`，SHA-256 已记录）；每份文档单独提交、等 status 回到 `ready` 再处理下一份；第 7 份文档首次执行日志 ID 与审计 UUID 不一致，**不采信该日志**，用审计确认的 document id 单独重跑并确认 `ready`。

**决策**：选方案 3。orphan 保留是预期结果而不是清理失败——安全重索引只重建来源链接；coverage 读取已经只信任 source-backed 点，orphan 不会成为可信训练目标。未来若确需物理清理，必须另走"可恢复删除 + 历史映射保留/迁移"方案，**不能把这次 reindex 说成已经清理完毕**。

**当前状态**：🟢 真实 BGE 知识库已逐文档安全重索引；⚪ orphan 物理清理未做，也不在本次范围。

**代码定位**：

```text
src/agent_mentor/application/coverage_catalog.py → sync_document_catalog()（删除并重建单文档 source link）
src/agent_mentor/api/knowledge.py → POST /documents/{id}/reindex（逐文档入口）
scripts/audit_catalog_reindex_plan.py / scripts/audit_coverage_health.py（只读审计）
```

**三十秒讲法**

> 审计发现 96 个目录点已经没有来源链接。我没有直接删——它们是历史 coverage 映射的一部分，删了审计链就断了，而且删除不可恢复。我选的是逐文档安全重索引：只重建来源链接，一份一份来、每份等 ready，前后各做一次只读审计。结果是可信目录点 99 个一个没少、source-provenance 映射 267 条一条没少、orphan 96 个原样保留。所以我会说"orphan 保留是设计决策"，不会说"目录已经清理干净了"。

## 3. 主故事三 · 题数/难度为什么隔离为 practice 🟢 ON

**问题**：用户很自然地想"今天状态好，练 5 题难题"或"只练 1 题快速热个身"。但如果题数和难度可以自由带进正式训练，不同轮次的面试就**不再可比**：3 题 medium 的画像被 1 题 hard 的评分稀释，coverage 统计混入练习目标，下一轮训练推荐被噪声带偏。

**约束**：正式训练必须保持唯一、可比较的口径；用户的自定义需求必须被满足；隔离不能只靠前端隐藏按钮——**边界要在服务层切死**。

**候选**：
1. 允许自由题数/难度进入正式训练 —— 灵活但毁掉可比性；
2. 只在前端限制 —— 一个手工构造的请求就能绕过；
3. **服务层双模式**：`profile_training` 强制 3 题 medium；`practice` 只接受 1/3/5 题与三档难度，且切断全部长期记忆写入。

**实现（服务层强制点）**：

```text
resolve_training_plan()          profile_training 恒写 3 题 medium；practice 非法题数/难度 422
create_interview()               practice 携带 coverage_catalog_point_id 直接拒绝（422）
_coverage_gap_focus()            对 practice 恒返回 None（coverage-gap 选点仅属于正式训练）
_create_question()               map_question_coverage() 仅对 profile_training 调用
apply_interview_evaluations()    practice 只读快照返回：不写 ability_profiles /
                                 profile_update_events / review_tasks
前端 InterviewPanel              模式选择 + "不计入能力画像和知识覆盖"警示 + 报告/历史模式标签
```

**指标 / 证据**（隔离数据库集成测试 + 独立审查）：

```text
practice 完成 5 题答题、评分与报告后：
  QuestionCoverage / ProfileUpdateEvent / ReviewTask  零新增
  coverage attempted / verified                       不变化
profile_training 请求携带 1 题 / hard：
  服务层仍写为 3 题 / medium，并正常产生画像与 coverage 结果
迁移回归 0017 → 0016 → 0017                            通过
迁移后既有库检查：92 个历史 session 全部为 profile_training
```

> 来源：`docs/evaluations/practice-mode-verification-20261023.md`。

**决策**：选方案 3，并且把它定义为**数据治理而不是 UI 功能**——它保护的是"训练统计只包含训练"这条不变量。practice 保留完整的出题、答题、报告、引用与 workflow trace 能力，用户练习体验不降级；报告和历史带"练习模式"标签，避免练习分数被误读成画像变化。

**当前状态**：🟢 双模式默认启用（默认即正式训练）；practice 报告仍进入报告历史与趋势（带标签），这是明确的取舍：物理删除会毁掉用户的练习记录。

**代码定位**：

```text
src/agent_mentor/domain/interview.py → TrainingMode / PRACTICE_QUESTION_COUNTS / PRACTICE_DIFFICULTIES
src/agent_mentor/application/interview_service.py → resolve_training_plan()
src/agent_mentor/application/profile_service.py → apply_interview_evaluations() 的 practice 分支
src/agent_mentor/infrastructure/database/models.py → InterviewSessionModel.training_mode
migrations/versions/20261023_0017_interview_training_mode.py（历史行回填 profile_training）
frontend/src/components/InterviewPanel.jsx → 模式选择与警示
```

**三十秒讲法**

> 用户想自选题数和难度，但这个需求直接放进正式训练会毁掉可比性——3 题 medium 的画像会被 1 题 hard 的评分稀释。所以我做了双模式：正式训练固定 3 题 medium，服务层强制，请求传 1 题 hard 也会被写回 3 题 medium；想自选走 practice，1/3/5 题三档难度，但服务层把它的画像、profile event、复习任务、coverage 写入全部切断。隔离数据库测试验证了 practice 答完 5 题之后这些表零新增、coverage 不变化。我觉得这体现的是数据治理：练习可以很自由，但训练统计必须只包含训练。

## 4. 评分证据收口：能说到哪一步 🟢

**问题**：评分是整个闭环的地基。"LLM 打分可不可信"必须有证据，但证据的**边界**必须和证据本身一起讲。

**当前证据（按强度排序）**：

| 证据 | 内容 | 它证明什么 | 它不证明什么 |
|---|---|---|---|
| 三档稳定性面板 | 同一 `deepseek-chat` 对 low/mid/high 三个固定样本各评 5 次，共 **15 次**；mid/high 四维与总分完全一致；low 出现 4–5/20 的一分波动（总体标准差 0.40）；三条样本复核路由均一致 | 同一模型、同一固定答案上的**重复性**；低分档有一分波动但复核路由不漂移 | 不是人工一致性、人工改判率或评分准确率；不代表全部题型和真实用户答案 |
| 多模型盲审趋同 | 两份独立模型输出对固定 **12 条** blind 样本的粗粒度判断：质量标签 **12/12** 一致、是否需复核 **12/12** 一致、双字段同时一致 **12/12** | 对无作者标签、无既有分数的固定样本，两个模型的粗粒度判断趋同 | 不证明人工评分一致性或生产评分准确率；模型可能共享训练语料或提示偏差；样本梯度清晰，不能外推边界答案 |
| 运行态基线 | 同一固定高质量答案连续 5 次评分总分 19–20/20，`completeness` 标准差 0.4，复核路由 5/5 一致 | 与上同类的单点稳定性观察 | 同上 |

> 来源：`docs/evaluations/scoring-stability-panel-20261023.md`（数据集 SHA-256 `91361bd2…`）；`docs/evaluations/multi-model-blind-calibration-20261023.md`；`docs/evaluations/runtime-and-scoring-stability-baseline-20261022.md`。

**明确的缺口**：**尚无真实人工评分金标准。** 人工对照契约（`docs/acceptance/human-scoring-comparison-contract-v1.md`）要求至少两名独立人工评审盲填 worksheet、由比较器重算总分；在获得之前，任何"评分与人工一致""评分准确率"的表述都是夸大。

**评分侧仍然成立的工程结论**（与人工金标准无关，靠结构与约束保证）：
- LLM 不决定最终分数：模型只给四维与结构化信号，总分由应用层 `total_score()` 重算；
- 不可信评分不进长期记忆：`disputed` / `review_pending` 不更新画像，低置信 `final` 降权更新；
- 每个 evaluation 只应用一次，靠 `profile_update_events` 唯一约束幂等。

**三十秒讲法**

> 评分可信度我分两层讲。结构层我有确定性保证：模型只打四维，总分应用层重算，争议和待复核不写画像。行为层我只有小样本证据：15 次三档稳定性观察显示中高分完全一致、低分有一分波动但复核路由不漂移；两个模型对 12 条盲样 12/12 粗粒度趋同。但我没有人工金标准——所以我会说"有重复性和趋同证据"，不会说"评分已被人工验证"或给出准确率数字。补齐它需要两名独立评审按契约盲填，这是明确的下一步。

代码：`src/agent_mentor/application/answer_service.py` → `assess_evidence_diagnostics()`；`src/agent_mentor/domain/evidence.py` → `EvidenceGatePolicy`。

### 5.2 检索评测：用数据定位问题 🟢

四组消融显示 Recall@6 各家打平（vector-only 70.59% / MRR 48.53%），瓶颈不在排序；损失漏斗 candidate@20 88.24% → post-filter@6 70.59%，5 个 miss 里 3 个死在每文档配额。配额 4 能把 R@6 提到 82.35%，但影响所有检索路径，未成为默认。

> 回链：`docs/evaluations/relation-value-v3-acceptance-20261004.md`、`docs/decisions/ADR-002 / ADR-003 / ADR-004`、`docs/evaluations/shadow-agent-v2-development-20261005.md`。

## 6. 追问弹药

> 每题只记三样：**30 秒答案的骨架 / 对方可能往哪追 / 一条不能说错的线**。

### A. RAG 质量

**A1. 为什么用混合检索而不是纯向量？**
- 30 秒：向量擅长语义近似，全文擅长类名、术语、精确片段；RRF 只融合排名、不比较分数，工程上更稳。消融显示纯向量头部最强，但两路互补提升了召回稳定性。
- 追问方向：RRF 的 k 怎么定 / 两路权重能不能调 / 为什么不用 reranker
- 红线：不要说"向量一定更好"，也不要宣称已有生产级中文 BM25。

**A2. 每文档配额和相邻块去重为什么必要？**
- 30 秒：否则一篇长文档的连续 chunk 会占满 Top-K，用户拿不到多来源证据。漏斗显示漏召回主要就死在这一步。
- 追问方向：会不会误杀有用证据 / 配额为什么是 3
- 红线：不要说 3 或 4 是"最优配置"——配额 4 只是消融候选，未成为默认。

**A3. 证据不足怎么处理？**
- 30 秒：先判证据充分性，不足就明确拒答或受控降级，不把模型常识伪装成资料结论；用户可显式开启模型补充，但要标注来源。
- 追问方向：阈值怎么定的 / 会不会过度拒答
- 红线：不要说"完全消除了幻觉"，只说降低了无依据生成。

### B. 状态机 / 幂等 / 恢复

**B1. 为什么不用 LangGraph？**
- 30 秒：节点本来按图节点形态设计，边由 Service 调用顺序显式表达，当前规模自研更可控、可观测性完全掌握；LangGraph 适合节点更多、分支更复杂的场景。
- 追问方向：迁移成本多大 / 多 Agent 协作怎么办
- 红线：不要说"我这就是 LangGraph 的思路"，也不要说"LangGraph 太复杂我用不来"。

**B2. checkpoint 能做什么、不能做什么？**
- 30 秒：能做——节点级轨迹、快照、刷新恢复证据、排障定位；不能做——任意代码位置续跑、任务租约、分布式调度、节点级补偿。恢复动作由服务层根据会话与答案状态执行。
- 追问方向：那进程重启后怎么恢复 / 为什么不做补偿
- 红线：不要承诺"从 checkpoint 重放"或分布式故障恢复。

**B3. 并发两个请求同时提交同一题？**
- 30 秒：幂等三层——前端复用同一 key（防重复点击）、服务端先查已有答案（友好返回）、数据库唯一约束 `uq_answer_idempotency`（并发最终防线）；冲突时回滚并返回既有快照。
- 追问方向：为什么不直接用 `ON CONFLICT` / 幂等键会过期吗
- 红线：不要说"完全无竞态"。可以承认未来可改成原生 upsert 减少异常路径。

### C. LLM 可靠性与降级

**C1. 没有模型 Key 怎么跑？**
- 30 秒：LLM 相关链路都有确定性降级——出题、评分、回答都能用规则或模板兜底，所以核心闭环可演示；但**效果不等同真实模型模式**。
- 追问方向：降级效果的量化 / 会不会掩盖问题
- 红线：绝不说"降级和真模型效果等价"。

**C2. 结构化输出失败怎么办？**
- 30 秒：网关做 JSON 提取与 Pydantic 校验，失败重试并按状态码分级；仍失败则抛错，由上层降级为确定性路径。`response_format` 不被支持时自动去掉重发。
- 追问方向：重试会不会放大成本 / 温度怎么设
- 红线：不承诺"模型输出稳定"。

**C3. 流式是怎么实现的？**
- 30 秒：**目前是伪流式**——先拿到完整内容再切分推送，首 token 延迟等于整段生成时间。真 SSE 是明确待办。
- 追问方向：为什么不做真流式 / 做了要改什么
- 红线：绝对不要说"我实现了真流式 SSE"。

### D. Agent 边界

**D1. 这个项目里的 Agent 在哪？**
- 30 秒：分两层讲——①受控 Agentic 工作流：显式节点、人机中断、checkpoint、幂等，关键状态流转由应用层控制；②只读 Shadow Agent 原型：三工具、三步预算、零业务写入，默认关闭。
- 追问方向：工具调用在哪 / 为什么不用 function calling
- 红线：不要说"实现了完整自主 Agent"。当前网关只支持结构化生成，**没有 tool-calling 能力**。

**D2. Shadow Agent 为什么关闭？**
- 30 秒：V1 动作准确率 69.44%、V2 完成率 41.67%，都没过预声明门槛；安全指标全过但"能安全调用工具"不等于"能稳定做对决策"。
- 追问方向：那 V2 的 100% 是什么意思
- 红线：必须主动澄清——那些 100% 是**确定性 fallback 导出的**，不是模型决策成功。

**D3. 什么时候才该上 LangGraph？**
- 30 秒：当节点数量和分支复杂度超过显式编排的可维护范围，或者需要运行时级的 checkpoint、子图、并行分支和人工中断恢复时。当前面试流程（含 practice 隔离）不需要。
- 追问方向：多 Agent 状态流转怎么设计
- 红线：不要用"复杂就该用框架"这种话术，要能说出具体触发条件。

### E. 企业化差距

**E1. 多租户和权限怎么补？**
- 30 秒：数据模型已预留 `user_id`，画像已按知识库隔离；企业化需要行级安全或按库隔离、RBAC/ABAC、文档 ACL 和审计日志。
- 追问方向：现在能不能多人用 / 数据隔离做到什么程度
- 红线：不要说"现在支持多租户"，当前是单用户本机部署。

**E2. 复杂文档怎么补？**
- 30 秒：当前支持 Markdown/TXT/PDF/DOCX 的基础解析，**没有 OCR、版面分析和复杂表格重建**。补法是接版面分析模型、表格结构化、扫描件 OCR 与跨页上下文重建。
- 追问方向：表格和代码块现在怎么处理
- 红线：不要说"复杂文档已解决"。

**E3. 评测怎么规模化？**
- 30 秒：已有冻结的人工标注检索集、评分边界夹具、机器可读报告和门槛协议；评分侧尚无人工金标准。短板是样本量有限且没有线上 A/B，所以我不给泛化准确率。
- 追问方向：怎么扩样本 / 怎么避免过拟合
- 红线：不要给一个"总体准确率"数字。

### F. 覆盖与练习隔离（新）

**F1. coverage 推进了说明我掌握了吗？**
- 30 秒：不代表。`attempted` 只证明这个目录点被真实考到过一次；`verified` 仍要求可信最终评分，而且 6 目标运行证明的是链路，不证明掌握度。
- 追问方向：那 verified 的标准是什么 / 会不会永远到不了 verified
- 红线：不要说"考过就是掌握"，也不要把 6/6 说成"掌握度验证"。

**F2. 用户练习会影响我的画像吗？**
- 30 秒：不会。practice 在服务层被切断：不写 `QuestionCoverage`，不走画像更新，不建复习任务；集成测试验证答完 5 题后这些表零新增、coverage attempted/verified 不变化。
- 追问方向：那练习分存在哪 / 为什么要保留练习报告
- 红线：不要说"前端藏了入口所以没事"——边界在服务层；也不要说"练习报告没存"，它存报告但带模式标签。

**F3. 为什么正式训练不让用户自选题数？**
- 30 秒：可比性。3 题 medium 是唯一训练口径，混入 1 题 hard 会稀释画像、污染 coverage 目标；自选需求由 practice 承接，但它的数据不进训练统计。
- 追问方向：用户就是想多练怎么办 / 这个口径以后会变吗
- 红线：不要把"题数/难度自由可选"说成正式训练能力；也不要说"永远不会变"——变口径必须走完整回归与独立验收。
