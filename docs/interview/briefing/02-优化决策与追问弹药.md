## 1. 主故事一 · Evidence Gate：为什么敢拒答 🟢 ON

**问题**：RAG 最危险的不是"答不出来"，而是"答得像真的"。检索分高只说明语义相近，不等于这段资料能支持当前问题；即使证据相关，模型也可能引用一个不存在的 chunk。

**约束**：默认门禁必须**可解释、可测试、可复现**，不能依赖一个自己都说不清边界的模型判定；同时不能因为过度保守把正常问题全拒了。

**候选**：
1. 纯分数阈值 —— 简单，但高分无关片段会漏过；
2. 词面支持过滤 + 阈值 —— 可解释，能挡住"高分但不相关"；
3. clause / claim 级语义判定 —— 更强，但引入语义模型的不确定性。

**指标 / 证据**：两条测试直接钉住这个边界。

```text
tests/unit/test_retrieval.py → test_answer_service_assesses_only_lexically_supported_candidates()
  → 向量分很高但没有任何词面支持的片段，不能算有效证据

tests/unit/test_llm_fallback_observability.py → test_answer_service_downgrades_when_llm_hallucinates_citation()
  → 模型返回不在本次上下文里的 chunk_id 时，降级为确定性 grounded 回答
```

**决策**：默认走方案 2（`EvidenceGatePolicy.current_binary_v1`：词面支持过滤 + 受支持候选最高分比对阈值）；方案 3 作为二级策略 `clause_demand_v1` 保留，但**不设为默认**，因为它还没有通过独立验收。

**当前状态**：🟢 默认门禁启用；🟡 二级策略已实现、非默认；⚪ 完整的语义蕴含校验未接入默认 Gate。

**代码定位**：

```text
src/agent_mentor/application/answer_service.py → AnswerService.assess_evidence_diagnostics()
src/agent_mentor/domain/evidence.py → EvidenceGatePolicy
src/agent_mentor/config.py → Settings.evidence_gate_policy
```

**三十秒讲法**

> 我做的第一件事是把"检索分高"和"证据真能支持问题"拆开。检索分只说明语义近，所以我先按词面支持过滤候选，再看受支持候选里的最高分是否达阈值；生成之后还有引用白名单，模型只能引用本次上下文里的 chunk，编造就直接降级。拒答在这里不是失败，而是证据不足时不下结论——在训练场景里，错答的代价比少答高。二级的 clause 级策略我已经实现了，但它没通过独立验收，所以保持非默认。

## 2. 主故事二 · 检索评测：怎么用数据定位问题 🟢 ON

**问题**：早期优化检索只能靠"感觉召回还行"。面试官一追问"你怎么证明调这组参数真的有效"，主观体验就不够了。

**约束**：必须在个人开发机上可复现、没有线上 A/B 流量；更重要的是——**数据不能拿去反复调参**，否则指标失去意义（冻结 split、预声明门槛）。

**候选**：四组检索消融（纯向量 / 纯全文 / RRF / RRF + 启发式重排）。

**指标 / 证据**

四组消融（冻结 Validation 集）：

| 模式 | Recall@1 | Recall@3 | Recall@6 | MRR | P95 |
|---|---:|---:|---:|---:|---:|
| vector-only | 35.29% | 52.94% | **70.59%** | **48.53%** | 58.55 ms |
| text-only | 17.65% | 35.29% | 41.18% | 26.67% | 50.14 ms |
| RRF | 29.41% | 52.94% | 70.59% | 44.61% | 355.76 ms |
| RRF + heuristic | 17.65% | 52.94% | 70.59% | 36.47% | 95.79 ms |

> 来源：`docs/evaluations/evidence-gate-claim-evaluation-20260929.md`

**关键转折**：Recall@6 上各家打平，说明瓶颈不在融合排序。于是做了**损失漏斗**诊断：

```text
candidate Recall@20   88.24%
  ↓
pre-filter Recall@6   82.35%
  ↓
post-filter Recall@6  70.59%   ← 5 个漏召回里，2 个没进候选池，3 个被每文档配额过滤掉
```

**决策**：不去调 RRF 权重，而是修**每文档配额**这个真正的瓶颈。配额从 3 调到 4，Validation Recall@6 从 70.59% 提升到 82.35%（与无限额相同，且来源多样性更好）。

**但它没有上线** —— 因为配额调整影响所有检索路径，需要完整回归与独立验收，不能因为一个消融指标就切默认。默认仍是 3。

**当前状态**：🟢 评测 runner、冻结数据集与机器可读报告可用；🟡 配额 4 是 eval-only 候选，未成为默认策略。

**代码定位**

```text
evals/run.py → retrieval / retrieval-ablation / scoring / all 子命令
src/agent_mentor/infrastructure/retriever.py → PostgresHybridRetriever.retrieve()
src/agent_mentor/rag/retrieval.py → reciprocal_rank_fusion()
src/agent_mentor/config.py → Settings.retrieval_max_chunks_per_document
```

**三十秒讲法**

> 我没有一上来就调 RRF 权重。我先做了四组消融，发现 Recall@6 上大家打平，说明瓶颈不在排序；再做损失漏斗，看到候选池有 88.24%、过滤后掉到 70.59%，5 个漏召回里 3 个是死在每文档配额上的。所以我去改配额，R@6 能到 82.35%。但我没有直接切默认——它会影响到所有检索路径，得走完整验收，所以现在还是候选状态。

## 3. 主故事三 · 面试闭环质量：怎么避免污染长期记忆 🟢 ON

**问题**：评分如果不可信，它就会一路污染到画像、错误模式和复习任务 —— 而画像会反过来决定下一轮练什么，噪声会被放大。

**约束**：LLM 不能决定最终分数；不可信的评分不能进长期记忆；新增资料不能凭空改变已有掌握度。

**候选**：直接采信模型给的分数与总分 → 改成"应用层重算 + 复核路由 + 画像更新门禁"。

**指标 / 证据**

评分区分度（12 条人工标注样例，确定性 fallback vs LLM 评分）：

| 指标 | fallback | LLM 评分 |
|---|---:|---:|
| MAE | 7.1667 | **1.6667** |
| Pearson correlation | 0.8735 | **0.9802** |
| Reviewer routing accuracy | 0.4167 | **1.0** |
| Band order accuracy | 1.0 | 1.0 |

历史题冷却修复前后（同一批样例）：

| 指标 | 修复前 | 修复后 |
|---|---:|---:|
| MAE | 2.0 | 1.6667 |
| Pearson correlation | 0.9671 | 0.9691 |
| Reviewer routing accuracy | 0.6667 | **1.0** |

> 来源：`docs/evaluations/training-quality-audit-20260902.md`

增量查漏闭环（向已有画像的知识库新增文档）：

```text
导入前：11 个有效知识点 = 8 已验证 + 3 未覆盖；主主题掌握度 0.9383
导入后：15 个有效知识点，4 个 Redis 知识点全部 uncovered；主主题掌握度仍是 0.9383  ← 上传不改画像
三轮面试：57/60、56/60、58/60
  → Cache-Aside 一致性 mastered（6 次验证，94.17%）
  → 缓存击穿 mastered（3 次，96.67%）
  → 缓存雪崩 mastered（6 次，94.17%）
  → 缓存穿透 uncovered（0 次）  ← 整场高分也没有把它误判为掌握
18 条题目引用中，15 条来自新导入文档；主主题掌握度 0.9383 → 0.9509（只由可信评分驱动）
```

> 来源：`docs/evaluations/incremental-document-coverage-acceptance-20260802.md`

**决策**：
1. 总分由应用层用 `total_score()` 重算，不信模型给的 total；
2. `disputed` / `review_pending` 一律**不更新画像**，低置信 `final` 降权更新；
3. 每个 evaluation 只应用一次，靠唯一约束 + `profile_update_events` 幂等；
4. 复习任务需要**连续两次可信高分**才置完成；
5. 掌握度与覆盖度分离：只有题目真实引用对应 chunk 且取得可信评分，覆盖状态才推进。

**当前状态**：🟢 全部默认启用。

**代码定位**

```text
src/agent_mentor/application/evaluation_service.py → evaluate_interview() / _evaluate_answer() / build_report()
src/agent_mentor/domain/evaluation.py → total_score() / review_reasons_for() / initial_review_route()
src/agent_mentor/application/profile_service.py → apply_interview_evaluations() / training_focuses()
src/agent_mentor/domain/profile.py → profile_update_decision() / updated_mastery() / review_verification_progress()
```

**幂等证据**

```text
tests/unit/test_data_consistency_constraints.py → test_user_answers_are_idempotent_per_question_key()
tests/unit/test_data_consistency_constraints.py → test_profile_update_event_is_idempotent_per_evaluation()
```

**三十秒讲法**

> 我最担心的是评分污染长期记忆，因为画像会决定下一轮练什么。所以三件事：第一，总分不由模型决定，模型只给四个维度，应用层重算，保证四维之和与总分一致；第二，争议和待复核的评分一律不写画像，低置信的降权写；第三，每个评分只应用一次，有唯一约束兜底。测下来 LLM 评分的 MAE 从 7.1667 降到 1.6667、与人工相关性 0.9802、复核路由命中 1.0。还有一个我比较满意的验证：往已经有画像的知识库里新增一份资料，4 个新知识点全部是 uncovered，主主题掌握度一点没变——上传资料不会凭空改变画像。

## 4. 合并章节 · 如何用独立验收阻止坏候选进入生产 🟡 OFF

**统一讲法**：这一段的核心不是"我做了三个功能"，而是"我建了一套**发布门禁**，并且它真的拦住过东西"。

门禁流程：

```text
冻结数据 → 实现候选 → 预声明硬门槛 → 独立验收集一次性运行 → 不达标则停止
（不降门槛、不针对验收集调参、不重跑已消耗的数据）
```

**决策总表**（面试时可以直接展示）

| 候选 | 局部收益 | 独立结果 | 决策 |
|---|---|---|---|
| Relation-Value V3 | 负例拒绝 100% | 正例 demand recall 6.45% | **不上线** |
| heading 二阶段检索 | Development 补回 6/6 miss | regression 固定消费精度 1.9% | **不接生成链路** |
| Shadow Agent V1 | schema 100%、安全护栏全通过 | 动作准确率 69.44%、稳定率 83.33% | **关闭** |
| Shadow Agent V2 | 首路由/动作/零写入均 100% | 正常完成率 41.67% | **关闭** |

### 4.1 Relation-Value V3：安全但不可用

```text
Demand accuracy                      32.56%   vs ≥90.00%   失败
Positive demand recall                6.45%   vs ≥87.10%   失败
Positive all-demands row accuracy     8.33%   vs ≥83.33%   失败
Negative demand rejection           100.00%   = 100.00%    通过
Binding precision                    22.22%   vs ≥90.00%   失败
Paired discrimination                 9.09%   vs ≥90.91%   失败
P95                                  0.2291ms vs ≤50ms     通过
```

**结论**：只有 2/31 正例 demand 完整绑定，而 12/12 负例全部拒绝 —— 这是典型的"安全但不可用"，**不能因为负例指标漂亮就上线**。实验线正式关闭，不创建 V4。

> 来源：`docs/evaluations/relation-value-v3-acceptance-20261004.md`；决策：`docs/decisions/ADR-002-关闭RelationValueV3实验线.md`

### 4.2 二阶段检索：能补回召回，但自动消费不可靠

已通过的验证：

```text
原始 Top-6 对象与顺序保持率 100%（单调安全）
Development：Combined Recall 0.50 → 1.00，补回 6/6 miss
regression：30/30 样本原 Top-6 完全一致；Gate 与生成调用次数均为 0
额外检索 P95 增量约 100 ms
```

未通过的验证：

```text
regression 固定消费精度 0.019（10 个负例产生 185 个 supplemental candidates）
rank-capped-3 把消费量降低约 57%，但综合精度只有 0.2353，仍低于预声明的 0.30
```

**结论**：基础设施保留、feature flag 默认关闭，**不接 Gate、不接生成、不注册 API、不做前端按钮**。定位到的根因是"缺少可靠的 demand-to-evidence support 信号"，这被记录为已知限制而不是用未证明的规则掩盖。

> 来源：`docs/decisions/ADR-003-阶段性关闭二阶段检索生产接入.md`

### 4.3 Shadow Agent：被问"你项目里的 Agent 在哪里"时再展开

**为什么保留它**：它证明了**"模型建议层"与"画像事实层"可以严格隔离**。

```text
零污染审计（llm=None 的确定性 fallback 路径）：
  ability_profiles / error_patterns / review_tasks / profile_update_events /
  evaluations / knowledge_catalog_points  →  前后指纹完全一致
  shadow_agent_runs → 0 → 1（唯一允许的副作用：审计轨迹）
  business_writes = 0
```

> 来源：`docs/evaluations/shadow-agent-zero-write-audit-20261005.md`

**为什么关闭**：

| 版本 | 结果 |
|---|---|
| V1（真实模型 `deepseek-chat`，36 次运行） | 工具选择准确率 86.11%（<90）、动作准确率 69.44%（<85）、跨三轮稳定率 83.33%（<85）→ 不通过 |
| V2（确定性策略收敛路由与动作） | 正常完成率 41.67%（<95）；首路由/动作/零写入虽 100%，但**完成率不达标** → 关闭 |

> 来源：`docs/evaluations/shadow-agent-semantic-development-20261005.md`、`docs/evaluations/shadow-agent-v2-development-20261005.md`；决策：`docs/decisions/ADR-004-关闭ShadowAgentV1并进入V2.md`

**⚠️ 这里有一条必须说对的红线**

> V2 里那些 100%（首路由、动作准确率、业务零写入）是 **executor 用确定性策略 fallback 导出的结果**，不是模型决策成功。报告里明确写了"该安全结果不能被误称为模型决策成功"。被追问时必须主动澄清，否则就是夸大。

**三十秒讲法（被问"Agent 在哪"时）**

> 我有一个只读 Shadow Agent 原型：三个只读工具、最多三步、参数 schema 白名单、必须人工确认、业务零写入，已用审计证明开启路径不会改变画像和评分任何一张表。但真实模型 V1 动作准确率只有 69.44%，V2 用确定性策略收敛后完成率仍只有 41.67%，所以我把它关了，只保留为默认关闭的技术原型。我做它的价值是证明了"模型建议层"和"画像事实层"可以彻底隔离——而不是为了在简历上写"多 Agent"。

## 5. 追问弹药：5 类 × 3 题

> 每题只记三样：**30 秒答案的骨架 / 对方可能往哪追 / 一条不能说错的线**。

### A. RAG 质量

**A1. 为什么用混合检索而不是纯向量？**
- 30 秒：向量擅长语义近似，全文擅长类名、术语、精确片段；RRF 只融合排名、不比较分数，工程上更稳。消融显示纯向量头部最强，但两路互补提升了召回稳定性。
- 追问方向：RRF 的 k 怎么定 / 两路权重能不能调 / 为什么不用 reranker
- 红线：不要说"向量一定更好"，也不要宣称已有生产级中文 BM25。

**A2. 每文档配额和相邻块去重为什么必要？**
- 30 秒：否则一篇长文档的连续 chunk 会占满 Top-K，用户拿不到多来源证据。漏斗显示漏召回主要就死在这一步。
- 追问方向：会不会误杀有用证据 / 配额为什么是 3
- 红线：不要说 3 或 4 是"最优配置"——配额 4 只是消融候选，未成为默认。

**A3. 证据不足怎么处理？**
- 30 秒：先判证据充分性，不足就明确拒答或受控降级，不把模型常识伪装成资料结论；用户可显式开启模型补充，但要标注来源。
- 追问方向：阈值怎么定的 / 会不会过度拒答
- 红线：不要说"完全消除了幻觉"，只说降低了无依据生成。

### B. 状态机 / 幂等 / 恢复

**B1. 为什么不用 LangGraph？**
- 30 秒：节点本来按图节点形态设计，边由 Service 调用顺序显式表达，当前规模自研更可控、可观测性完全掌握；LangGraph 适合节点更多、分支更复杂的场景。
- 追问方向：迁移成本多大 / 多 Agent 协作怎么办
- 红线：不要说"我这就是 LangGraph 的思路"，也不要说"LangGraph 太复杂我用不来"。

**B2. checkpoint 能做什么、不能做什么？**
- 30 秒：能做——节点级轨迹、快照、刷新恢复证据、排障定位；不能做——任意代码位置续跑、任务租约、分布式调度、节点级补偿。恢复动作由服务层根据会话与答案状态执行。
- 追问方向：那进程重启后怎么恢复 / 为什么不做补偿
- 红线：不要承诺"从 checkpoint 重放"或分布式故障恢复。

**B3. 并发两个请求同时提交同一题？**
- 30 秒：幂等三层——前端复用同一 key（防重复点击）、服务端先查已有答案（友好返回）、数据库唯一约束 `uq_answer_idempotency`（并发最终防线）；冲突时回滚并返回既有快照。
- 追问方向：为什么不直接用 `ON CONFLICT` / 幂等键会过期吗
- 红线：不要说"完全无竞态"。可以承认未来可改成原生 upsert 减少异常路径。

### C. LLM 可靠性与降级

**C1. 没有模型 Key 怎么跑？**
- 30 秒：LLM 相关链路都有确定性降级——出题、评分、回答都能用规则或模板兜底，所以核心闭环可演示；但**效果不等同真实模型模式**。
- 追问方向：降级效果的量化 / 会不会掩盖问题
- 红线：绝不说"降级和真模型效果等价"。

**C2. 结构化输出失败怎么办？**
- 30 秒：网关做 JSON 提取与 Pydantic 校验，失败重试并按状态码分级；仍失败则抛错，由上层降级为确定性路径。`response_format` 不被支持时自动去掉重发。
- 追问方向：重试会不会放大成本 / 温度怎么设
- 红线：不承诺"模型输出稳定"。

**C3. 流式是怎么实现的？**
- 30 秒：**目前是伪流式**——先拿到完整内容再切分推送，首 token 延迟等于整段生成时间。真 SSE 是明确待办。
- 追问方向：为什么不做真流式 / 做了要改什么
- 红线：绝对不要说"我实现了真流式 SSE"。

### D. Agent 边界

**D1. 这个项目里的 Agent 在哪？**
- 30 秒：分两层讲——①受控 Agentic 工作流：显式节点、人机中断、checkpoint、幂等，关键状态流转由应用层控制；②只读 Shadow Agent 原型：三工具、三步预算、零业务写入，默认关闭。
- 追问方向：工具调用在哪 / 为什么不用 function calling
- 红线：不要说"实现了完整自主 Agent"。当前网关只支持结构化生成，**没有 tool-calling 能力**。

**D2. Shadow Agent 为什么关闭？**
- 30 秒：V1 动作准确率 69.44%、V2 完成率 41.67%，都没过预声明门槛；安全指标全过但"能安全调用工具"不等于"能稳定做对决策"。
- 追问方向：那 V2 的 100% 是什么意思
- 红线：必须主动澄清——那些 100% 是**确定性 fallback 导出的**，不是模型决策成功。

**D3. 什么时候才该上 LangGraph？**
- 30 秒：当节点数量和分支复杂度超过显式编排的可维护范围，或者需要运行时级的 checkpoint、子图、并行分支和人工中断恢复时。当前三题面试 + 固定流程不需要。
- 追问方向：多 Agent 状态流转怎么设计
- 红线：不要用"复杂就该用框架"这种话术，要能说出具体触发条件。

### E. 企业化差距

**E1. 多租户和权限怎么补？**
- 30 秒：数据模型已预留 `user_id`，画像已按知识库隔离；企业化需要行级安全或按库隔离、RBAC/ABAC、文档 ACL 和审计日志。
- 追问方向：现在能不能多人用 / 数据隔离做到什么程度
- 红线：不要说"现在支持多租户"，当前是单用户本机部署。

**E2. 复杂文档怎么补？**
- 30 秒：当前支持 Markdown/TXT/PDF/DOCX 的基础解析，**没有 OCR、版面分析和复杂表格重建**。补法是接版面分析模型、表格结构化、扫描件 OCR 与跨页上下文重建。
- 追问方向：表格和代码块现在怎么处理
- 红线：不要说"复杂文档已解决"。

**E3. 评测怎么规模化？**
- 30 秒：已有冻结的人工标注检索集与评分标注集、机器可读报告和门槛协议；短板是样本量（几十到几百条）和没有线上 A/B，所以我不给泛化准确率。
- 追问方向：怎么扩样本 / 怎么避免过拟合
- 红线：不要给一个"总体准确率"数字。

## 6. 附录 A · 评测治理的附属案例（DraftClaim / NLI）

> **不主动讲。** 只在面试官追问"你的评测设计到什么程度"时展开。它实验设计完整，但最终**没有进入生产默认路径**，投入产出比不适合作为主线。

**一句话讲法**

> 我尝试过把 Gate 从"词面支持"升级到 claim 级语义判断：让模型把答案和资料都抽成结构化 claim，再用 NLI 判断覆盖关系。Development 上确实做到了满分，但建了独立 holdout 之后 recall 只有 66.67%，低于预声明的 90%，所以我保留为 eval-only，而不是伪装成线上能力。

**过程数据（被追问设计时用）**

```text
人工 DraftClaim fixture：NLI accuracy 86.67%
初始 5 题 LLM extractor：schema 100%、必要声明召回 100%
扩展 15 题三轮：必要声明召回 81.82%～84.85%、claim 集稳定率 73.33%   ← 小样本满分不代表泛化
Boundary v2：必要声明召回 96.97%、claim 集稳定率 93.33%～100%
主语签名解析率：79.07%

Duplicate Development（22 组平衡对）：
  NLI baseline             P 77.78% / R 63.64% / F1 70.00%
  五类 typed features      P 84.62% / R 100.00% / F1 91.67%
  Typed features + entity veto  P 100% / R 100% / F1 100%

独立 Holdout（24 组，与 Development 无文本重叠，门槛 P≥95% / R≥90% / F1≥92%）：
  P 100.00% / R 66.67% / F1 80.00% / Entity FP 0  →  不通过
  该 holdout 已消耗，不得用于调参后重跑
```

> 来源：`docs/evaluations/evidence-gate-claim-evaluation-20260929.md` §2.2–§2.4

**这条案例真正的价值**：证明了评测工程能力 —— 严格数据隔离、单能力消融、冻结候选、一次性 holdout、以及**基于证据拒绝上线**。
