# AgentMentor V2 项目面试题与专家答辩

> 文档定位：用于项目走读后的模拟面试与答辩准备。  
> 回答口径：严格以当前 V2 源码为准，明确区分“已经实现”“当前取舍”和“后续演进”，不把规划包装成现状。  
> 项目定位：面向个人学习者的、可在 16GB 普通开发机通过 Docker Compose 运行的 RAG 面试训练系统。

---

## 1. 作为面试官，我对这个项目感兴趣的点

如果只看“上传文档后调用大模型问答”，这个项目并不稀缺。真正值得继续追问的是以下几点：

1. **它试图形成长期学习闭环**：资料入库、证据检索、模拟面试、可信评分、能力画像、复习任务和下一轮训练并非相互独立的演示页面。
2. **它没有把 LLM 输出直接当作事实**：回答需要证据，评分需要 Rubric，引用需要白名单校验，低置信结果有复核状态。
3. **它考虑了工作流可靠性**：面试并非一次请求，而是包含 checkpoint、幂等提交和恢复语义的多步状态流程。
4. **它正面处理了画像漂移问题**：采用“稳定主题 + 动态诊断子知识点”的两层模型，并通过可信评分渐进更新。
5. **它在低资源约束下做了明确取舍**：PostgreSQL 同时承担业务数据、全文检索和向量检索，Embedding 使用轻量开发实现，整体由三个容器编排。
6. **它包含真实的失败路径**：无 API Key、LLM 调用失败、证据不足、文档处理中断、重复提交等情况都有可解释的降级或恢复策略。
7. **它具备一定的工程验证意识**：除单元测试外，还使用真实 PostgreSQL/pgvector 验证关键闭环。
8. **它的局限也很适合考察候选人**：复杂文档、检索评测、工作流引擎、消息队列、多用户隔离等能力尚未全部产品化，候选人是否能准确描述边界，比堆砌名词更重要。

下面 13 组问题围绕这些兴趣点展开。每组包含一道主问题和 2～3 个递进追问。其中前 10 组聚焦当前项目，第 11～13 组考察企业级 RAG 的理解及本项目的企业化演进能力。

## 第 1 题：项目价值与边界——为什么不直接使用 Codex 或 ChatGPT？

### 面试官主问题

用户同样可以把学习资料交给 Codex 或 ChatGPT，然后要求它充当面试官。你这个项目与通用对话产品相比，真正不可替代的价值是什么？

### 追问

1. 如果去掉前端页面，你的系统还剩下哪些可复用的核心能力？
2. 你如何证明所谓“长期训练闭环”不是几张独立页面拼接出来的？
3. 这个项目当前最容易被质疑为 Demo 的地方是什么？

### Agent 专家回答

#### 对主问题的回答

通用对话产品擅长完成一次会话中的问答和角色扮演，但 AgentMentor 解决的是一个**可持续、可审计的个人训练过程**。

它的差异不在“模型能不能出题”，而在模型前后增加了确定性的工程约束：

- 学习资料被解析、切分和索引，问题和答案能够关联到具体证据；
- 面试题不仅包含题目，还包含本题参考答案和 Rubric；
- 用户回答经过四维评分、引用校验和置信路由；
- 可信结果会沉淀为稳定主题能力、动态诊断子知识点、错误模式和复习任务；
- 下一轮训练主题由画像中的训练焦点反哺；
- 关键过程写入数据库，可查看历史报告、趋势和工作流轨迹。

因此，通用对话产品强调“当前对话完成得好不好”，这个项目更强调“为什么这样出题、为什么这样评分、训练结果是否可信、下一轮为什么练这个，以及刷新或失败后能否继续”。

我不会把它描述成 Codex 的替代品。更准确的定位是：**把通用大模型包装为一个有领域数据、有状态、有评价规则、有长期记忆边界的训练应用**。

#### 对追问 1 的回答

去掉前端后，核心仍然是一个通过 API 暴露的学习训练后端，主要包括：

1. 文档摄入、解析、分块、Embedding 和索引；
2. 全文检索、向量检索、RRF 融合及引用校验；
3. 基于证据的 RAG 回答与证据不足降级；
4. 面试创建、出题、幂等答题、checkpoint 和状态推进；
5. 四维评分、报告生成、低置信路由；
6. 两层能力画像、复习任务和训练焦点推荐；
7. 历史报告、趋势和运行态检查。

这些能力由 Application Service 和领域规则承载，不依赖 React 页面才能成立。

#### 对追问 2 的回答

闭环是否真实，要看数据是否跨模块流动，而不是看页面是否相邻：

- `EvaluationService` 产生的评分结果是画像更新的输入；
- `ProfileService` 只消费符合规则的 Evaluation，并更新主题、子知识点和复习任务；
- `/profiles/me/training-focuses` 将待加强主题返回给前端；
- 前端把用户选中的训练焦点作为下一场面试的主题提交给 `InterviewService`；
- 新一轮结果继续进入评分和画像更新。

这里需要如实说明：当前“画像驱动出题”并不是 `InterviewService` 在后端直接读取完整画像后自主规划，而是由前端读取训练焦点、用户选择后把主题注入面试创建请求。这已经形成闭环，但自动化程度仍是可控的人机协作，而不是全自主 Agent。

#### 对追问 3 的回答

最容易被质疑的有三点：

- Embedding 当前是轻量特征哈希实现，不是生产级语义模型；
- 工作流虽然有显式节点和 checkpoint，但不是直接由 LangGraph 运行时调度；
- PDF/DOCX 已支持基础解析，但没有 OCR、版面理解和复杂表格重建。

我的答辩策略不是隐藏这些限制，而是解释它们与“16GB 本地可运行”约束之间的关系，并说明接口已经隔离：Embedding Gateway、LLM Gateway、Retriever 和工作流服务都可以逐步替换，而不需要推翻业务闭环。

## 第 2 题：RAG 可信性——系统如何避免“检索到了，但回答仍然胡说”？

### 面试官主问题

请完整说明一次 RAG 请求从 Query 到带引用答案的路径。除了“向量检索 + 大模型”，你做了哪些可信性控制？

### 追问

1. 为什么同时使用全文检索和向量检索？RRF 解决了什么问题？
2. 引用白名单能防住什么，不能防住什么？
3. 你如何判断证据不足？如果判断错了会发生什么？

### Agent 专家回答

#### 对主问题的回答

一次问答首先由 `AnswerService` 接收知识库、Query 等上下文，然后调用 Retriever 获取候选分块。Retriever 分别执行 PostgreSQL 全文检索和 pgvector 向量检索，再使用 Reciprocal Rank Fusion 合并排名。

检索结果进入回答生成前，系统会进行证据判断。证据充分时，LLM Gateway 使用检索片段构造上下文，生成回答和引用；生成后，应用层再次校验引用是否来自本次检索返回的 chunk 白名单。证据不足、模型不可用或输出不符合约束时，系统不会伪造“已被资料证明”的结论，而是返回明确的降级结果。

可信性控制主要有四层：

1. **召回层**：全文与向量双路召回，降低单一检索方式的盲区；
2. **融合层**：使用 RRF 基于排名融合，不直接比较不同检索器不可比的原始分数；
3. **生成层**：提示模型仅依据给定证据回答；
4. **应用层**：引用必须属于本次候选白名单，证据不足时显式降级。

#### 对追问 1 的回答

全文检索适合精确术语、类名、API 名称和代码标识符；向量检索更适合同义表达和语义接近的问题。技术学习资料中两种情况会同时出现，例如 `checkpoint` 这样的关键词适合全文召回，“如何恢复中断的工作流”则更依赖语义召回。

两类检索返回的分数尺度不同，直接加权需要做标定。RRF 只使用各列表中的名次，公式近似为：

`score(d) = Σ 1 / (k + rank_i(d))`

它实现简单、结果确定、对分值尺度不敏感，适合作为当前版本的稳健基线。它并不保证最优，因此企业化阶段仍需基于评测集调节候选数、权重或增加 reranker。

#### 对追问 2 的回答

引用白名单能防止模型返回一个数据库中不存在、或不属于本次检索结果的 chunk ID，也能避免把未召回的材料包装成本轮证据。

它不能证明以下事情：

- 被引用片段一定完整支持回答中的每个结论；
- 检索到的文档本身一定正确；
- 模型没有曲解片段；
- 召回集合没有漏掉更关键的证据。

所以白名单解决的是“引用来源合法性”，不是完整的事实一致性验证。进一步增强可以增加 claim-evidence 对齐、NLI 校验和人工标注的 RAG 评测集。

#### 对追问 3 的回答

当前证据判断依赖检索是否返回足够可用的候选及其相关性信号，是一个保守的工程规则，不是假装拥有绝对正确的事实判定器。

误判有两种：

- 把充分证据判为不足：系统会拒答或降级，召回率下降，但不会制造高置信错误；
- 把不足证据判为充分：模型可能基于薄弱上下文扩写，这是风险更高的一类。

因此当前设计偏向宁可少答，也不伪造引用。生产化时我会建立包含“可回答/不可回答”标签的数据集，分别统计检索 Recall、拒答准确率、引用正确率和 groundedness，而不是只看回答是否流畅。

## 第 3 题：复杂文档——你的“文档清洗”到底做到了什么程度？

### 面试官主问题

企业 RAG 经常面对扫描 PDF、复杂表格、多栏版式、页眉页脚和代码块。你当前的解析、清洗和分块策略是什么？请不要只说“支持 PDF 和 DOCX”。

### 追问

1. 为什么要保存 heading path、page 和 block type？
2. 你如何处理重复上传和重新索引，怎样避免引用失效？
3. 如果明天接入扫描版 PDF，你会在哪一层扩展？

### Agent 专家回答

#### 对主问题的回答

当前系统支持 Markdown、TXT、PDF 和 DOCX，但“支持”指的是可提取文本并进入基础 RAG 链路，不等同于企业级复杂版面理解。

当前处理过程是：

1. 根据文件类型选择解析器并提取正文；
2. 识别基础结构信息，例如标题层级、页码和块类型；
3. 以标题路径和长度约束进行分块；
4. 对内容生成稳定标识，用于去重或重建；
5. 生成 Embedding 并写入 PostgreSQL/pgvector；
6. 保存 chunk 与原文档的关系，供引用溯源。

代码块会尽量按连续内容保留，避免逐行切碎；Markdown 的标题结构会进入 heading path。当前没有 OCR、表格结构重建、多栏阅读顺序修复和图片理解，所以面对扫描件或复杂财报，我会明确说明需要增强解析层。

#### 对追问 1 的回答

这些元数据有三个作用：

- `heading path` 提供语义层级，使同一句话能够带上“它属于哪一章、哪一节”的上下文；
- `page` 让引用可回到原文位置，便于用户核验；
- `block type` 区分正文、标题、代码、表格和列表，后续可以采用不同切分、检索或展示策略。

当前数据库对部分结构元数据的持久化还不够完整，一些 block type 信息在检索阶段存在推断行为。这是我会如实指出的实现边界，也是后续 schema 演进的明确方向。

#### 对追问 2 的回答

重复上传和重新索引不能简单地“删掉所有 chunk 再插入”，因为评分报告或引用可能已经保存了 chunk ID。当前重新索引按 `chunk_index` 更新已有 chunk，尽量保留原 ID；增加的块再插入，多余块再按明确范围处理。

这样做的目标是降低重建索引对历史引用的破坏。它仍有边界：如果原文发生大规模重排，相同序号不再代表相同语义，仅靠位置稳定不够。更完整的方案是使用内容指纹和结构路径匹配，为引用增加文档版本，并保留历史版本的可追溯性。

#### 对追问 3 的回答

我会在文档解析边界扩展，而不是修改上层业务服务：

- 在 `rag/documents.py` 增加 OCR/Layout Parser 适配器；
- 输出统一的结构化 Document Block，包括文本、页码、坐标、块类型和置信度；
- `chunking.py` 继续消费统一结构，针对表格、标题和正文采用不同策略；
- 低 OCR 置信度的块可以标记为不适合高置信引用；
- 上层 `KnowledgeService`、Retriever 和 AnswerService 保持接口稳定。

这体现的是把“文件解析能力”与“学习训练业务”解耦，而不是在 Service 中堆文件类型分支。

## 第 4 题：Agent 与工作流——这真的是 Agent，还是普通 CRUD 加几次 LLM 调用？

### 面试官主问题

请说明这个项目中“Agent 工程化”的具体证据。为什么面试流程需要状态机、checkpoint 和幂等，而不是一个同步接口从出题跑到报告？

### 追问

1. 你是否真的使用了 LangGraph？如果没有，为什么文档中会出现工作流节点？
2. checkpoint 能恢复到什么程度，不能恢复什么？
3. `load_profile` 节点是否真的从数据库加载画像并自主规划面试？

### Agent 专家回答

#### 对主问题的回答

我对 Agent 的定义不是“调用过 LLM”，而是系统围绕一个目标，保存状态、执行多个有语义的步骤、根据结果推进，并允许外部输入中断流程。

本项目的面试流程具有这些特征：

- 创建会话后依次经历加载画像语义、规划、生成题目、等待回答、持久化回答、推进或完成；
- `waiting_for_answer` 是真实的人机中断点，不能由一次同步请求自动跨越；
- 每个关键节点写入 `WorkflowCheckpointModel`；
- 答案提交使用 `Idempotency-Key`，避免网络重试造成重复写入和重复推进；
- 面试完成后，评分与画像更新是后续步骤，而不是在用户答题请求中混成一个不可恢复的大事务。

因此它不是全自主 Agent，但已经具备“状态化、人机协作、可恢复、可观测”的 Agent 工作流骨架。

#### 对追问 1 的回答

当前没有把 LangGraph 作为运行时引擎。`workflows/interview.py` 定义了节点规格、状态转换和 checkpoint 语义，真正的编排中心仍是 `InterviewService`。

这是刻意的轻量取舍：流程规模有限，在 16GB 本地环境中先把状态、事务、幂等和恢复语义做实，再决定是否引入框架。面试中我不会说“系统基于 LangGraph 编排”，而会说“借鉴图工作流思想实现了显式节点和 checkpoint，并为以后迁移到 LangGraph 保留清晰边界”。

#### 对追问 2 的回答

checkpoint 当前能做到：

- 展示会话经过哪些节点；
- 保存关键状态快照；
- 页面刷新后根据服务端会话状态恢复当前题目和进度；
- 出现异常时定位流程停在哪一步。

它不能做到任意代码位置的自动续跑，也没有通用工作流引擎的任务租约、分布式调度、节点级自动重试和补偿机制。目前恢复动作仍由服务层根据数据库状态执行。

#### 对追问 3 的回答

当前 `load_profile` 节点主要表达工作流语义和写入 checkpoint，并不会在 `InterviewService` 中直接查询完整画像后自主规划。

真实的数据路径是：前端调用 `/profiles/me/training-focuses` 获取画像推荐，用户选择训练焦点，前端再把主题传入创建面试请求。也就是说，当前实现是“画像辅助、用户确认、主题驱动”，不是后端全自动画像规划。

这个回答很重要，因为它区分了流程图的概念语义与当前代码的执行事实。若后续增强，可以让 `load_profile` 真正加载摘要，并把选题原因以结构化字段持久化，但当前不能把它当作已实现能力。

## 第 5 题：可信评分——让同一个大模型出题又评分，如何避免“自说自话”？

### 面试官主问题

你的评分为什么值得用户相信？请说明 Rubric、总分计算、引用校验、置信度和复核状态分别承担什么责任。

### 追问

1. 为什么最终总分要由应用层重新计算，不能直接相信 LLM？
2. `final`、`review_pending`、`disputed` 如何影响后续画像？
3. 同一个模型既生成参考答案又参与评分，会有什么偏差？当前系统解决了多少？

### Agent 专家回答

#### 对主问题的回答

评分不是让模型自由输出一个 0～100 的数字，而是围绕每道题预先生成的 Rubric，从四个维度评估：

- correctness：核心事实和结论是否正确；
- completeness：关键点是否覆盖；
- reasoning：推理和因果是否成立；
- communication：表达是否清晰、结构是否适合面试。

LLM 返回维度分、理由、缺失点和置信度后，应用层重新计算最终分，校验引用是否属于本题允许的证据集合，并根据差异和置信度把结果路由到 `final`、`review_pending` 或 `disputed`。

可信性来自“模型提出判断，确定性代码约束结果”，而不是来自假设模型永远正确。

#### 对追问 1 的回答

应用层重算总分有三点价值：

1. 防止模型返回的总分与维度分之和不一致；
2. 固定评分规则，避免提示词版本变化造成总分口径漂移；
3. 便于测试边界条件，使最终业务数据由确定性逻辑产生。

同理，引用白名单、状态路由和画像更新权重也属于应用或领域层规则，不交给模型随意决定。

#### 对追问 2 的回答

画像更新使用 `profile_update_decision`：

- `disputed` 和 `review_pending` 不更新画像，避免未确认结果污染长期记忆；
- 高置信 `final` 按完整权重更新；
- 低置信但仍为 `final` 的结果按较低权重渐进更新。

因此评分状态不是展示标签，而是控制下游副作用的业务门禁。复习任务的验证也要求可信结果，不能通过一次低置信高分直接结题。

#### 对追问 3 的回答

同源模型会带来几个偏差：

- 参考答案可能限定了评分视角，忽略其他正确解法；
- 模型倾向维护自己生成的 Rubric；
- 相似提示词可能导致一致但错误的判断；
- 对表达风格的偏好可能被误当成技术能力。

当前系统通过结构化 Rubric、应用层重算、引用白名单、置信路由和可选复核降低风险，但没有彻底解决“同源评审偏差”。更严格的生产方案可以使用不同模型或不同提示策略做独立 Reviewer，并用人工标注答案校准维度分。当前的准确表述是“可信性增强”，而不是“评分绝对客观”。

## 第 6 题：能力画像——为什么高分之后画像没有立刻变成高分？

### 面试官主问题

请解释 V2 的“稳定主题 + 动态子知识点”两层画像。为什么画像分不等于最近一次面试分？

### 追问

1. 如何避免大模型每次使用不同措辞，产生几十个重复知识点？
2. 历史数据如何迁移到新画像，怎样保证重复迁移不重复累计？
3. 复习任务为什么需要连续两次高分才能完成？

### Agent 专家回答

#### 对主问题的回答

旧模型容易把每道题的文字直接当作画像节点，最终产生大量细碎、重复且无法比较的知识点。V2 将画像拆为两层：

- **稳定主题层**：例如 RAG、LangGraph、Java 后端工程，适合长期观察和趋势展示；
- **动态诊断子知识点层**：例如“RAG 检索增强生成”“状态建模与工作流控制”，用于解释具体薄弱点和保存证据。

画像分是多次可信结果的渐进估计，而不是最近一次得分的百分比映射。更新会考虑历史掌握度、题目难度、评分置信度和 Evaluation 状态。这样可以避免一次高分让长期薄弱项瞬间满分，也避免一次偶然低分把稳定能力完全推翻。

#### 对追问 1 的回答

系统使用 `profile_taxonomy` 将自由文本知识点规范化到稳定主题和 canonical subtopic。规范化时会处理别名和已知模式，再把原始题目细节作为诊断证据保留，而不是把每个句子都创建为新的主画像节点。

换句话说，“节点用于统计，证据用于解释”。这也是两层模型的核心：既保持画像稳定，又不丢失模型发现的细粒度问题。

#### 对追问 2 的回答

历史回填由 `ProfileService.backfill_two_layer_profiles` 执行。它读取旧画像、错误和复习任务，映射到新的主题/子主题结构，同时写入 `ProfileUpdateEvent` 作为版本标记。

回填必须幂等：检测到同一用户已经完成 `hierarchy_version=2` 的迁移后，不会再次累计。迁移保留旧记录，而不是破坏性删除，便于比较和回退。

#### 对追问 3 的回答

一次高分可能来自参考答案演示、题目恰好熟悉或评分波动，不能证明知识已经稳定掌握。当前规则要求可信度达到阈值且分数达到标准，并连续两次通过：

- 第一次通过：增加 `verification_streak`，降低任务紧迫度但不直接完成；
- 第二次连续通过：将任务标记为完成；
- 中间出现不达标结果：连续计数重置。

这相当于一个轻量的抗偶然机制，也更符合间隔复习中“重复成功才能确认掌握”的思想。

## 第 7 题：画像驱动出题——系统为什么总在问相似的问题？

### 面试官主问题

你声称画像会反哺下一轮训练。请准确说明当前选题路径，以及系统如何兼顾知识库内容、用户薄弱项、难度和题目去重。

### 追问

1. “为什么出这道题”是否作为结构化数据持久化了？
2. 当前去重是只针对本轮，还是跨历史面试？
3. 新用户没有画像时如何冷启动？

### Agent 专家回答

#### 对主问题的回答

当前链路分为两步：

1. `ProfileService` 根据主题掌握度、错误模式和待完成复习任务生成 training focuses；
2. 前端展示训练焦点，用户选择后，将 topic、difficulty 等参数传给面试创建接口；`InterviewService` 再结合知识库检索片段生成题目、参考答案和 Rubric。

这使选题同时受到“用户需要练什么”和“知识库实际有什么证据”的约束。画像决定优先方向，检索片段限定题目内容，难度控制问题深度。

同一场面试内，服务会把已生成问题作为上下文，要求模型避免重复；失败时还有确定性的回退题目。但当前并没有跨所有历史面试建立语义去重索引，因此只能说实现了本轮去重和基础历史主题规避，不能宣称彻底消除相似题。

#### 对追问 1 的回答

目前训练焦点的推荐原因会在前端展示，但 `why_this_question` 还没有作为每道题的独立结构化字段持久化。

因此现在可以解释“为什么选择这个训练主题”，但对单题级别的完整因果审计还不够。若面试官追问，我会把它列为明确改进点：保存 `focus_id`、画像快照版本、命中的错误模式、检索证据和选题策略版本，使每道题都能回放生成依据。

#### 对追问 2 的回答

当前主要是同一轮内去重：生成下一题时带入本轮已有题目。跨轮历史会通过训练焦点和近期报告间接影响选题，但没有使用 Embedding 对所有历史题目做相似度过滤。

如果要最小成本增强，可以在出题前召回该用户同主题的历史问题，对候选题进行语义相似度检查；超过阈值时要求模型换考察角度，而不是简单换措辞。

#### 对追问 3 的回答

冷启动时没有可靠画像，系统应以知识库中的主要主题和用户选择为主，使用中等难度、覆盖定义—流程—风险—工程实践的基础题建立初始样本。

完成第一轮后，可信评分开始建立主题掌握度和错误模式，再逐步提高画像权重。也就是说，冷启动阶段强调覆盖面，数据积累后强调个性化，不能在没有证据时伪造精准画像。

## 第 8 题：一致性与故障恢复——处理中断、重复点击和重建索引会怎样？

### 面试官主问题

请从真实故障出发说明系统的一致性设计：用户重复提交答案、文档处理到一半服务重启、报告重复生成、文档重新索引，这四种情况分别如何处理？

### 追问

1. 为什么当前使用 FastAPI BackgroundTasks，而不是消息队列？
2. 幂等键的作用域是什么？数据库是否有最终约束？
3. 哪些流程具备真正的恢复，哪些只是“检测到异常后标记失败”？

### Agent 专家回答

#### 对主问题的回答

四种情况分别采用不同策略：

- **重复提交答案**：API 要求 `Idempotency-Key`，数据库按题目和幂等键约束；同一提交重试返回已有结果，不重复写答案或推进题目。
- **文档处理中断**：启动时识别遗留的 `pending/processing` 文档，避免它们永久卡在“处理中”；根据当前策略转为可解释的失败状态或重新处理入口。
- **报告重复生成**：报告使用稳定关系进行创建或更新，在事务内完成，不采用“先删除旧报告再重建”这种容易留下空窗的做法。
- **重新索引**：优先按 chunk 顺序更新已有记录并保留 ID，降低历史引用失效风险。

这里的关键是：幂等、恢复、重建并不是一个统一开关，而是针对每类副作用设计稳定键、事务边界和恢复语义。

#### 对追问 1 的回答

当前约束是单机、个人用户、三个容器和有限并发，BackgroundTasks 足以避免上传请求长时间阻塞，复杂度也较低。

它的不足是任务没有独立 broker、租约和可靠重试，API 进程崩溃时任务本身不会像队列消费者那样自动恢复。因此项目通过启动扫描处理遗留状态，但这不等同于可靠消息队列。

当业务进入多实例、大文件或高并发后，我会把“文档处理任务”抽象为持久化 Job，引入队列，并以文档版本和处理阶段作为幂等依据。当前不引入是资源与复杂度取舍，不是认为队列没有价值。

#### 对追问 2 的回答

幂等键由客户端针对“某场面试的某道题”生成并通过 Header 提交。服务端查询已有记录，数据库还通过唯一约束提供最终防线，避免两个并发请求都越过应用层检查。

只靠前端禁用按钮不能解决网络重试和并发；只靠应用查询也可能有竞态。因此幂等设计必须同时包含稳定业务键和数据库约束。

#### 对追问 3 的回答

答案提交和报告生成具有较明确的幂等与事务语义；面试 checkpoint 支持按持久化状态恢复页面和流程位置。

文档 BackgroundTasks 的当前能力更接近“中断检测 + 状态纠正”，并不是从任意解析步骤自动续跑。重新索引也强调引用稳定，但对文档大幅重排没有完整版本化保障。

我会在面试中明确区分：

- 可重试且不会重复产生副作用；
- 可根据 checkpoint 恢复业务状态；
- 只能检测异常并转成可处理状态；
- 尚需队列和任务状态机才能做到的分布式恢复。

## 第 9 题：16GB 资源约束——你的架构取舍是设计，还是能力不足的借口？

### 面试官主问题

为什么选择 PostgreSQL + pgvector、轻量 Embedding 和 Docker Compose 三容器？这些选择带来了哪些收益与代价？

### 追问

1. 当前 Embedding 到底是什么？它能否支撑中文语义检索？
2. 为什么不直接使用 Elasticsearch、Milvus、Redis、Kafka 和工作流平台？
3. 如果数据量从个人资料增长到企业百万级 chunk，你先改哪里？

### Agent 专家回答

#### 对主问题的回答

项目有一个明确非功能约束：在 16GB 普通开发机上可完整运行。因此架构优先控制常驻进程数和运维成本：

- PostgreSQL 保存业务数据；
- pgvector 在同一数据库内提供向量检索；
- PostgreSQL 全文检索承担关键词召回；
- API 容器承载业务服务和网关；
- 前端容器提供 React 工作台；
- 外部 LLM 通过 OpenAI-compatible HTTP Gateway 接入。

收益是部署简单、事务一致性清晰、本地可复现，适合个人项目展示完整闭环。代价是检索与业务数据库共享资源，横向扩展能力有限，轻量 Embedding 的语义质量也不等同于生产模型。

#### 对追问 1 的回答

当前 `DevelopmentEmbeddingGateway` 是特征哈希基线：对字符 n-gram 和英文词等特征做哈希映射，再进行 L2 归一化，默认输出 1536 维向量。它无需加载本地神经网络，资源稳定，测试可确定。

它能捕获部分字面和局部模式相似性，对技术术语有一定效果，但不能声称具备强中文语义理解。项目通过全文检索和 RRF 对其进行补充。

生产化时可以保持 Gateway 接口不变，替换为 BGE、云 Embedding 或其他中文语义模型，并对旧向量做版本化重建。当前实现的价值是工程链路真实可运行，不是检索质量已经达到企业最优。

#### 对追问 2 的回答

这些组件各有价值，但一起引入会让个人项目把主要精力消耗在基础设施运维上，而且无法证明业务闭环更好。

当前阶段的原则是“一个组件解决多个足够规模的问题”：

- PostgreSQL 同时覆盖事务、全文和向量；
- BackgroundTasks 覆盖低并发异步处理；
- 显式服务编排覆盖有限状态流程。

当指标证明瓶颈存在时再拆分：检索吞吐和召回需求推动专用检索引擎，任务可靠性推动消息队列，复杂分支和长任务推动工作流平台。避免为了简历关键词进行无依据的微服务化。

#### 对追问 3 的回答

我会先用指标确认瓶颈，但通常优先处理：

1. 将文档处理从 API 进程拆为可靠任务消费者；
2. 换成生产 Embedding，并引入向量版本；
3. 对检索做离线评测，增加 reranker；
4. 为 chunk 和向量建立分区、批量写入及合适索引；
5. 根据 PostgreSQL CPU、IO 和查询延迟，再决定是否拆专用向量/全文检索；
6. 增加租户隔离、配额和对象存储。

我不会从“百万级”直接推导出必须使用某个中间件，而会用数据规模、查询模式、SLA 和团队运维能力共同决策。

## 第 10 题：测试、可观测性与生产就绪度——你怎么证明它真的能跑？

### 面试官主问题

这个项目开发周期很短。你如何证明它不是“在你电脑上点过一次”的原型？请给出测试策略、运行态观测和发布前验收证据。

测试的重点不是追求一个漂亮的覆盖率数字，而是覆盖最可能破坏核心卖点的边界：引用可信、幂等、报告一致性、画像不被低可信评分污染，以及服务重启后的状态。

- 唯一约束、事务和 upsert 行为；
- 迁移后的 schema 兼容；

- LLM 输出结构解析；

Fake 保证测试确定和快速，真实集成测试防止“模拟对象通过、数据库语法或扩展实际失败”。

#### 对追问 2 的回答

系统把 LLM 封装在 Gateway 后面。无 Key 或调用失败时，使用确定性回退，保证开发者仍能走通知识库、工作流、评分结构和画像链路。

降级确实可能掩盖问题，所以必须可观测：

- 健康接口区分真实 LLM 和 fallback；
- 前端运行态显示当前模型模式；
- 日志与指标记录 fallback 原因和次数；
- Demo Readiness 不应把“链路可演示”误报为“真实模型质量已验证”。

回退的目的不是假装模型成功，而是隔离外部依赖，让工程闭环可测试，同时把能力降级明确暴露给用户。

#### 对追问 3 的回答

当前离生产最远的三个部分是：

1. **复杂文档理解**：缺少 OCR、版面分析、复杂表格与图像处理；
2. **检索与评分评测体系**：已有规则与测试，但缺少规模化人工标注集、Recall/NDCG、groundedness 和评分一致性基准；
3. **多租户与可靠异步基础设施**：当前定位是本机默认用户，尚未实现企业级认证授权、租户数据隔离、对象存储、消息队列和分布式任务恢复。

另外，Embedding 是开发基线、工作流不是通用引擎，也属于明确限制。我的项目陈述会聚焦：我完成了一个资源受控、真实可运行、可解释的个人学习闭环，并能准确说明扩展到企业级需要补哪些证据和基础设施。

## 第 11 题：企业级 RAG——真正落地的难点到底是什么？

### 面试官主问题

你的项目目前是个人学习场景，并不是企业级 RAG。假设让你参与企业知识库建设，你认为企业级 RAG 最难的部分是什么？请不要只回答“提高检索准确率”。

### 追问

1. 企业中的复杂文档、权限和知识时效性分别会带来什么问题？
2. 为什么在 Demo 中表现不错的 RAG，上线后经常效果下降？
3. 这些问题应该按照什么顺序解决？

### Agent 专家回答

#### 对主问题的回答

企业级 RAG 的难点不是某一个向量数据库或模型选型，而是要同时解决**数据、检索、生成、权限、评测和运营**六类问题，并让它们在长期运行中保持一致。

我会把主要难点归纳为以下几类：

1. **数据质量与复杂文档**
   - 扫描 PDF、复杂表格、多栏排版、图片、公式和代码无法仅靠普通文本提取正确还原；
   - 页眉页脚、目录、重复版本和模板噪声会污染索引；
   - 文档之间可能互相冲突，系统需要知道哪个版本更可信。

2. **切分与语义完整性**
   - 固定长度切分容易切断定义、表格和上下文；
   - 分块过小会缺少语义，过大会降低召回精度并增加 Token 成本；
   - 不同文档类型需要不同的切分策略，不能使用一套参数处理所有资料。

3. **检索准确率与知识边界**
   - 关键词、缩写、产品代号和内部术语会造成 Query 与文档表达不一致；
   - 只使用向量检索容易漏掉精确编号和专有名词，只使用全文检索又难以处理语义改写；
   - “检索到相似内容”不等于“检索到足以回答问题的证据”。

4. **权限与数据隔离**
   - 用户可以搜索到什么，必须与企业原有 ACL、组织、项目和文档密级一致；
   - 权限过滤不能只在生成答案后处理，必须在召回阶段生效；
   - 引用、缓存、日志和历史对话也可能泄露敏感数据。

5. **知识更新与版本治理**
   - 企业知识持续变化，需要处理新增、修改、撤回、过期和冲突；
   - 索引、引用和历史回答必须能够追踪到文档版本；
   - 删除原文后，向量、缓存和派生数据也必须同步失效。

6. **可量化评测**
   - “回答看起来不错”不是验收标准；
   - 需要分别测量解析质量、召回率、排序质量、引用正确率、事实一致性、拒答能力、延迟和成本；
   - 没有真实业务问题和人工标注集，就无法判断优化是否有效。

7. **稳定性与成本**
   - 大文件处理、Embedding、rerank 和 LLM 调用都是异步、耗时且可能失败的任务；
   - 必须考虑限流、重试、幂等、降级、缓存、熔断和成本预算；
   - 模型或提示词升级后，还要防止效果无声回退。

因此，企业级 RAG 的核心不是“接入更强的模型”，而是构建一套**有权限、有版本、有评测、有监控、有反馈闭环的知识服务系统**。

#### 对追问 1 的回答

三个问题分别作用在不同层：

- **复杂文档**影响知识能否被正确提取。若解析阶段把表格行列关系打乱，后面的 Embedding 和 LLM 再强也无法恢复原始事实；
- **权限**影响系统能否安全使用。若先召回无权文档再让模型过滤，敏感内容已经进入上下文、缓存或日志，属于越权；
- **知识时效性**影响答案是否仍然有效。系统需要保存文档版本、生效时间、失效时间、来源和权威等级，在召回时优先使用有效版本。

解决方案也必须分层：

- 解析层引入 OCR、Layout Model、表格结构化和质量置信度；
- 索引层保存租户、ACL、文档版本、有效期和数据血缘；
- 检索层先做权限过滤，再做全文/向量召回和 rerank；
- 生成层携带版本化引用，并在证据冲突时显式说明；
- 生命周期层通过事件或 CDC 触发增量索引、撤回和缓存失效。

#### 对追问 2 的回答

Demo 的问题通常经过人工挑选，文档数量少、权限单一、表达规范，而且开发者知道“应该问什么”。上线后会出现：

- 用户问题含糊、带错别字或内部缩写；
- 知识库规模扩大，相似但错误的文档变多；
- 同一制度存在多个冲突版本；
- 权限过滤减少了可召回候选；
- 问题超出知识边界，但用户仍期待确定答案；
- 模型、网络和依赖服务存在延迟及失败；
- 真实用户更关心引用是否能核验，而不是回答是否流畅。

因此效果下降往往不是单点算法退化，而是数据分布、权限约束和真实 Query 分布发生了变化。解决它需要采集匿名化失败样本，建立分场景评测集，并把解析、召回、排序和生成分别观测，不能只调整 Prompt。

#### 对追问 3 的回答

我会按以下顺序推进：

1. 明确业务场景、用户、数据边界和成功指标；
2. 完成权限模型、数据分级和审计要求；
3. 建立文档摄入、版本、删除和质量治理；
4. 建立最小可用的离线评测集；
5. 优化解析、混合检索和 rerank；
6. 增加引用、拒答、冲突检测和答案校验；
7. 建设异步任务、监控、告警、成本和容量治理；
8. 小流量试运行，利用真实失败样本持续评测。

原因是：没有安全边界和评测标准时，过早优化模型参数既无法证明价值，也可能制造合规风险。

## 第 12 题：项目企业化——AgentMentor 如果真正落地，需要做哪些改造？

### 面试官主问题

假设公司认可当前学习训练闭环，希望把它扩展成企业内部的技术人才培养平台。你会如何从当前版本演进，而不是推倒重来？

### 追问

1. 哪些当前设计可以保留，哪些必须重构？
2. 你会如何划分阶段，避免一次性“大改造”导致项目失控？
3. 企业化过程中最大的技术风险是什么？

### Agent 专家回答

#### 对主问题的回答

我不会先做微服务拆分，而会围绕企业落地必须满足的能力逐步演进。当前项目已经具备知识摄入、检索、面试、评分、画像和复习闭环，可以保留业务骨架；企业化工作的重点是补齐身份权限、可靠异步、数据治理、质量评测和运营能力。

我会分为五个阶段。

##### 阶段一：身份、租户与权限基线

需要完成：

- 接入企业 SSO/OIDC；
- 引入 tenant、organization、user、role 等实体；
- 为知识库、文档、面试、报告和画像增加租户归属；
- 实现 RBAC，并在需要时补充基于部门、项目、密级的 ABAC；
- 检索 SQL 必须在全文与向量召回前加入权限过滤；
- 增加审计日志，记录谁在何时访问了哪些知识和报告。

验收标准不只是“页面无法打开”，而是通过跨租户越权测试证明：用户无法通过 API、引用 ID、缓存或检索结果访问无权数据。

##### 阶段二：企业数据接入与文档治理

需要完成：

- 接入对象存储和企业内容源，如 Wiki、网盘、代码仓库或工单系统；
- 建立 Connector 接口、增量同步、重试和限流；
- 引入文档版本、来源、责任人、有效期、密级和权威等级；
- 增加 OCR、版面分析、表格与图片解析；
- 建立去重、冲突、过期和删除传播机制；
- 为每次解析和索引保存版本及质量报告。

此阶段的关键验收是：一份文档更新或撤回后，检索结果、引用和缓存能在规定时间内同步变化。

##### 阶段三：检索与回答质量工程

需要完成：

- 替换生产级中文或多语言 Embedding；
- 建立向量版本，支持灰度重建；
- 增加 Query Rewrite、术语词典和 metadata filter；
- 使用 hybrid retrieval + reranker；
- 增加 claim-evidence 对齐、冲突检测和严格拒答；
- 构建按业务领域划分的评测集。

验收不能只看人工体验，应包含 Recall@K、MRR/NDCG、引用正确率、groundedness、不可回答问题拒答率、P95 延迟和单次成本。

##### 阶段四：可靠工作流与规模化运行

需要完成：

- 把 BackgroundTasks 替换为持久化队列和 Worker；
- 为解析、Embedding、索引、报告和画像更新建立任务状态机；
- 增加任务租约、超时、重试、死信队列和人工补偿入口；
- 将当前 checkpoint 演进为可重放的工作流状态；
- 增加限流、熔断、缓存、资源配额和容量监控；
- 依据实际瓶颈决定是否拆分检索服务或专用向量库。

关键验收是故障注入：Worker 重启、LLM 超时、数据库短暂不可用和重复消息均不能产生重复副作用或不可恢复状态。

##### 阶段五：企业学习与治理闭环

需要完成：

- 将个人训练主题映射到岗位、职级和技能矩阵；
- 支持课程、题库、人工教练和团队训练计划；
- 评分模型使用校准集，并允许人工申诉与复核；
- 画像更新保留证据和版本，可解释每一次变化；
- 为管理者提供聚合趋势，但限制查看个人敏感内容；
- 建立模型、Prompt、Rubric 和策略版本管理。

最终产品的价值不只是“AI 面试”，而是形成可追溯的组织能力培养系统。

#### 对追问 1 的回答

可以保留的设计：

- API、Application Service、Domain、Infrastructure 的分层；
- `KnowledgeService` 到 `ProfileService` 的业务闭环；
- LLM Gateway、Embedding Gateway、Retriever 等可替换边界；
- Rubric、引用白名单、置信状态和画像更新门禁；
- checkpoint、幂等键和稳定报告关系的设计思想；
- PostgreSQL 作为事务主库。

必须增强或重构的部分：

- 默认本机用户必须替换为真实身份和租户上下文；
- 所有核心表补充租户、权限和版本维度；
- `DevelopmentEmbeddingGateway` 替换为生产模型；
- BackgroundTasks 替换为可靠任务基础设施；
- 文档解析升级为可插拔、多模态并带质量报告的 Pipeline；
- 当前 Service 编排需要在流程复杂后迁移到可靠工作流运行时；
- 建立独立评测和观测体系。

这里不是推翻业务模型，而是把“单机假设”逐项替换成“企业运行假设”。

#### 对追问 2 的回答

我会采用“每一阶段都可上线、可验收”的演进方式：

1. 先给现有表和 API 增加租户上下文，并保持单租户兼容；
2. 再将文档处理抽成 Job，但保留原同步入口作为适配层；
3. 新旧 Embedding 使用版本字段并行构建，完成评测后切换；
4. 新 Retriever 在同一接口后灰度运行，记录影子结果；
5. 工作流引擎先接管耗时节点，不一次迁移所有业务；
6. 每次迁移都有数据回填、双写或回退策略。

这样能避免“所有组件一起替换，但出了问题无法定位”的风险。

#### 对追问 3 的回答

最大的风险不是单纯性能，而是**长期数据一致性和权限一致性**：

- 文档更新了，旧向量是否失效；
- 用户权限撤销了，缓存和引用是否仍可访问；
- 模型或 Rubric 更新后，历史分数是否还能比较；
- 同一任务重试时，会不会生成重复画像事件；
- 数据删除后，派生报告和日志是否符合保留策略。

解决方法是：

- 所有派生数据携带 source/version/tenant；
- 使用 Outbox 或事件表保证业务事务与异步事件一致；
- 消费端用业务幂等键；
- 对模型、Prompt、Embedding、Rubric 和画像算法进行版本化；
- 对权限撤销和数据删除建立传播任务及审计；
- 为关键链路增加 reconciliation 对账任务，而不是只依赖实时消息永不丢失。

### 企业化演进后的建议架构

```text

        │
SSO / API Gateway / 租户与权限
        │
AgentMentor 应用服务
        ├── 知识与连接器服务
        ├── RAG 检索与回答服务
        ├── 面试工作流服务
        ├── 评分与复核服务
        └── 画像与训练计划服务
        │
可靠任务队列 / 工作流运行时
        │
解析 Worker / Embedding Worker / 索引 Worker / 评测 Worker
        │
PostgreSQL + 对象存储 + 检索索引 + 缓存
        │
LLM / Embedding / Reranker / OCR 与版面模型
        │
评测平台 / 可观测平台 / 审计与成本治理
```

这是一条目标路线，不是当前项目已经部署的架构。

## 第 13 题：企业落地治理——如何证明安全、效果和投入产出？

### 面试官主问题

企业同意开发不代表同意上线。你如何向安全团队、业务负责人和运维团队分别证明这个系统可以落地？

### 追问

1. 企业 RAG 应建立哪些核心指标？
2. 如何防止 Prompt Injection、敏感信息泄露和知识库投毒？
3. 上线后效果下降，你如何定位是解析、检索、模型还是用户问题？

### Agent 专家回答

#### 对主问题的回答

三个角色关注的证据不同：

- **安全团队**关注身份、最小权限、数据流向、敏感信息、审计、供应商和删除能力；
- **业务负责人**关注任务成功率、员工节省时间、训练效果、答案可信度和错误风险；
- **运维团队**关注容量、延迟、失败率、重试、依赖可用性、成本和恢复时间。

因此上线材料至少需要包含：

1. 数据流和威胁模型；
2. 租户与文档权限模型；
3. 模型供应商和数据保留说明；
4. 离线评测报告及已知边界；
5. 小流量试点结果；
6. SLI/SLO、容量和成本预算；
7. 降级、回滚、数据删除和事故响应方案；
8. 人工复核与用户申诉流程。

#### 对追问 1 的回答

指标应分层，避免只看一个“回答准确率”：

| 层级 | 关键指标 |
|---|---|
| 数据摄入 | 解析成功率、OCR 置信度、重复率、索引延迟、过期文档数 |
| 检索 | Recall@K、MRR/NDCG、权限过滤正确率、零召回率 |
| 回答 | groundedness、引用正确率、完整性、拒答准确率、冲突检出率 |
| 评分 | 与人工评分相关性、维度偏差、复核率、争议率 |
| 系统 | P50/P95/P99 延迟、可用性、任务积压、错误率、恢复时间 |
| 成本 | 每次问答/面试成本、每千文档索引成本、缓存命中率 |
| 业务 | 问题解决率、用户采纳率、训练完成率、能力提升趋势 |
| 安全 | 越权拦截、敏感信息事件、审计覆盖率、删除传播时延 |

指标还要按租户、知识域、文档类型、模型版本和 Query 类型分组，否则总体平均值会掩盖局部故障。

#### 对追问 2 的回答

需要采用纵深防御：

1. **输入侧**
   - 对上传来源做身份校验、病毒扫描、类型和大小限制；
   - 将文档内容视为不可信数据，而不是系统指令；
   - 对外部连接器设置来源白名单和内容审批。

2. **检索侧**
   - 在数据库查询阶段执行租户和 ACL 过滤；
   - 对敏感字段进行分类、脱敏或禁止进入索引；
   - 为高风险知识设置额外审批和更短缓存周期。

3. **Prompt 与工具侧**
   - 将系统指令、用户输入和检索内容明确分隔；
   - 禁止文档片段改变系统权限或工具策略；
   - 工具调用使用最小权限、参数校验和 allowlist；
   - 对高风险动作要求人工确认。

4. **输出侧**
   - 校验引用、检测敏感信息和越权内容；
   - 高风险领域使用严格拒答或人工复核；
   - 不在日志中记录完整敏感 Prompt 和原文。

5. **运营侧**
   - 建立红队用例，包括间接 Prompt Injection、越权查询和数据外带；
   - 监控异常 Query、批量枚举和高频失败；
   - 对模型、Prompt 和安全策略版本进行审计。

Prompt Injection 不能只靠一句“忽略文档中的指令”解决，关键是模型即使受到诱导，也没有越权的数据和工具能力。

#### 对追问 3 的回答

必须让一次请求携带可关联的 trace，并记录每一阶段的结构化信息：

- 原始 Query 与规范化 Query；
- 解析器版本、文档版本和 chunk 元数据；
- 全文、向量、融合及 rerank 的候选和分数；
- 权限过滤前后的数量，但不能泄露无权内容；
- 最终进入 Prompt 的证据；
- 模型、Prompt、参数和输出状态；
- 引用校验、拒答和 fallback 原因；
- 用户反馈及人工复核结果。

定位顺序可以是：

1. 原文是否存在且版本有效；
2. 解析结果是否保留了正确内容；
3. 正确 chunk 是否被召回；
4. 是否在融合、rerank 或权限过滤中丢失；
5. 正确证据是否进入模型上下文；
6. 模型是否错误理解或生成；
7. 用户问题是否本身含糊或超出知识边界。

这要求观测系统能把“回答失败”拆成摄入、召回、排序、生成和策略失败。只有这样，团队才知道应该修解析器、调检索、改 Prompt，还是补知识。

### 当前项目可以延续的治理基础

但企业化仍需补充 OpenTelemetry Trace、统一指标平台、安全审计、租户维度、成本归因和完整评测平台。

## 2. 面试答辩时的统一口径

### 2.1 可以明确说“已实现”的能力

- Markdown/TXT/PDF/DOCX 基础解析、结构化切分、向量化和入库；
- PostgreSQL 全文检索、pgvector 向量检索和 RRF 融合；
- 基于证据的 RAG 回答、引用白名单和证据不足降级；
- 面试题、参考答案、Rubric 的生成；
- 面试 checkpoint、答题幂等和页面恢复；
- 四维评分、应用层总分重算、低置信状态路由；
- 稳定主题 + 动态诊断子知识点的两层画像；
- 可信评分渐进更新与连续两次验证完成复习任务；
- 报告历史、多轮趋势、训练焦点和多知识库切换；
- Docker Compose 三容器部署及 16GB 本地开发约束。

### 2.2 必须带边界说明的能力

| 能力 | 准确口径 |
|---|---|
| Agent 工作流 | 有显式状态节点、checkpoint、人机中断和恢复语义；当前由 Service 编排，不是 LangGraph 运行时 |
| 画像驱动出题 | 画像生成训练焦点，前端由用户选择并注入面试主题；后端尚未完全自主读取画像规划 |
| 语义检索 | 已有 pgvector 链路；当前 Embedding 是轻量特征哈希基线，不是生产神经 Embedding |
| 复杂文档 | 支持四类文档的基础解析；尚无 OCR、版面模型和复杂表格重建 |
| 题目去重 | 支持本轮已有问题规避；尚无完整跨轮语义去重索引 |
| 题目可解释性 | 可解释训练主题来源；单题 `why_this_question` 尚未完整结构化持久化 |
| 故障恢复 | 关键业务具备幂等/checkpoint；BackgroundTasks 尚不等于可靠消息队列 |
| 可信评分 | 有 Rubric、白名单和置信路由；不能宣称完全消除 LLM 自评偏差 |

### 2.3 不建议在面试中使用的表述

- “系统完全杜绝了大模型幻觉。”
- “系统基于 LangGraph 实现了完整的自主 Agent。”
- “支持所有复杂 PDF 和企业文档。”
- “画像能准确代表用户真实能力。”
- “向量检索已经达到生产级语义效果。”
- “具备分布式故障恢复。”
- “评分完全客观。”

更好的表达方式是：

> 我没有把 LLM 输出直接当作可信结果，而是在召回、引用、评分、状态路由和画像副作用之间增加了确定性约束。当前版本在 16GB 本地环境中跑通了完整闭环，同时保留了对生产 Embedding、复杂解析器、可靠任务队列和工作流引擎的替换边界。

## 4. 一分钟项目总结参考

> AgentMentor 是我为 Java 后端转向 AI Agent 开发设计的个人学习训练系统。它将学习资料解析并写入 PostgreSQL/pgvector，通过全文与向量检索、RRF 融合提供带引用的 RAG 问答；在此基础上生成面试题、参考答案和 Rubric，使用四维评分、引用白名单和置信路由生成报告。可信评分会进入“稳定主题 + 动态子知识点”的两层能力画像，形成复习任务并反哺下一轮训练。  
> 
> 工程上我重点处理了 checkpoint、答题幂等、报告一致性、失败降级和历史趋势，并把系统约束在 16GB 普通开发机可通过 Docker Compose 运行。当前版本不是企业级终态：Embedding 仍是轻量基线，复杂文档尚无 OCR/版面模型，工作流由 Service 显式编排而不是 LangGraph 运行时。但这些边界都通过 Gateway、Service 和领域规则隔离，后续可以渐进替换，而不需要推翻已经跑通的学习闭环。
