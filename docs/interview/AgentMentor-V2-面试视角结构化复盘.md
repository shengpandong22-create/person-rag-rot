## 1. 项目概览（面试版）

### 1.1 项目背景

项目来源于个人从 Java 后端向 AI Agent 开发转型的学习需求。

直接使用通用大模型进行模拟面试存在三个问题：

1. 模型回答缺少可核验依据，用户很难判断结论是否真实；
2. 一次对话结束后，无法持续沉淀能力变化和高频错误；
3. 模型可能反复询问相似题目，也无法判断知识库中还有哪些内容从未考查。

AgentMentor 将个人学习资料作为前置知识边界，让资料同时服务于 RAG 问答和面试出题；再通过可信评分、两层能力画像、复习任务和知识覆盖目录，把一次性问答变成长期训练闭环。

### 1.2 核心功能

1. **知识库与资料入库**：支持 Markdown、TXT、文本型 PDF、DOCX 的解析、切分、内容去重、版本管理、向量和全文索引。
2. **可信 RAG 问答**：使用 PostgreSQL 全文检索、pgvector 向量检索和 RRF 融合；回答携带引用，证据不足时拒答或显式降级。
3. **可恢复模拟面试**：按主题和难度生成三道题、参考答案与 Rubric，支持用户真实答题、幂等提交、checkpoint 和刷新恢复。
4. **评分、报告和能力画像**：基于正确性、完整性、推理、表达四个维度评分，通过置信度和复核状态控制画像更新。
5. **补缺与查漏训练**：稳定主题画像描述长期能力，错误和复习任务处理“补缺”；知识目录记录哪些资料被真实考查，处理“查漏”。

### 1.4 技术选型理由

| 技术 | 选择理由 |
|---|---|
| FastAPI | 异步接口和类型校验能力适合调用数据库与外部 LLM，OpenAPI 文档开箱即用 |
| SQLAlchemy Async | 统一管理异步事务和数据模型，避免在 Service 中散落 SQL |
| PostgreSQL + pgvector | 一套数据库同时承载业务数据、全文检索和向量检索，符合个人项目的资源约束 |
| Alembic | 数据模型持续演进，需要可追踪、可重复执行的迁移链 |
| React + Vite | 组件化组织知识库、面试、报告和画像界面，构建链轻量、开发反馈快 |
| OpenAI-compatible Gateway | 不让业务代码绑定单一模型厂商，可通过配置切换 DeepSeek 等兼容服务 |
| Docker Compose | 用最低部署复杂度复现数据库、API 和前端环境，适合演示与本地验收 |

没有引入 Redis、Kafka、Elasticsearch、Celery、Kubernetes，是有意控制复杂度，并非不了解这些组件。当前规模下 PostgreSQL 和进程内编排足够；企业化后再按吞吐、可靠性和组织边界引入。

## 2. 核心模块说明

### 2.1 知识库与文档摄入

**模块职责**

- 创建和切换知识库；
- 校验文件类型、大小和内容哈希；
- 解析、分块、Embedding、全文索引和向量入库；
- 处理同名文档版本、失败重试和归档；
- 增量维护知识目录和切片来源。

**关键入口**

- `api/knowledge.py`
- `application/knowledge_service.py::KnowledgeService`
- `rag/documents.py::DocumentParser`
- `rag/chunking.py::chunk_sections`
- `application/coverage_catalog.py::sync_document_catalog`

**数据流转**

```text
上传文件
→ 后端扩展名、大小、SHA-256 校验
→ SourceDocument(pending)
→ DocumentParser
→ ChunkDraft
→ EmbeddingGateway
→ KnowledgeChunk + tsvector + vector
→ KnowledgeCatalogPoint + KnowledgeCatalogSource
→ SourceDocument(ready)
```

当前文档摄入由 FastAPI `BackgroundTasks` 触发，适合本地演示，但不是可靠任务队列。API 进程中断可能导致任务丢失；启动扫描只能把长期遗留的 pending/processing 修复为可重试状态，不能从解析或 Embedding 的中间位置续跑。生产化需要独立 Worker、持久化队列、重试次数、租约/心跳、死信和步骤幂等。

### 2.2 混合检索与 RAG 回答

**模块职责**

- 规范化查询；
- 分别执行全文与向量召回，汇总两路候选；
- 使用 RRF 融合排序并限制相邻重复切片；
- 进行知识边界和证据门禁；
- 调用 LLM 生成回答并校验引用白名单。

**关键入口**

- `api/chat.py`
- `application/answer_service.py::AnswerService`
- `infrastructure/retriever.py::PostgresHybridRetriever`
- `rag/retrieval.py`
- `infrastructure/llm.py::OpenAICompatibleLLMGateway`

**数据流转**

```text
用户问题
→ 查询规范化
→ PostgreSQL 全文召回 + pgvector 向量召回
→ RRF 融合和候选限额
→ 证据充分性判断
├─ 不足：拒答或允许模型知识的显式降级
└─ 充分：LLM 基于证据回答 → 引用白名单校验 → 保存会话和引用
```

### 2.3 可恢复模拟面试

**模块职责**

- 创建面试并保存画像路由；
- 按主题、难度、题型和检索片段生成题目；
- 生成本题参考答案和 Rubric；
- 使用幂等键保存答案；
- 写入 checkpoint，支持刷新后恢复当前业务节点；进程重启后可读取已提交状态，但不支持从节点执行中间位置续跑。

**关键入口**

- `api/interviews.py`
- `application/interview_service.py::InterviewService`
- `workflows/interview.py`
- `domain/interview.py`
- `QuestionReferenceModel`、`WorkflowCheckpointModel`

**数据流转**

```text
创建面试
→ 加载画像路由
→ 规划主题与题型
→ 检索知识库切片
→ LLM 生成题目/参考答案/Rubric
→ 等待用户回答
→ Idempotency-Key 幂等写入
→ 下一题或 completed
```

### 2.4 可信评分与报告

**模块职责**

- 对每道回答执行四维评分；
- 校验 Rubric 权重、得分范围和引用来源；
- 由应用层重新计算总分；
- 根据置信度进入 final、review_pending 或 disputed；
- 生成逐题解析、总报告、历史记录和趋势。

**关键入口**

- `api/evaluations.py`
- `application/evaluation_service.py::EvaluationService`
- `domain/evaluation.py`
- `EvaluationModel`、`InterviewReportModel`

**数据流转**

```text
用户答案 + 题目 Rubric + 引用切片
→ LLM 结构化评分
→ 应用层字段、权重、引用校验
→ 应用层重算总分
→ 置信与 Reviewer 路由
→ 逐题结果和整场报告
```

### 2.5 能力画像、复习任务与知识覆盖

**模块职责**

- 将题目路由到稳定主题和规范化子知识点；
- 只消费允许更新的 Evaluation；
- 使用渐进算法更新掌握度；
- 记录错误模式和间隔复习任务；
- 根据题目引用的候选切片计算知识覆盖状态；
- 输出补缺和查漏的下一轮推荐。

**关键入口**

- `api/profiles.py`
- `application/profile_service.py::ProfileService`
- `domain/profile.py`
- `domain/profile_taxonomy.py`
- `application/coverage_catalog.py::map_question_coverage`

**数据流转**

```text
可信 Evaluation
├─ 稳定主题/子知识点 → AbilityProfile 渐进更新
├─ 错误分类 → ErrorPattern → ReviewTask
└─ QuestionReference → QuestionCoveragePoint → 覆盖状态

ReviewTask（补缺）+ Coverage Gap（查漏）+ 低掌握度主题
→ 下一轮训练计划
```

## 3. 技术亮点与难点

### 3.1 RAG 的知识边界和引用可信

**问题**

仅把检索结果拼入 Prompt，仍然可能出现弱相关证据、越界回答和模型伪造引用。

**解决方案**

- 全文和向量两路召回，通过 RRF 融合而不是直接比较两类异构分数；
- 设置证据阈值并限制同文档相邻切片数量；
- 把允许引用的 Chunk ID 作为白名单；
- 模型返回后由应用层校验引用；
- 证据不足时明确拒答，允许使用模型知识时也标记降级原因。

**收益**

回答可以追溯到真实文档切片，失败模式对用户可见；项目的价值从“模型能回答”提升为“系统能说明答案依据和边界”。

### 3.2 可恢复工作流和答题幂等

**问题**

三题面试跨越多次请求。页面刷新、网络重试或重复点击可能导致进度丢失、同一道题重复写入或状态越级。

**解决方案**

- 将面试建模为显式状态迁移；
- 每个关键步骤持久化 `WorkflowCheckpointModel`；
- 答案请求携带 `Idempotency-Key`；
- 数据库唯一约束作为最终防线；
- Service 在事务中保存答案、推进序号和写 checkpoint。

**收益**

刷新后可以从数据库恢复当前面试；相同幂等键不会造成重复副作用；同时体现了比“连续调用 LLM 三次”更完整的 Agent 工程能力。当前恢复粒度是已提交的业务节点，不是分布式任务的指令级续跑。

### 3.3 评分结果不能直接污染长期画像

**问题**

LLM-as-Judge 存在输出波动和自评偏差。如果每次评分直接覆盖画像，一次偶然高分或错误评分就会污染长期训练计划。

**解决方案**

- 使用固定四维 Rubric 和字段范围；
- 最终总分由应用层计算；
- 根据置信度和 Reviewer 状态决定阻断、降权或正常更新；
- 掌握度使用指数式渐进更新，不用最近一次成绩覆盖历史；
- 使用 `ProfileUpdateEvent` 保证副作用可审计、可幂等回放；
- 复习任务需要连续两次可信高分才完成。

**收益**

画像变化更稳定，可以解释“为什么最近高分但画像没有瞬间满分”，同时避免 disputed/review_pending 结果污染长期状态。

### 3.4 新文档下的“补缺 + 查漏”双闭环

**问题**

画像只能说明已经考过的问题表现如何，不能说明资料是否被完整覆盖。如果把未考知识直接记成低分，会错误降低用户能力；如果不记录，又无法发现知识盲区。

**解决方案**

- 从文档标题路径生成知识库级稳定目录；
- 保存知识点到 Document/Chunk 的来源关系；
- 只有题目保存了对应 Chunk 引用才建立覆盖候选关系；
- 只有可信 final 评分才推进验证状态；
- 区分 `uncovered、attempted、insufficient_evidence、verified、mastered、weak`；
- 新文档只增加待覆盖点，不修改既有画像。

**收益**

系统能够同时回答“用户哪里答得不好”和“知识库里还有什么没考到”。Redis 增量资料三轮验收中，三个知识点进入 mastered，而从未被引用的缓存穿透保持 uncovered，没有被整场高分直接覆盖。

当前实现仍有一项需要准确说明的边界：`QuestionCoveragePoint` 来自题目的引用切片，而“切片进入出题上下文”不必然等于最终题目确实考查了切片对应的全部知识点；同一道题的总分也会作用于该题关联的全部目录点。因此当前覆盖度是比关键词匹配更可靠的“引用切片级覆盖”，尚未达到“逐知识点 Rubric 评分”。后续应让出题结构显式返回 `target_knowledge_point_ids`，并让 Rubric 与评分结果逐点绑定。

### 3.5 当前证据能够证明什么

目前可以证明：

- Docker Compose 三容器、数据库迁移和真实 DeepSeek 调用能够运行；
- 自动化测试覆盖领域规则、门禁、幂等和主要 Service 行为；
- 多知识库之间的报告与画像可以隔离；
- 新文档能够形成增量目录，引用、评分和覆盖状态可以完成端到端迁移。

目前不能证明：

- RAG 的 Recall@K、MRR/NDCG、引用正确率和 groundedness 达到生产标准；
- LLM 评分与资深面试官人工评分高度一致；
- 三轮面试高分代表用户能力提升；
- 系统已经通过高并发、P95 延迟、可用性或单次成本验证。

Redis 三轮验收使用的是本题参考答案，主要验证工程闭环，不是评分准确率或学习效果实验。出题与评分还可能使用同一模型，存在自洽偏差。生产化需要独立 Judge、规则 Grader、人工抽检以及版本化标注集。

## 4. 面试追问预测与回答要点

### 4.1 为什么使用 PostgreSQL + pgvector，而不是 Elasticsearch 或独立向量数据库？

当前是单机个人项目，数据规模和并发量有限。PostgreSQL 可以同时承载事务数据、全文检索和向量检索，减少部署组件和数据一致性成本，更符合 16GB 本机约束。企业化后若全文召回规模、过滤维度或吞吐成为瓶颈，再通过 Retriever 接口替换或增加专用检索服务。

### 4.2 为什么同时使用全文检索和向量检索？

全文检索擅长精确术语、类名和错误码，向量检索擅长语义近似。两者召回集合互补。系统通过 RRF 基于排名融合，避免直接比较全文分数和向量距离这两种不可直接对齐的量纲。

当前 PostgreSQL 使用 `to_tsvector('simple', content)`，没有真正的中文分词能力，因此全文侧更适合英文术语、标识符和精确片段，不能宣称已经具备生产级中文 BM25。当前 `DevelopmentEmbeddingGateway` 也是特征哈希开发基线，用于验证 pgvector 和检索接口，不代表生产语义模型效果。

### 4.3 RRF 是什么，为什么适合这个项目？

RRF 为候选在每条召回列表中的排名计算 `1 / (k + rank)`，再合并得分。它不依赖原始分数归一化，对组合 BM25/全文排名和向量排名很实用，实现简单且结果确定。但它不是自动最优，生产环境仍需通过标注集调节参数和评估 Recall@K、MRR/NDCG。

### 4.4 如何防止 RAG 在没有依据时胡编？

检索后先执行证据充分性判断；不足时返回明确的 evidence guard。进入生成后，只允许模型引用本次检索白名单中的 Chunk ID，应用层再次验证。允许使用模型通识时会显式标记 generation mode 和 fallback reason，不会伪装成资料结论。

### 4.5 为什么 checkpoint 不等于使用了 LangGraph？

当前使用 Service 显式编排状态节点，并把 checkpoint 持久化到 PostgreSQL，具备业务节点级恢复语义，但没有使用 LangGraph Runtime。已经提交的节点状态可以读取和恢复，节点执行中断则依靠幂等重新执行；它不提供分布式调度、外部工具自动重放或 exactly-once。后续可将节点和状态迁移映射到 LangGraph，而 API 和领域规则不必全部重写。

### 4.6 Idempotency-Key 如何保证重复提交安全？

客户端为每题提交生成稳定幂等键，后端先查询已有答案，同时数据库对 `question_id + idempotency_key` 建唯一约束。业务检查提升体验，数据库约束处理并发竞争，答案保存、状态推进和 checkpoint 写入处于同一事务边界。

### 4.7 为什么不能直接相信 LLM 给出的总分？

LLM 只返回各维度建议和证据，应用层校验字段范围、Rubric 权重和引用后重新计算总分。这样确定性业务规则不依赖模型执行，避免模型返回维度分与总分不一致，也便于审计和回归测试。但应用层重算只能保证结构一致，不能证明评分语义准确；当前 `0.70` 置信阈值是工程规则，尚未通过人工标注集校准。

### 4.8 为什么一次 55/60 的面试不会让画像立即变成 92 分？

报告是单场表现，画像是多次可信证据的渐进估计。系统根据难度和置信度计算学习率，用旧画像向本次归一化得分逐步移动。这样可以降低题目难度、参考答案演示和评分波动对长期状态的影响。

### 4.9 掌握度和覆盖度有什么区别？

掌握度回答“已经验证过的题目表现怎样”；覆盖度回答“资料中的知识是否进入过有引用、有评分的训练过程”。未覆盖属于未知，不能记成低分。当前覆盖必须有知识点来源、题目引用和可信 Evaluation 三层证据，而不是根据题目文字做关键词猜测；但它仍是引用切片级近似，尚未通过逐知识点 Rubric 证明题目确实考查了切片中的每个知识点。

### 4.10 新文档导入后如何避免破坏旧画像？

上传动作只更新文档、切片和知识目录，不生成 Evaluation，所以不会触发 ProfileService。新目录点初始为 uncovered。后续题目实际引用切片并完成可信评分后，才分别更新覆盖状态和对应画像；已有其他主题画像保持不变。

当前稳定目录主要根据规范化标题生成 `point_key`。它可以处理同标题重建和同知识库内的基础合并，但不能完全解决同义词、上下位关系或同名异义。文档归档后活动来源退出覆盖统计，历史报告和引用仍保留；更严格的企业实现需要显式知识点 ID、别名表、taxonomy 版本和历史快照。

### 4.11 LLM 接口不可用时系统怎么办？

LLM Gateway 失败或未配置 Key 时，RAG、出题和评分都有确定性本地基线，使核心流程仍能演示和测试。运行态接口和结果字段会暴露模型是否启用、使用的模型和降级原因，不能把 fallback 结果伪装成真实模型结果。

### 4.12 如果扩展成企业级系统，优先改什么？

第一步补租户、身份和文档 ACL，并确保检索前权限过滤；第二步增强 OCR、版面、表格和多模态解析；第三步建立人工标注评测集，测召回、引用正确率、groundedness 和拒答率；之后再引入可靠任务队列、缓存、限流、链路追踪、模型与 Prompt 版本治理。不会一开始就盲目拆微服务。

## 6. 面试前最小掌握清单

不需要记住全部源码，但至少能不看文档讲清楚：

- 为什么做这个项目，而不是直接使用通用聊天工具；
- 一份文档如何变成可检索、可引用和可查漏的知识点；
- 全文、向量和 RRF 各自解决什么问题；
- 为什么题目提交需要幂等键和数据库唯一约束；
- 为什么模型评分不能直接覆盖画像；
- 报告分、掌握度、覆盖度分别代表什么；
- DeepSeek 不可用时系统如何降级且保持可观测；
- 当前实现与企业级 RAG 之间还差哪些关键能力；
- Redis 增量文档三轮验收证明了什么，又暴露了什么问题。

最后一项的标准回答：三轮验收使用参考答案，证明的是新增资料、检索引用、评分、画像和覆盖状态能够完成工程闭环，不证明评分准确率或用户能力提升。增量资料没有重置旧画像，三个被引用的 Redis 目录点获得多次可信记录，未引用的缓存穿透保持 uncovered；但当前仍是引用切片级覆盖，且三轮题目相似度较高，因此逐知识点 Rubric 和跨场语义去重是后续 P1。
