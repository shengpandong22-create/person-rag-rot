# 优先级审计修复记录：中文检索、并发提交与摄入任务

> 目标：继续处理 V2/V2.5 审计中剩余的高优先级工程短板，用小改动提升“可追问性”和“演示可靠性”。

## 1. 修复背景

上一轮已经处理了画像驱动出题、推荐排序、重索引软停用和检索阈值。本轮继续补四个边界：

- 中文全文检索不能依赖 PostgreSQL `simple` 分词，否则中文资料的全文召回能力较弱。
- 提交答案虽然有幂等键，但状态推进前没有行锁，并发点击存在竞态窗口。
- RRF 只有召回融合，没有二阶段重排，不能利用词面覆盖和原始分数做微调。
- 文档摄入只靠 FastAPI `BackgroundTasks`，重启或异常时缺少持久化任务记录。

本轮仍坚持不大改架构，优先做能被代码和验收证明的增强。

## 2. 修复内容

### 2.1 中文检索：应用层 bigram 召回

没有直接引入 `zhparser` 或 `pg_jieba`，原因是它们会增加数据库插件依赖，不适合当前本地 Docker 演示环境。

当前采用更轻量的方案：

- 检测 query 是否包含中文；
- 如果包含中文，则从 query 中抽取中文连续片段和 bigram；
- 使用 `ILIKE` 做词面召回；
- 将 bigram 命中数作为 `text_score`；
- 继续参与 RRF 融合。

代码路线：

- `src/agent_mentor/infrastructure/retriever.py`
  - `_contains_cjk`
  - `_lexical_terms`
  - `_bigram_text_candidates`
  - `_text_candidates`

面试表达：

> V2 没有强依赖 PostgreSQL 中文分词插件，而是先做应用层 bigram 召回，让中文资料至少具备可解释的词面召回信号。这个方案不是企业级最终答案，但对本地演示可移植、可验证。

### 2.2 RRF 后轻量 rerank

之前：

- RRF 只按两路排名融合；
- 原始向量分、全文分、词面覆盖只展示，不参与最终排序。

现在：

- RRF 仍作为主召回分；
- rerank 在 RRF 后做小幅加权：
  - query 与 chunk 的词面覆盖；
  - vector 原始相似分；
  - text 原始命中分；
- 返回解释仍以 `RRF=...` 开头，并追加 `rerank=...` 和 `lexical_overlap=...`，保持兼容。

代码路线：

- `src/agent_mentor/infrastructure/retriever.py`
  - `_lexical_overlap`
  - `_rerank_score`
  - `_retrieval_explanation`

面试表达：

> 我没有让 rerank 完全覆盖 RRF，而是把它作为二阶段小幅重排，避免重排过强导致向量召回结果被词面噪声压掉。这个版本强调“可解释、低风险”。

### 2.3 并发提交：状态推进入口加行锁

之前：

- `submit_answer` 有 `Idempotency-Key` 唯一约束；
- 但业务逻辑仍然是先查再写；
- 如果两个请求同时提交同一题，理论上可能同时通过状态校验。

现在：

- 主答案提交和追问答案提交都会先锁定当前 `interview_sessions` 行；
- 同一场面试的状态推进串行化；
- 第二个并发请求拿到锁后，会看到已有主答案，直接返回当前 snapshot；
- 不会重复推进状态机。

代码路线：

- `src/agent_mentor/application/interview_service.py`
  - `_get_session_for_update`
  - `_session_for_update_statement`
  - `submit_answer`
  - `submit_follow_up_answer`

面试表达：

> 幂等键解决的是“同一个请求重复提交”，行锁解决的是“两个请求同时推进同一场面试”。这两个不是一回事，所以这里同时保留了幂等唯一约束和状态行锁。

### 2.4 摄入任务：轻量持久化任务表

之前：

- 上传文档后直接把 `ingest(document_id)` 丢给 `BackgroundTasks`；
- 服务重启或异常时，只能靠文档状态兜底；
- 看不到明确的摄入任务记录。

现在：

- 新增 `ingestion_jobs` 表；
- 上传/重索引时先写入 pending job；
- 后台任务只负责唤醒队列消费；
- worker 执行后把 job 标记为 completed / failed；
- 服务启动时会尝试恢复 processing 状态的任务，并消费 pending job。

代码路线：

- `src/agent_mentor/domain/knowledge.py`
  - `IngestionJobStatus`
- `src/agent_mentor/infrastructure/database/models.py`
  - `IngestionJobModel`
- `migrations/versions/20260908_0013_persistent_ingestion_jobs.py`
- `src/agent_mentor/application/knowledge_service.py`
  - `enqueue_ingestion`
  - `process_ingestion_queue`
  - `recover_interrupted_ingestions`
- `src/agent_mentor/api/knowledge.py`
  - 上传与重索引改为先 enqueue
- `src/agent_mentor/main.py`
  - 启动时触发轻量队列恢复

面试表达：

> 这不是完整的 Celery/Kafka 任务系统，但已经从“纯内存后台任务”升级成“数据库可观测、可恢复的轻量任务队列”。对于个人项目和本地演示，它是一个合适的中间态。

## 4. 剩余边界

本轮已经补上“本地演示可解释”的中文检索，但仍不是企业级最终形态。

后续如果继续增强，可以考虑：

- 使用 `zhparser` / `pg_jieba` / OpenSearch 做真正中文分词索引；
- 引入 cross-encoder reranker 或 embedding reranker；
- 将轻量 ingestion job 扩展为任务 worker、重试次数、死信队列和进度百分比；
- 提交答案进一步增加乐观版本号，支持更复杂的多人协作场景。
