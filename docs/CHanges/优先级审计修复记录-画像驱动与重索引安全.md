# 优先级审计修复记录：画像驱动与重索引安全

> 目标：不大改架构，优先修复会影响面试表达可信度和核心闭环成立的问题。

## 1. 修复背景

本轮审计重点不是继续堆新功能，而是检查已有 V2/V2.5 能力是否“讲得出去、追问站得住”。

外部审计和本地走查共同暴露出几个高优先级问题：

- 画像已经能沉淀，但出题阶段没有真正消费画像目标，容易被追问成“画像只是报表”。
- 推荐计划来源混杂，复习任务、覆盖盲区、低掌握度能力项之间没有统一排序和去重口径。
- 文档重索引时如果继续硬删除旧 chunk，历史引用表可能出现外键风险。
- 检索阈值过低，RRF 尾部候选也可能被当成有效证据。

本轮采用最小改动修复，不引入新的大型工作流，也不改变用户主要操作路径。

## 2. 修复内容

### 2.1 画像目标真正进入出题策略

之前：

- `profile_topic_key` / `profile_subtopic_key` 主要用于画像写入路由；
- 创建面试时即便带上画像推荐点，生成题目仍主要按 `topic + question_type + angle` 检索；
- 面试官追问“推荐了薄弱点以后，题目具体怎么变”时，代码证据不够强。

现在：

- `InterviewService._create_question()` 会读取画像推荐标题；
- 画像目标进入检索 query；
- 画像目标进入 LLM 出题 prompt；
- workflow policy 中记录 `ask_profile_targeted_question`；
- 生成题目的 required points 会补入画像目标，便于后续评分和 trace 解释。

代码路线：

- `src/agent_mentor/application/interview_service.py`
  - `_profile_focus_title`
  - `_question_policy`
  - `_question_search_text`
  - `_question_prompt`
  - `_generate_question_output`

面试表达：

> 画像不是只做展示。推荐计划点选进入面试后，会作为出题策略的一部分进入检索和题目生成，并写入 workflow trace。这样画像从“报表”变成了“训练控制信号”。

### 2.2 推荐计划统一排序与去重

之前：

- `recommend_interview_plan` 按“复习任务 → 覆盖盲区 → 低掌握度能力项”顺序 append；
- 最后直接 `[:limit]` 截断；
- 如果 open review task 太多，coverage gap 和 low mastery 可能永远展示不出来；
- 不同来源的知识点 key 语义不完全一致，去重不稳定。

现在：

- 统一转换成推荐项；
- 按来源权重、优先级、掌握度、置信样本量综合排序；
- 使用统一 recommendation key 做合并；
- confidence 只参与排序分，不污染前端展示的 `P1/P2/P3/P4` 优先级。

代码路线：

- `src/agent_mentor/application/profile_service.py`
  - `recommend_interview_plan`

面试表达：

> 推荐计划不是简单罗列，而是把复习任务、覆盖盲区和低掌握度能力项统一纳入候选池。系统优先推荐“到期、低掌握、证据更充分”的训练项，同时避免前端出现重复推荐。

### 2.3 重索引从硬删除 chunk 改为软停用

之前：

- `KnowledgeService.ingest()` 重索引文档时会删除旧 chunk；
- 历史问答引用、评分引用、聊天引用都可能指向旧 chunk；
- 如果数据库外键未设置级联删除，重索引高频文档存在完整性风险。

现在：

- `knowledge_chunks` 增加 `is_active` 字段；
- 重索引后仍匹配的 chunk 会保持 active 并更新内容；
- 多余的旧 chunk 不再删除，而是 `is_active = false`；
- 检索、全文索引刷新、catalog 同步只消费 active chunk；
- 历史引用仍能保留旧 chunk 证据，不影响新的检索结果。

代码路线：

- `src/agent_mentor/infrastructure/database/models.py`
  - `KnowledgeChunkModel.is_active`
- `migrations/versions/20260908_0012_chunk_soft_deactivation.py`
- `src/agent_mentor/application/knowledge_service.py`
  - `ingest`
- `src/agent_mentor/infrastructure/retriever.py`
  - `_base_query`
- `src/agent_mentor/application/coverage_catalog.py`
  - `sync_document_catalog`

面试表达：

> 我没有简单加级联删除，因为历史引用本身是报告可信度的一部分。这里选择软停用旧 chunk，让新检索只看 active 数据，同时保留历史证据链，属于“数据一致性”和“可追溯性”的折中。

### 2.4 检索阈值重新标定

之前：

- `retrieval_min_score = 0.01`；
- 在 RRF `k=60`、候选数 20 的情况下，尾部候选分约为 `1/(60+20)=0.0125`；
- 这意味着阈值低于尾部候选，过滤效果很弱。

现在：

- `retrieval_min_score = 0.013`；
- 可以过滤单路尾部候选；
- 仍保留向量或融合排名靠前的候选；
- 这是保守调参，不替代后续 rerank / 动态阈值。

代码路线：

- `src/agent_mentor/config.py`
- `tests/unit/test_config.py`

面试表达：

> 我们没有把阈值当玄学参数，而是结合 RRF 分数下界重新标定。当前是一个保守过滤，目的是先挡住明显的尾部弱证据，后续可以结合评测集进一步调参。

## 4. 本轮没有处理的边界

以下问题本轮刻意不做大改：

- 中文全文检索仍使用 PostgreSQL `simple` 配置，中文分词增强需要明确选择 `zhparser`、`pg_jieba` 或应用层 bigram 索引。
- 并发提交答案目前仍不是完整锁模型，后续可通过数据库行锁或乐观锁增强。
- RRF 仍以 rank 融合为主，尚未引入 rerank。
- 摄入任务仍是 FastAPI BackgroundTasks，不是持久化任务队列。

这些属于下一轮工程增强，不影响本轮“画像驱动闭环”和“重索引安全”的修复目标。
