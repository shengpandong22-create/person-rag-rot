# AgentMentor V2.5 → V3 演进路线：从受控追问到完整 Agent Loop

> 文档定位：后续开发路线、V2.5 实现记录与验收标准。  
> 当前阶段：V2 已具备 RAG、模拟面试、评分报告、画像闭环、知识库隔离、BGE 检索、工程审计、演示模式和轻量面试官出题策略。  
> 演进原则：先做小而真实的受控追问，不直接推翻现有三题面试状态机；根据实际面试反馈逐步抽象 Turn 模型，最后再升级完整 Agent Loop。

---

## 1. 总体路线

```text
V2.5：每题最多一次受控追问
  ↓
V2.6：追问前后评分对比
  ↓
V2.7：面试 Turn 模型抽象
  ↓
V3：完整 Observe → Decide → Act Loop
```

这条路线的核心取舍是：

> 先让系统具备“根据用户回答动态追问”的真实能力，再逐步升级数据模型和 Agent Loop，而不是一开始就重构成完整对话式 Agent。

---

## 2. 当前 V2 的基线

### 2.1 已经具备的能力

当前 V2 已经完成：

- 资料入库：Markdown / TXT / PDF / DOCX 解析、切分、向量化、入库；
- RAG 问答：基于检索片段生成回答，支持证据门禁、引用白名单和降级；
- 三题面试：创建面试、启动面试、生成题目、提交答案、完成面试；
- 评分报告：四维 Rubric、逐题解析、报告历史、多轮趋势；
- 能力画像：知识库隔离、稳定主题、动态子知识点、覆盖状态、复习任务；
- 工程可靠性：checkpoint、答题幂等、API 契约、状态一致性、RAG 可信度测试；
- 展示增强：首页演示模式、readiness signals、企业级边界说明；
- 轻量出题策略：题目生成时记录策略动作、原因、目标主题和确定性边界。

### 2.2 当前还没有的能力

当前 V2 还没有真正做到：

- 用户回答后动态判断是否追问；
- 追问问题由模型根据当前回答生成；
- 追问回答参与该题最终评分；
- 报告展示“追问前后是否补齐”；
- 面试由通用 Turn 模型承载；
- Agent 根据观察结果动态决定追问、换题、复盘或结束。

所以当前 V2 更准确的定义是：

```text
固定三题训练闭环 + 轻量出题策略
```

不是：

```text
完整动态面试官 Agent
```

## 3. V2.5：每题最多一次受控追问

### 3.1 目标

V2.5 的目标是让系统第一次具备“回答后决策”能力：

```text
用户回答主问题
  ↓
系统基于题目、用户回答、参考答案、Rubric、检索片段判断是否需要追问
  ↓
如果需要，生成一个追问
  ↓
用户回答追问
  ↓
进入下一道主问题
```

这里的“受控”含义是：

```text
LLM / Agent 可以判断是否追问；
但是否允许追问、最多追问几次、是否进入下一题，由确定性代码控制。
```

### 3.2 不做什么

V2.5 不做：

- 不改成无限对话；
- 不让 LLM 决定整场面试是否结束；
- 不让 LLM 直接修改状态机；
- 不改变主流程的三题模型；
- 不引入复杂 Tool Calling；
- 不重构成完整 Turn 表。

### 3.3 推荐实现方式

采用最小可控方案：

```text
每道主问题最多 1 个追问；
追问不计入 question_count；
追问归属于当前主问题；
追问回答作为当前题的补充回答；
评分时合并主回答 + 追问回答；
报告中展示追问原因和补齐效果。
```

### 3.4 后端设计

建议新增：

```text
FollowUpDecision
FollowUpQuestionOutput
```

示例结构：

```python
class FollowUpDecision(BaseModel):
    should_follow_up: bool
    reason: str
    follow_up_question: str | None
    expected_points: list[str]
    confidence: float
    risk_flags: list[str]
```

确定性校验规则：

```text
1. 当前题已经有追问 → 不再追问
2. confidence < 0.7 → 不追问
3. follow_up_question 为空 → 不追问
4. 追问与当前题/知识库明显无关 → 不追问
5. 当前面试已 completed → 不追问
```

### 3.5 数据模型建议

V2.5 可以有两种方案。

#### 方案 A：不加新表，塞入现有 JSON

优点：

- 改动小；
- 不需要迁移；
- 适合快速验证。

缺点：

- 后续 V3 抽象 Turn 时仍要迁移；
- 查询历史追问不方便。

#### 方案 B：新增 `interview_followups` 表

推荐字段：

```text
id
question_id
prompt
reference_answer
reason
expected_points
confidence
status: pending / answered / skipped
answer_text
created_at
answered_at
```

优点：

- 结构清晰；
- 方便报告展示；
- 方便后续迁移到 Turn 模型；
- 面试时更容易讲工程设计。

缺点：

- 需要 Alembic 迁移；
- 前后端都要适配。

建议：

> 如果确认要继续向 V3 演进，V2.5 建议选方案 B。虽然多一点迁移，但不会把追问塞进不合适的字段里。

### 3.6 前端设计

当前题目卡片中增加：

```text
面试官追问
- 追问原因
- 追问题目
- 用户追问回答输入框
- 提交追问回答
```

交互规则：

```text
提交主回答后：
  如果系统生成追问 → 展示追问卡片，不进入下一题
  如果系统不追问 → 进入下一题

提交追问回答后：
  当前题完成 → 进入下一题
```

### 3.7 评分设计

V2.5 暂时不做复杂评分拆分，采用合并评分：

```text
final_answer = 主回答 + "\n\n追问回答：" + follow_up_answer
```

报告中额外展示：

```text
原回答缺失点
为什么追问
追问后补齐了什么
仍然缺失什么
```

### 3.8 验收标准

功能验收：

- 一道题主回答较浅时，系统能生成追问；
- 一道题主回答充分时，系统可以不追问；
- 每道主问题最多追问一次；
- 追问回答提交后能进入下一题；
- 刷新页面后追问状态可恢复；
- 完成三题后仍能生成评分报告和画像。

工程验收：

- `ruff check src tests` 通过；
- `pyright` 通过；
- `pytest` 通过；
- `npm --prefix frontend run build` 通过；
- 至少补充以下测试：
  - 追问决策低置信不执行；
  - 每题最多一次追问；
  - 追问回答幂等提交；
  - 主回答 + 追问回答合并评分；
  - completed 状态不能继续追问。

### 3.9 V2.5 已落地实现

本轮采用“方案 B：新增 `interview_followups` 表”。这样追问是独立业务对象，不塞进题目 JSON，也方便后续升级到 V2.7 的 Turn 模型。

核心代码路线：

```text
用户提交主回答
  -> POST /api/v1/interviews/{interview_id}/answers
  -> InterviewService.submit_answer
  -> _maybe_create_follow_up
  -> _generate_follow_up_decision
  -> interview_followups 写入 pending
  -> 前端展示 current_follow_up

用户提交追问回答
  -> POST /api/v1/interviews/{interview_id}/follow-ups/{follow_up_id}/answers
  -> InterviewService.submit_follow_up_answer
  -> UserAnswerModel(answer_kind=follow_up)
  -> interview_followups 更新 answered
  -> _advance_or_finish_after_answer
```

涉及文件：

```text
src/agent_mentor/domain/interview.py
  - 新增 FollowUpStatus

src/agent_mentor/infrastructure/database/models.py
  - 新增 InterviewFollowUpModel
  - question_id 唯一约束保证每道主题最多一次追问

migrations/versions/20260906_0011_interview_followups.py
  - 新增 interview_followups 表

src/agent_mentor/application/interview_service.py
  - 主回答提交后判断是否生成追问
  - 追问提交后再推进下一题或完成面试
  - LLM 失败时用确定性规则降级

src/agent_mentor/application/evaluation_service.py
  - 评分时合并“主回答 + 追问 + 追问补充回答”
  - 评估记录仍挂在主回答上，避免报告和画像链路大范围变化

src/agent_mentor/api/interviews.py
  - InterviewResponse 新增 current_follow_up
  - 新增追问回答提交接口

frontend/src/main.jsx
frontend/src/components/InterviewPanel.jsx
frontend/src/styles.css
  - 当前题卡展示受控追问
  - 支持追问参考答案演示
```

当前实现边界：

```text
1. 每道主问题最多一次追问；
2. 追问不计入 question_count；
3. LLM 只生成追问决策，不直接推进状态；
4. confidence < 0.70、追问为空、主答覆盖充分时不追问；
5. 追问回答使用独立幂等键；
6. 刷新后 current_follow_up 可从数据库恢复；
7. 评分暂采用合并评分，不拆分追问前后增益。
```

补充门禁：

```text
如果用户主回答已经超过 80 个字符，并且包含引用、证据、降级、边界、风险、验证、
工程、记录、校验、回归、状态、checkpoint、幂等、trace 等至少 3 类工程化信号，
系统会直接判定“不追问”，避免 LLM 把追问变成每题都触发的固定动作。
```

已补充的专项测试：

```text
  - 短答触发受控追问

```

## 4. V2.6：追问前后评分对比

### 4.1 目标

V2.6 的目标是让追问不只是“多问一句”，而是证明追问对训练质量有提升。

核心问题：

```text
用户原回答哪里不足？
追问是否帮助用户补齐？
补齐后分数提升在哪里？
```

### 4.2 推荐实现

在评分报告中增加：

```text
追问前评分摘要
追问后评分摘要
补齐点
仍缺失点
分数变化原因
```

可以先不做两次完整 LLM 评分，而是让评分 prompt 同时观察：

```text
primary_answer
follow_up_question
follow_up_answer
reference_answer
rubric
```

然后输出：

```json
{
  "before_follow_up_summary": "...",
  "after_follow_up_summary": "...",
  "improved_points": [],
  "remaining_gaps": [],
  "follow_up_effective": true
}
```

### 4.3 验收标准

- 报告能展示追问前后差异；
- 高质量追问回答能被识别为补齐；
- 无效追问回答不会虚假提分；
- 画像更新仍只消费最终可信评分；
- 文档能讲清楚“追问不是为了复杂，而是为了训练质量可解释”。

## 5. V2.7：面试 Turn 模型抽象

### 5.1 目标

V2.7 的目标是为 V3 做数据结构准备。

当前模型以 `InterviewQuestion` 和 `UserAnswer` 为中心，适合固定三题面试。但追问、复盘、提示、换题越来越多后，需要更通用的 Turn 模型。

建议抽象：

```text
InterviewTurn
- id
- session_id
- parent_turn_id
- question_id
- turn_type: main_question / primary_answer / follow_up_question / follow_up_answer / review / system_decision
- role: interviewer / candidate / system
- content
- action
- reason
- status
- sequence
- created_at
```

### 5.2 不急着替换全部旧模型

V2.7 不建议一下子删除 `InterviewQuestion` / `UserAnswer`。

更稳的方式是：

```text
旧模型继续服务报告和兼容路径；
Turn 模型先作为事件轨迹/对话轨迹；
稳定后再逐步让报告和评分读取 Turn。
```

### 5.3 验收标准

- 主问题、主回答、追问、追问回答都能映射到 Turn；
- Turn 可以还原一场面试对话；
- 旧报告接口不受影响；
- 新 Turn 轨迹可以在前端或调试接口展示；
- 后续 V3 可以基于 Turn 做 Observe。

## 6. V3：完整 Observe → Decide → Act Loop

### 6.1 目标

V3 的目标是把面试从固定三题流程升级为完整面试官 Agent Loop：

```text
Observe：观察当前题目、回答、画像、覆盖状态、历史表现、检索证据
  ↓
Decide：决定追问、换题、提升难度、降低难度、复盘或结束
  ↓
Act：执行出题、追问、提示、总结等动作
  ↓
Validate：确定性规则校验动作是否合法
  ↓
Persist：写入状态、Turn、checkpoint、报告证据
  ↓
Loop：继续下一轮观察
```

### 6.2 Action Schema

建议定义受控动作集合：

```text
follow_up
new_question
switch_topic
increase_difficulty
decrease_difficulty
review_answer
finish_interview
```

示例：

```json
{
  "action": "follow_up",
  "reason": "用户回答缺少引用白名单失败后的降级处理",
  "target_topic": "RAG 引用可信度",
  "difficulty": "medium",
  "confidence": 0.86,
  "risk_flags": []
}
```

### 6.3 必须保留的确定性边界

V3 最重要的设计原则：

> LLM 可以建议动作，但不能直接执行业务状态迁移。

确定性代码必须控制：

- 最大轮数；
- 最大追问次数；
- 是否允许提前结束；
- 是否允许切换主题；
- 是否有知识库证据；
- 是否重复问题；
- 是否更新画像；
- 是否写入最终报告。

### 6.4 验收标准

功能验收：

- Agent 能根据浅回答追问；
- Agent 能根据充分回答换更难问题；
- Agent 能根据跑题回答拉回主题；
- Agent 能根据覆盖盲区切换考点；
- Agent 能在达到条件后结束并生成报告。

可靠性验收：

- 非法 action 被拒绝或降级；
- LLM 低置信决策不会改变关键状态；
- 所有 action 都有 trace；
- 所有副作用都有幂等边界；
- 画像只消费可信最终评分。

面试表达验收：

可以讲出：

> V3 的 Agent Loop 不是让模型裸奔，而是模型负责观察和建议，工程层负责验证、执行和持久化。

## 7. 推荐开发顺序

### 第一阶段：V2.5

建议优先开发：

1. 追问决策模型；
2. 追问持久化；
3. 追问生成接口；
4. 追问回答提交；
5. 前端追问卡片；
6. 合并评分；
7. 回归测试和 3～5 轮真实面试验证。

### 第二阶段：V2.6

建议开发：

1. 评分 prompt 增加追问前后对比；
2. Evaluation 输出增加补齐点；
3. 报告前端展示追问效果；
4. 构造人工答案集验证追问是否有效。

### 第三阶段：V2.7

建议开发：

1. 新增 Turn 模型；
2. 兼容写入 Turn；
3. 增加 Turn 轨迹查询；
4. 前端展示面试对话轨迹；
5. 报告逐步读取 Turn。

### 第四阶段：V3

建议开发：

1. Agent Action Schema；
2. Observe Context Builder；
3. Decide Policy；
4. Action Validator；
5. Action Executor；
6. Agent Trace；
7. Eval 验证 Agent 决策质量。

## 8. 风险控制

### 8.1 最容易失控的点

- LLM 决策过于自由；
- 追问次数失控；
- 追问和主问题评分归属不清；
- 前端流程变复杂；
- 状态恢复变脆弱；
- 画像被低质量追问污染。

### 8.2 控制原则

```text
先限制能力，再逐步放权。
先做每题一次追问，再做多轮追问。
先做合并评分，再做追问前后评分对比。
先保留旧模型，再引入 Turn 模型。
先做确定性规则，再让 LLM 提建议。
```
