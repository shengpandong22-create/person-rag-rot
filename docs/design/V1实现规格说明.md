# AgentMentor V1 实现规格说明

## 1. 目的与约束

本文档将产品与架构设计落实为可编码、可测试、可验收的 V1 规格。

具体开发顺序、Phase 范围、阶段门禁和验收报告以 [V1 分阶段开发计划与验收标准](../planning/V1分阶段开发计划与验收标准.md) 为唯一执行基线。

约束如下：

- 从零开发，不导入旧项目模块。
- 单用户优先，但主要业务表包含 `user_id`。
- 后端优先，前端只实现核心演示路径。
- PostgreSQL + pgvector 同时承担业务数据、全文检索和向量检索。
- V1 允许单进程后台任务，不引入分布式任务队列。
- 所有外部模型调用都必须经过 Gateway。
- 单元测试默认使用 Fake LLM、Fake Embedding 和内存 Repository。
- 完整系统必须能在 16GB 内存、无独立 GPU 的普通个人开发机上通过 Docker Compose 运行；LLM、Embedding 和 Reranker 默认使用云端 API。

## 3. 分层依赖规则

```text
API → Application → Domain
             ↓          ↑
       Ports/Interfaces
             ↑
Infrastructure / RAG / Agents / Workflows
```

强制规则：

- `domain` 不导入 FastAPI、SQLAlchemy、LangGraph 或模型 SDK。
- `application` 通过 Port 使用 Repository 和模型服务。
- `infrastructure` 实现 Port，不反向包含业务规则。
- LangGraph 节点调用 Application Service，不直接操作数据库 Session。
- Prompt 文件不得包含数据库或 HTTP 细节。

可通过架构测试扫描导入依赖，阻止领域层引用外部框架。

class LLMGateway(Protocol):

## 8. LangGraph 状态设计

```python
class InterviewState(TypedDict):
    session_id: str
    user_id: str
    knowledge_base_id: str
    topic: str
    difficulty: str
    question_count: int
    plan: list[QuestionPlanItem]
    current_index: int
    current_question_id: str | None
    current_answer_id: str | None
    current_evaluation_id: str | None
    follow_up_count: int
    needs_review: bool
    waiting_action: str | None
    status: str
    error_code: str | None
```

State 只保存工作流定位信息和必要快照，不在 checkpoint 中重复保存完整文档和大段模型上下文。详细数据通过 ID 从 Repository 获取。

### 8.1 节点

1. `load_profile`：加载画像和复习优先级。
2. `plan_interview`：规划本场知识点和难度分布。
3. `generate_question`：检索证据，生成题目、参考答案和 Rubric。
4. `wait_for_answer`：写入等待状态并 interrupt。
5. `evaluate_answer`：生成结构化评分。
6. `review_evaluation`：对低置信度或冲突结果复核。
7. `decide_follow_up`：确定是否追问。
8. `generate_follow_up`：生成一个针对缺失点的追问。
9. `persist_question_result`：原子保存评分和引用。
10. `advance_question`：推进题号或进入报告。
11. `generate_report`：生成整场结构化总结。
12. `update_profile`：使用确定性规则更新画像。
13. `create_review_tasks`：创建复习任务。
14. `finish_interview`：完成会话。

### 8.2 路由规则

```text
START → load_profile → plan_interview → generate_question → wait_for_answer
wait_for_answer --resume--> evaluate_answer
evaluate_answer --needs_review--> review_evaluation
evaluate_answer/review_evaluation → decide_follow_up
decide_follow_up --yes--> generate_follow_up → wait_for_answer
decide_follow_up --no--> persist_question_result → advance_question
advance_question --more--> generate_question
advance_question --done--> generate_report → update_profile
 → create_review_tasks → finish_interview → END
```

追问限制：每道题最多一次。以下任一情况不追问：

- 用户明确选择跳过。
- 评分置信度过低且证据不足。
- 已达到一次追问限制。
- 回答完全正确或完全偏离且追问没有诊断价值。

### 8.3 Checkpoint

- `thread_id = interview_session.id`。
- checkpoint 持久化至 PostgreSQL。
- 每次 resume 前验证会话状态和答案幂等键。
- 进程重启后可依据 session ID 继续。

## 9. Agent 输出契约

### 9.1 生成题目

```python
class GeneratedQuestion(BaseModel):
    question_text: str
    question_type: Literal["concept", "scenario", "design", "debugging"]
    difficulty: Difficulty
    knowledge_points: list[str]
    reference_answer: str
    rubric: EvaluationRubric
    reference_chunk_ids: list[UUID]
```

校验要求：引用必须来自当前检索结果；Rubric 总权重必须等于 100%；题目不得直接泄露答案。

### 9.2 Rubric

```python
class RubricItem(BaseModel):
    criterion: str
    description: str
    weight: int
    required_points: list[str]

class EvaluationRubric(BaseModel):
    items: list[RubricItem]
    max_score: int = 20
```

### 9.3 评分

```python
class EvaluationOutput(BaseModel):
    correctness: int = Field(ge=0, le=5)
    completeness: int = Field(ge=0, le=5)
    reasoning: int = Field(ge=0, le=5)
    communication: int = Field(ge=0, le=5)
    confidence: float = Field(ge=0, le=1)
    covered_points: list[str]
    missing_points: list[str]
    incorrect_claims: list[str]
    answer_evidence: list[str]
    reference_chunk_ids: list[UUID]
    feedback: str
    follow_up_recommended: bool
    review_reasons: list[str]
```

应用层计算 `total`，不信任模型返回的加总结果。

### 9.4 复核

触发条件默认如下：

- `confidence < 0.70`。
- 引用校验失败。
- 评分维度相互矛盾。
- 检索证据之间存在明显冲突。
- 总分接近关键分档边界且用户回答包含争议论断。

Reviewer 接收原始输入和首次评分，但必须独立输出评分。最终结果由确定性合并策略决定：差异小则平均或采用复核结果；差异大则标记 `disputed`，不自动强更新画像。

## 10. RAG 实现规格

### 10.1 入库管道

- MIME 与扩展名双重验证。
- 默认文件上限 20MB，PDF 上限 200 页，可配置。
- SHA-256 内容哈希。
- 解析器输出统一 `ParsedDocument`。
- 清除重复页眉页脚、连续空白和不可见字符。
- 保留标题层级和页码。
- 分块后批量 Embedding，单批失败可重试。
- 数据库事务完成后才将文档标记为 `READY`。
- 失败时保留错误码，不能留下可检索的半成品 chunk。

### 10.2 检索请求

```python
class RetrievalQuery(BaseModel):
    knowledge_base_id: UUID
    query: str
    top_k: int = 6
    candidate_k: int = 20
    trust_levels: list[TrustLevel] | None = None
    knowledge_point_ids: list[UUID] | None = None
```

### 10.3 检索步骤

1. 规范化查询，保留 Java 类名、异常名和缩写。
2. 使用 `ts_rank_cd` 获取全文候选。
3. 使用余弦距离获取向量候选。
4. 使用 RRF 融合两个排名列表。
5. 可配置 Cross-Encoder 或 LLM Reranker。
6. 相邻 chunk 去重并控制单文档占比。
7. 输出前 K 个片段。

RRF 默认：

```text
score(d) = Σ 1 / (60 + rank_i(d))
```

具体常数和 K 值通过离线评测调整，禁止只凭经验宣称最优。

### 10.4 证据不足

以下情况标记为证据不足：

- 没有候选片段。
- 最佳重排分数低于评测确定的阈值。
- 片段只命中词面但无法支持问题结论。

默认行为：

- 学习问答：返回知识库证据不足，询问是否允许模型补充。
- 出题：更换知识点或降低题目具体程度。
- 评分：降低置信度并触发复核，不用模型常识伪装证据。

## 11. 画像更新规则

### 11.1 单次表现

```python
score_ratio = evaluation.total / 20
difficulty_factor = {"easy": 0.9, "medium": 1.0, "hard": 1.1}[difficulty]
evidence_factor = evaluation.confidence
performance = clamp(score_ratio * difficulty_factor * evidence_factor, 0, 1)
```

### 11.2 掌握度

```python
alpha = 0.30 if evaluation.confidence >= 0.70 else 0.10
new_mastery = old_mastery * (1 - alpha) + performance * 100 * alpha
```

若评分处于争议状态，则不更新掌握度，只增加尝试记录。

### 11.3 错误模式

V1 错误类型固定为：

- `concept_confusion`
- `missing_detail`
- `incorrect_reasoning`
- `scenario_misapplication`
- `unclear_communication`
- `no_answer`

Evaluator 可以建议错误类型，应用层校验后保存。相同知识点和类型在 30 天内重复出现则累计计数。

### 11.4 复习计划

- 首次错误：1 天后。
- 第二次错误：3 天后。
- 第三次及以上：7 天后并生成相似题。
- 复习正确：下次间隔乘 2。
- 复习错误：间隔重置为 1 天。

该规则是 V1 可解释基线，后续可替换为 SM-2 等间隔重复算法。

## 12. 模型调用策略

### 12.1 Operation

统一定义：

- `question_generation`
- `answer_evaluation`
- `evaluation_review`
- `coaching`
- `query_rewrite`
- `answer_generation`
- `reranking`

不同 Operation 可配置模型、温度、最大输出、超时和重试次数。

### 12.2 默认参数原则

- 出题和评分使用较低温度，保证稳定。
- Coaching 可使用略高温度，但结构仍需校验。
- 超时最多重试两次，只对网络错误、限流和可恢复的结构化输出错误重试。
- 不对明确的认证失败、余额不足和非法请求无限重试。
- 关键写操作在模型成功后再进入数据库事务。

### 12.3 降级

- Structured Output 失败：一次修复提示；仍失败则返回明确错误。
- Reviewer 不可用：保留首次评分并标记 `review_pending`，不更新画像。
- Reranker 不可用：回退到 RRF 排名并记录降级。
- 模型完全不可用：保存会话状态，允许稍后重试。

## 18. Docker Compose

V1 服务：

- `api`
- `frontend`
- `db`：带 pgvector 扩展的 PostgreSQL

V1 不在 Compose 中启动本地大模型、Redis、Celery、Kafka、Elasticsearch、Prometheus、Grafana 或 Jaeger。需要模型能力时调用云端 API；测试和 CI 使用 Fake 实现。

### 18.1 资源预算

以 16GB Windows/WSL2 开发机为验收环境，预算如下：

| 服务 | 内存上限 | 稳定运行目标 |
|---|---:|---:|
| API | 2GB | 512MB～1GB |
| PostgreSQL + pgvector | 2GB | 512MB～1GB |
| Frontend | 1GB | 128MB～512MB |
| 一次性迁移或初始化任务 | 1GB | 256MB～512MB |
| 业务容器合计 | 6GB | 不超过 4GB |

该预算不包含操作系统、Docker Desktop/WSL2、IDE、Codex 和浏览器。Windows 开发环境建议为 WSL2/Docker Desktop 设置 4～6GB 可用内存；若完整 Compose 与开发工具同时运行出现压力，可在开发阶段只将 PostgreSQL 容器化，API 与前端在宿主机运行。

资源控制要求：

- 在 Compose 中为主要服务声明内存限制或预留配置。
- API 数据库连接池默认 `pool_size=5`、`max_overflow=5`，并允许通过环境变量调整。
- 文档解析并发默认 1，Embedding 单批默认 16～32 个 chunk。
- 单文件默认不超过 20MB，PDF 默认不超过 200 页。
- 离线评测按数据集分批执行，不与批量入库并发运行。
- 前端生产演示使用构建产物，不要求同时运行高占用的开发服务器。

### 18.2 资源验收

提供 `scripts/verify_local_resources` 脚本或等价命令，在完成以下演示链路时周期性记录各容器内存：

```text
启动系统 → 上传并索引示例资料 → 完成一次带引用问答
 → 完成至少三题模拟面试 → 生成报告和复习任务
```

验收结果保存到 `docs/benchmarks/local-resource-v1.md`，至少记录测试机器配置、数据规模、峰值内存、稳定内存和测试时间。业务容器峰值总内存不得超过 6GB，稳定运行总内存不得超过 4GB。

启动流程：

1. 数据库健康。
2. API 执行 Alembic migration。
3. API 启动并通过 readiness。
4. 前端启动。

提供演示数据命令，创建默认用户、知识库、知识点体系和少量测试文档。

## 20. V1 验收用例

### 用例 1：资料入库

给定一份包含标题层级的学习资料，上传后状态变为 READY；chunk 保留标题路径和来源，重复上传不会重复向量化。

### 用例 2：证据化问答

提出资料已覆盖的问题，回答至少包含一个有效引用；点击引用可查看原文和来源。

### 用例 3：证据不足

提出资料未覆盖的问题，系统明确说明证据不足，不生成虚假的资料引用。

### 用例 4：面试暂停恢复

创建三题面试，在第一题等待回答时重启 API，随后仍可提交答案并继续流程。

### 用例 5：评分复核

Fake Evaluator 返回低置信度结果，系统进入 Reviewer 节点；复核完成前不更新画像。

### 用例 6：幂等提交

使用相同 `Idempotency-Key` 重复提交答案，只产生一条答案和一次有效评分。

### 用例 7：画像闭环

用户在同一知识点连续两次出现概念混淆，错误模式计数增加，并生成高优先级复习任务。

### 用例 8：离线评测

执行评测命令，输出纯向量、混合检索、混合检索加重排三组指标，结果能够保存为版本化基线。

### 用例 9：16GB 开发机资源验收

在 16GB 内存、无独立 GPU 的开发机上通过 Docker Compose 启动系统，依次完成示例资料入库、带引用问答、三题面试、报告和画像更新。记录各容器峰值与稳定内存，业务容器合计分别不超过 6GB 和 4GB。

## 21. 完成定义

一个功能只有满足以下条件才算完成：

- API 和业务实现完成。
- 输入输出模型及错误码明确。
- 单元测试覆盖核心分支。
- 至少一个集成或验收用例通过。
- 日志中包含 trace ID 且不泄露密钥。
- 文档和 `.env.example` 已更新。
- 不依赖开发者本机隐式配置。
- 新增或调整基础设施后，16GB 开发机资源验收仍满足预算。

## 22. 后续版本候选

以下不进入 V1：

- 语音面试和语音表达评价。
- 多用户认证与租户隔离完善。
- Redis/Celery 分布式任务。
- Qdrant/Milvus 独立向量库。
- 多模型仲裁和成本路由。
- 基于遗忘曲线的高级学习计划。
- GitHub 项目分析与项目面试题。
- 公开题库与社区资料协作。
- Kubernetes 和完整监控平台。

这些能力必须依据真实使用数据和瓶颈逐步引入，避免为了技术栈丰富而增加无效复杂度。
