# AI 面试学习助手产品与架构设计

## 1. 文档信息

- 项目暂定名：AgentMentor
- 项目定位：面向 Java 后端转型 AI Agent 开发者的个性化学习与面试训练平台
- 文档版本：V1.0
- V1 用户范围：单用户个人助手，领域模型和数据结构保留多用户扩展能力
- 建设方式：从零开发，不复用旧项目代码；旧项目只作为需求来源，不作为实现约束
- 阶段执行基线：具体开发顺序、阶段门禁和验收以 [V1 分阶段开发计划与验收标准](../planning/V1分阶段开发计划与验收标准.md) 为准

## 2. 项目背景

Java 后端开发者转型 AI Agent 开发时，通常会面对以下问题：

1. 学习资料分散在文章、课程笔记、官方文档和开源项目中，难以形成统一知识体系。
2. 直接向大模型提问虽然方便，但回答可能存在幻觉、知识过时或无法验证来源的问题。
3. 完成学习后缺少持续、客观的验证机制，很难判断自己是真正掌握，还是只形成了模糊印象。
4. 普通题库无法根据个人历史错误、能力变化和近期目标动态调整训练内容。
5. 错题、薄弱点和复习计划互相割裂，没有形成长期学习闭环。

本项目将用户筛选后的 Java、RAG、Agent、LangGraph 等学习资料构建成个人知识库，通过 AI 工作流组织问答、面试、评分和复习，并持续更新个人能力画像。

RAG 在系统中的作用不是保证答案绝对正确，而是提供可检索、可引用、可追溯的参考证据，降低无依据生成的概率，并为回答和评分建立可评测基础。

## 3. 产品目标

### 3.1 核心目标

构建以下持续学习闭环：

```text
资料收集与审核
      ↓
文档解析、切分与索引
      ↓
基于资料学习和提问
      ↓
AI 组织面试训练
      ↓
用户回答与追问
      ↓
基于证据和 Rubric 评估
      ↓
识别薄弱点和错误模式
      ↓
更新个人能力画像
      ↓
生成复习任务和针对性训练
      └──────────────→ 再次验证
```

### 3.2 工程目标

- 展示完整的 RAG 数据链路，而不是只调用向量库。
- 展示可暂停、可恢复、带条件分支的 Agent 工作流。
- 让自动评分具备评分标准、证据、置信度和复核机制。
- 让个人画像真正参与下一轮训练决策。
- 建立可量化的检索、生成、评分和性能评测体系。
- 支持 Docker Compose 一键启动和可重复演示。
- 在 16GB 内存的普通个人开发机上完成开发、部署和核心流程演示，模型推理默认使用云端 API，不依赖高性能 GPU。

### 3.3 非目标

V1 不追求：

- 通用在线教育平台或完整 LMS。
- 企业级招聘和候选人筛选。
- 覆盖所有学科的通用题库。
- 复杂社交、排行榜、付费和运营系统。
- 自动认定网络资料为权威事实。
- 使用多个 Agent 只为增加概念数量。

## 4. 目标用户与典型场景

### 4.1 目标用户

V1 的目标用户是正在从 Java 后端向 AI Agent 应用开发转型的开发者。用户具备基础编程能力，希望系统学习 RAG、LLM 应用、Agent 编排、评测和工程化知识。

### 4.2 用户故事

#### 场景 A：建设个人知识库

用户上传 PDF、Markdown、TXT、DOCX 或录入网页来源。系统完成解析、清洗、切分、向量化和索引，并展示处理状态与失败原因。

#### 场景 B：证据化学习问答

用户针对知识库提问。系统检索相关资料，生成带来源引用的回答；证据不足时明确提示，而不是把模型自身知识伪装成资料结论。

#### 场景 C：目标驱动的模拟面试

用户选择主题、难度、题数和训练目标。系统根据资料覆盖范围与个人画像生成题目，并在用户回答后决定是否追问。

#### 场景 D：结构化评分

系统基于题目 Rubric、必答知识点、用户回答和检索证据，从正确性、完整性、推理和表达四个维度评分，并展示依据和置信度。

#### 场景 E：错题复习与能力画像

系统保存错误类型、缺失知识点和历史得分，形成能力趋势；后续根据薄弱点安排复习材料、相似题和间隔复习任务。

## 5. V1 功能范围

### 5.1 知识库管理

- 创建和查看知识库。
- 上传 Markdown、TXT、PDF、DOCX 文档。
- 保存资料标题、来源 URL、作者、发布时间、可信等级和标签。
- 文档内容哈希去重和版本管理。
- 异步或后台执行解析与索引。
- 查看文档处理状态、分块数量和错误信息。
- 删除或重新索引文档。

### 5.2 学习问答

- 基于指定知识库提问。
- 混合检索候选片段并重排。
- 返回答案、引用片段、来源和置信提示。
- 证据不足时返回受控降级结果。
- 保存问答记录和用户反馈。

### 5.3 面试训练

- 创建面试会话：主题、难度、题数、模式。
- 根据画像和资料生成题目、参考答案及评分 Rubric。
- 支持文本回答。
- 根据回答质量决定是否追问一次。
- 支持暂停和恢复会话。
- 生成整场报告。

### 5.4 自动评分

- 正确性、完整性、推理、表达分项评分。
- 展示已覆盖、缺失和存在问题的知识点。
- 给出支持评分的资料证据。
- 输出评分置信度和复核原因。
- 低置信度或证据冲突时触发第二次评审。
- 用户可以对评分标记“认可”或“有争议”。

### 5.5 画像与复习

- 按知识点维护掌握度、最近训练时间和历史趋势。
- 记录概念混淆、细节遗漏、推理断裂、表达不清等错误模式。
- 生成薄弱知识点列表。
- 创建复习任务并记录完成结果。
- 根据复习效果更新下一次训练策略。

## 6. 关键产品原则

### 6.1 证据不等于事实

知识库中的网络资料可能不完整、过时或错误。每份资料需保留来源和可信等级。系统输出应区分：

- 资料明确支持的结论。
- 多个资料存在冲突的结论。
- 资料未覆盖、由模型补充的通用知识。
- 用户已人工确认的标准答案。

### 6.2 评分必须可解释

系统不能只输出一个分数。每次评分至少包含：

- 评分维度及分项得分。
- 评分 Rubric。
- 用户回答中对应的证据。
- 知识库中的参考证据。
- 覆盖和缺失知识点。
- 评分置信度。

### 6.3 画像必须驱动行为

画像不是展示页面上的静态标签，必须参与：

- 题目主题选择。
- 难度调整。
- 追问策略。
- 复习任务排序。
- 相同错误重复出现时的强化训练。

### 6.4 Agent 数量服从职责

V1 采用逻辑角色而非独立人格堆叠：

- Interviewer：生成问题和追问。
- Evaluator：按 Rubric 评分。
- Reviewer：低置信度复核。
- Coach：生成学习反馈和复习建议。

角色可以共用模型实例，但 Prompt、输入输出契约和可观测记录必须独立。

## 7. 总体架构

```text
┌───────────────────────────────────────────────────────────┐
│                       React Web                           │
│ 知识库 | 学习问答 | 模拟面试 | 报告 | 能力画像 | 复习任务 │
└──────────────────────────┬────────────────────────────────┘
                           │ HTTP / SSE
┌──────────────────────────▼────────────────────────────────┐
│                       FastAPI API                         │
│ Auth预留 | Knowledge API | Chat API | Interview API      │
└──────────────┬────────────────────────────┬───────────────┘
               │                            │
┌──────────────▼─────────────┐  ┌──────────▼──────────────┐
│      Application Layer     │  │   LangGraph Workflows   │
│ 用例编排、事务、权限与幂等 │  │ 面试、评分复核、画像更新 │
└──────────────┬─────────────┘  └──────────┬──────────────┘
               │                            │
┌──────────────▼────────────────────────────▼───────────────┐
│                        Domain Layer                       │
│ Exam | Question | Evaluation | Profile | ReviewTask      │
└──────────────┬────────────────────────────┬───────────────┘
               │                            │
┌──────────────▼─────────────┐  ┌──────────▼──────────────┐
│          RAG Core          │  │      LLM Gateway        │
│ 解析/切分/召回/融合/重排   │  │ 模型适配/重试/降级/统计 │
└──────────────┬─────────────┘  └──────────┬──────────────┘
               │                            │
┌──────────────▼────────────────────────────▼───────────────┐
│               PostgreSQL + pgvector                      │
│ 业务数据 | 文档元数据 | Chunk | Embedding | Checkpoint   │
└───────────────────────────────────────────────────────────┘
```

### 7.1 为什么选择 PostgreSQL + pgvector

- V1 同时需要关系数据和向量数据，使用一个数据库可降低部署复杂度。
- 容易表达考试、问题、评分、画像和引用之间的关系。
- 支持事务、过滤条件、全文检索和向量检索。
- 后续规模扩大时，可通过接口替换为 Qdrant 或 Milvus。

### 7.2 为什么使用 LangGraph

面试不是一次普通的请求响应，而是包含暂停、恢复、条件追问、低置信度复核和画像更新的有状态流程。LangGraph 主要负责：

- 保存会话状态。
- 在等待用户回答时中断。
- 根据评分结果选择追问、复核或进入下一题。
- 通过 checkpoint 恢复长时间会话。
- 观察每个节点的输入输出和耗时。

普通知识库问答不强制使用 LangGraph，保持简单调用链即可。

## 8. 核心业务流程

### 8.1 文档入库

```text
上传文件
 → 格式与大小校验
 → 计算内容哈希
 → 解析正文和元数据
 → 清洗与标题层级识别
 → 语义分块
 → Embedding
 → 写入 pgvector
 → 建立全文索引
 → 标记为 READY
```

重新上传相同内容时直接复用；内容发生变化时创建新版本，并使旧版本退出默认检索范围。

### 8.2 学习问答

```text
问题规范化
 → 查询改写（必要时）
 → 全文检索 + 向量检索
 → RRF 融合
 → Rerank
 → 上下文组装
 → 带引用生成
 → 引用一致性检查
 → 返回答案
```

若最高相关度或重排分数低于阈值，系统应说明“个人知识库证据不足”，允许用户选择是否查看模型补充答案。

### 8.3 面试工作流

```text
创建会话
 → 读取能力画像
 → 规划本场知识点
 → 生成题目、Rubric、参考证据
 → 中断并等待用户回答
 → 评估回答
 → [低置信度?] → Reviewer 复核
 → [需要追问?] → 生成追问 → 等待回答 → 再评估
 → 保存题目结果
 → [还有题目?] → 下一题
 → 生成报告
 → 更新能力画像
 → 创建复习任务
 → 完成
```

### 8.4 评分流程

评分输入：

- 题目及知识点。
- 难度。
- 用户回答。
- 当前追问及补充回答。
- 题目 Rubric。
- 参考答案。
- 检索证据及来源可信等级。

评分输出示例：

```json
{
  "correctness": 4,
  "completeness": 3,
  "reasoning": 4,
  "communication": 3,
  "total": 14,
  "max_total": 20,
  "confidence": 0.82,
  "covered_points": ["扩容机制", "哈希冲突"],
  "missing_points": ["红黑树退化条件"],
  "incorrect_claims": [],
  "answer_evidence": ["用户提到数组加链表处理冲突"],
  "reference_chunk_ids": ["chunk-101", "chunk-108"],
  "feedback": "整体正确，但缺少树化和退化条件。",
  "needs_review": false
}
```

### 8.5 画像更新

V1 不让 LLM 直接决定最终掌握度。LLM 负责提取结构化评价，应用层使用可测试规则更新画像。

建议采用 0～100 的掌握度：

```text
本次表现 = 总分百分比 × 评分置信度
时间权重 = 越新的训练权重越高
新掌握度 = 旧掌握度 × 0.7 + 本次表现 × 0.3
```

附加规则：

- 低置信度评分不更新或降低更新权重。
- 相同错误连续出现时增加错误模式计数。
- 连续多次正确且题目难度提高时，才将知识点标记为“已掌握”。
- 超过设定时间未复习时，仅降低熟练度展示，不篡改历史成绩。

## 9. RAG 设计

### 9.1 文档可信等级

- `OFFICIAL`：官方文档、规范、论文。
- `CURATED`：用户人工筛选并确认的资料。
- `COMMUNITY`：博客、论坛、公开视频整理。
- `UNKNOWN`：未确认来源。

检索排序可将可信等级作为轻量特征，但不能完全覆盖语义相关性。

### 9.2 分块策略

- 优先依据 Markdown 标题、PDF 段落和 DOCX 标题层级切分。
- 保留父标题路径、来源、页码、章节和版本。
- 超长段落再按递归字符规则切分。
- 默认目标块大小为 400～800 中文字符，保留 80～120 字符重叠；最终参数必须通过评测确定。

### 9.3 混合检索

- PostgreSQL 全文检索用于关键词、类名和专有名词。
- pgvector 用于语义相似召回。
- 使用 Reciprocal Rank Fusion 合并两路结果。
- 对前 20 个候选进行重排，最终提供 4～8 个片段。
- 使用知识库、主题、标签、资料版本和可信等级过滤。

### 9.4 引用机制

模型只能引用系统提供的 `chunk_id`。响应生成后校验引用是否存在，并保存答案与引用关系。前端展示：

- 资料标题。
- 章节或页码。
- 支持结论的原文片段。
- 来源 URL 和可信等级。

### 9.5 注入防护

文档内容属于不可信输入。Prompt 明确要求模型忽略文档中的操作指令，只将其作为事实候选材料。系统还应：

- 对文档和用户输入使用清晰边界标记。
- 禁止知识库内容覆盖系统指令。
- 工具调用使用白名单和严格参数模型。
- 不向模型上下文注入密钥、内部配置和无关用户数据。

## 10. 非功能需求

### 10.1 性能目标

- 普通元数据 API P95 小于 500ms。
- 不含模型生成的混合检索 P95 小于 1.5s。
- 问答首个 SSE 事件目标小于 3s。
- 面试评分结果目标在 15s 内返回；超时后提供重试状态。

### 10.2 可靠性

- 文档入库任务可重试且幂等。
- 用户答案提交使用幂等键，防止重复计分。
- LLM 调用设置超时、有限重试和降级策略。
- 结构化输出必须经过 Pydantic 校验。
- 工作流状态持久化，可在进程重启后恢复。

### 10.3 可观测性

每次模型调用记录：

- trace ID、session ID 和 workflow node。
- 模型供应商、模型名称和 Prompt 版本。
- 输入/输出 Token、延迟、重试次数和结果状态。
- 检索候选数、最终引用数和相关度分数。
- 评分置信度、是否触发复核。

日志不得记录 API Key，用户回答和文档正文默认截断或脱敏。

### 10.4 可维护性

- 领域层不依赖 FastAPI、LangGraph、数据库和具体模型 SDK。
- 模型、Embedding、重排器和存储通过接口适配。
- Prompt 独立版本化，避免散落在业务代码中。
- 核心画像更新和流程路由使用确定性代码，并进行单元测试。

### 10.5 本地资源约束

- 完整 V1 必须能在 16GB 内存、无独立 GPU 的普通个人开发机上通过 Docker Compose 启动。
- LLM、Embedding 和可选 Reranker 默认使用云端 API；本地模型不属于 V1 运行依赖。
- Compose 仅包含 API、前端和 PostgreSQL + pgvector，不为展示目的引入 Redis、Kafka、Elasticsearch、独立向量数据库或完整监控套件。
- 在演示数据规模下，Compose 业务容器总内存目标不超过 6GB，稳定运行时目标不超过 4GB，不含 Docker Desktop/WSL2、IDE、浏览器和操作系统本身。
- 文档解析和 Embedding 必须采用限并发、分批处理，避免一次性将大量文档或 chunk 加载到内存。
- 资源约束通过容器指标和验收脚本记录，README 给出 Windows/WSL2 的建议资源配置。

## 11. 评测体系

### 11.1 检索评测

- Recall@K
- MRR
- NDCG@K
- 无答案问题拒答准确率

准备包含问题、相关 chunk 和不可回答标记的人工评测集，对比：

1. 纯向量检索。
2. 混合检索。
3. 混合检索 + Rerank。

### 11.2 生成评测

- Answer Relevance
- Faithfulness
- Citation Precision / Recall
- 人工认可率

### 11.3 评分评测

- 与人工评分的 Pearson 或 Spearman 相关系数。
- 分档一致率。
- 同一答案重复评分的稳定性。
- 错误知识点识别 Precision / Recall。
- 低置信度复核触发准确率。

### 11.4 工程指标

- P50/P95 延迟。
- 单次问答和单场面试 Token 成本。
- 模型调用成功率、重试率和降级率。
- 文档入库成功率。

## 12. 安全与合规边界

- API Key 只通过环境变量或密钥管理服务注入。
- 上传文件限制扩展名、MIME、大小和页数。
- 不执行上传文档中的宏、脚本或外部命令。
- 对用户数据预留 `user_id` 隔离条件。
- 删除文档时同步取消其 chunk 的检索资格。
- 清晰提示自动评分只用于个人学习，不代表正式招聘评价。

| 层级 | V1 选择 | 说明 |
|---|---|---|
| 后端 | Python 3.12 + FastAPI | AI 生态成熟，接口开发简单 |
| 数据模型 | Pydantic v2 | 请求、领域 DTO 和结构化输出校验 |
| ORM/迁移 | SQLAlchemy 2 + Alembic | 数据访问和版本迁移 |
| 数据库 | PostgreSQL + pgvector | 关系数据、全文和向量统一存储 |
| 工作流 | LangGraph | 暂停恢复、条件路由、checkpoint |
| LLM 接口 | 自定义 Gateway + OpenAI-compatible adapter | 避免业务绑定供应商 |
| 前端 | React + TypeScript | 提供最小可演示界面 |
| 测试 | pytest | 单元、集成和契约测试 |
| 交付 | Docker Compose | 本地一键启动 |

V1 不强制引入 Redis、Celery、Kafka、Kubernetes。只有出现明确的并发、任务队列或部署需求时再增加。

## 14. 分阶段路线

### Phase 0：工程骨架

- 新建 `src` 布局、配置、日志、数据库迁移和健康检查。
- 定义领域模型、Repository 和 LLM Gateway 接口。

### Phase 1：知识库与问答

- 文档上传、解析、分块、Embedding、混合检索和引用回答。
- 建立第一版检索评测集。

### Phase 2：面试闭环

- 创建面试、生成问题、等待回答、评分、报告。
- LangGraph checkpoint 和中断恢复。

### Phase 3：画像与复习

- 知识点掌握度、错误模式、复习任务和个性化选题。

### Phase 4：评测与可观测性

- 离线评测、Prompt 版本、Token/延迟追踪和对照实验。

### Phase 5：展示完善

- React 页面、Docker Compose、演示数据、架构图和简历材料。

## 15. V1 成功标准

V1 完成必须同时满足：

1. 能上传学习资料并查询处理状态。
2. 能基于资料回答问题并展示可点击引用。
3. 能完成一场可暂停和恢复的模拟面试。
4. 每道题有 Rubric、分项评分、依据和置信度。
5. 低置信度评分能够触发复核。
6. 考试结束后更新知识点掌握度并生成复习任务。
7. 核心业务可在不调用真实 LLM 的情况下测试。
8. 至少完成一组检索方案对照实验。
9. Docker Compose 能在全新环境启动系统。
10. 系统能在 16GB 内存、无独立 GPU 的开发机上完成资料入库、问答和一场模拟面试，且业务容器总内存满足资源预算。
11. README 能在十分钟内指导完成一次演示。

## 16. 面试表达重点

项目介绍不应停留在“使用了 RAG、LangGraph 和多 Agent”，而应回答：

- 为什么直接使用大模型不足以支撑学习评估。
- RAG 如何提供证据，但为什么不能保证绝对真实。
- 为什么面试流程需要有状态工作流。
- 自动评分如何建立 Rubric、证据和置信度。
- 如何证明混合检索和重排确实有效。
- 画像如何参与下一轮题目选择，而不是只做数据展示。
- 模型超时、结构化输出失败和证据不足时如何降级。

简历摘要建议：

> 针对 Java 后端向 AI Agent 开发转型过程中资料分散、学习效果难验证的问题，设计并实现基于 RAG 与 Agent 工作流的个性化面试学习平台，通过知识检索、证据化评分、错题分析和能力画像形成“学习—训练—评估—复习—再验证”闭环。
