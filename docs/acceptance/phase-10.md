# Phase 10 验收报告：复杂文档 RAG 增强

## 目标

Phase 10 的目标不是把系统扩成企业级重型文档平台，而是在 16GB 普通开发机可运行的约束下，补齐复杂文档 RAG 在面试中最容易被追问的几个工程点：

- 文档解析不只拿纯文本，还尽量保留标题层级、页码、块类型等结构线索。
- 切分阶段区分段落、表格、代码块、列表等内容，降低复杂资料被粗暴压扁后的语义损失。
- 检索结果对前端暴露“为什么召回这段”的解释，方便用户和面试官理解召回依据。
- RAG 回答继续坚持引用溯源，证据不足时显式降级，不让模型假装知道。

## 本阶段实现内容

### 1. 文档块类型识别

`DocumentParser` 新增 `block_type` 元数据，支持对以下内容进行轻量识别：

- `paragraph`：普通段落。
- `table`：Markdown 表格、简单管道表格或制表符表格。
- `code`：Markdown fenced code block。
- `list`：连续项目符号列表。
- `unknown`：空内容或无法判断内容。

该增强覆盖 Markdown、TXT、PDF、DOCX 的统一解析结果。

### 2. 切分阶段保留结构线索

`ChunkDraft` 新增 `block_type` 字段。

普通段落仍会归一化空白，代码块会保留换行，避免代码示例在入库前被压成一行。

### 3. 检索结果增加可解释字段

`RetrievedChunk` 和 RAG API 响应新增：

- `block_type`：召回片段类型。
- `retrieval_explanation`：召回信号说明，例如 RRF 分数、向量排序、全文排序、向量相似度、全文得分。

由于当前数据库表暂未增加 `block_type` 字段，检索层会基于已存 chunk 内容做兼容推断，保证旧数据仍可直接使用。

### 4. 前端展示引用证据

RAG 问答结果增加引用卡片，展示：

- 文档标题。
- 片段类型。
- chunk 序号。
- 页码。
- heading path。
- 检索解释。

这样用户不只看到答案，还能看到“这段证据为什么被系统拿来回答”。

## 本阶段未做内容

以下能力留到后续企业级增强，不在 Phase 10 当前范围内：

- OCR 扫描 PDF 识别。
- 表格结构化抽取为行列 JSON。
- 图片、流程图、公式的多模态解析。
- Elasticsearch / OpenSearch 等重型全文检索服务。
- 文档版式坐标级引用。

这些能力有现实价值，但会显著提高部署复杂度和资源成本，不适合作为当前 16GB 本机可运行版本的默认能力。

## 面试表达口径

如果面试官追问“复杂文档怎么处理”，可以这样回答：

> V1/V2 当前没有把复杂文档处理吹成 OCR 平台，而是在本机可运行约束下做了轻量结构化增强：解析阶段保留 heading path、页码和 block type，切分阶段避免代码块被破坏，检索阶段暴露 RRF、向量排序和全文排序等解释信号。对于扫描件、图片表格、公式等复杂场景，我会作为后续企业级增强接入 OCR、布局解析和更强的全文检索服务。
