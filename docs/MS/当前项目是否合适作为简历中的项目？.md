# 当前项目是否合适作为简历中的项目？

### 一、为什么说"合适"

#### 1. 精准覆盖了 AI Agent 开发者的核心能力栈

一个 AI Agent 岗位的面试官最想验证候选人是否理解以下几件事：

| 能力维度         | 本项目如何覆盖                                               | 面试官的考量                               |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------ |
| **RAG 系统设计** | 混合检索（向量+全文+RRF）、引用白名单、证据不足拒绝回答      | "他知道 RAG 不只是调个 embedding API 吗？" |
| **LLM 工程化**   | OpenAI-compatible Gateway、结构化输出、重试/降级、JSON 提取容错 | "他理解 LLM 是不可靠基础设施吗？"          |
| **Agent 工作流** | 面试流程编排、checkpoint 轨迹、刷新状态恢复、幂等提交        | "他知道 Agent 不是一次性调用，而是有状态流程吗？" |
| **评估与可靠性** | 四维评分、Rubric 权重校验、低置信路由、Review 机制           | "他有没有'AI 需要评估闭环'的意识？"        |
| **Prompt 工程**  | 结构化输出 schema 注入、出题/评分/问答三套 prompt、版本管理  | "他写 prompt 是拍脑袋还是有工程方法？"     |

这五个维度恰好是面试官区分"调包侠"和"AI 工程师"的分水岭。很多转型候选人只会调 LangChain API，说不清 RRF 为什么能融合两路检索、为什么要做引用校验。而你的项目在代码层面回答了这些问题。

#### 2. 完美发挥了 Java 后端背景的优势

面试官看转型候选人，最担心的是"你会写 Python 吗"和"你的后端工程能力能不能迁移"。这个项目同时回答了这两个问题：

- **架构能力迁移**：项目采用模块化单体 + Ports/Gateway 隔离外部能力，Domain 层保持纯净并有架构测试守护。它不是教科书式完全六边形架构，但能体现后端分层、依赖隔离和组合根意识。
- **状态机设计**：`ALLOWED_STATUS_TRANSITIONS` + `can_transition()` 这种显式状态转换表，是典型的 Java 后端思维——Java 开发者天然习惯用 enum + 状态表来管理生命周期。
- **幂等性意识**：`Idempotency-Key` header + 数据库唯一约束，这是 REST API 设计的老练做法。很多纯算法/ML 背景的候选人不会有这个意识。
- **数据库设计能力**：10 个 migration 文件、HNSW/GIN 索引、JSONB 字段、内容去重、版本管理——这些体现了关系型数据库的扎实功底。

#### 3. "可降级"设计是最大的面试加分项

这是我想特别强调的一点。很多 AI 项目的 demo 在有 API Key 的时候很炫，但 Key 一拔就全挂了。你的项目设计了完整的降级链：

```
无 LLM Key → 确定性评分器（启发式规则）
无 Embedding API → Feature Hashing（BLAKE2b 特征哈希）
LLM 调用失败 → 降级到模板拼接回答
LLM 返回非法 JSON → 重试 → 再失败抛 LLMGatewayError
```

这在面试中能讲出一个非常有力的故事：**"我知道 LLM 是不可靠基础设施，所以我在每一层都设计了降级方案。"** 这恰恰是生产级 AI Agent 系统最核心的工程挑战。一个转型候选人能意识到这一点，比会调 10 个 API 更有价值。

### 二、面试中如何讲这个项目

我建议用这个结构：

#### 开场（30 秒）

> "我做了一个面向 Java 后端开发者转型 AI Agent 的个人面试学习助手。核心是 RAG 问答 + 模拟面试 + 可信评分 + 能力画像的完整闭环。特别的地方是系统在没有 LLM API Key 时也能降级跑通工程链路，配置 DeepSeek/OpenAI-compatible Key 后可以切换到真实模型能力。"

#### 核心亮点（按面试官兴趣选 2-3 个深入）

1. **混合检索 + RRF**："为什么不用纯向量检索？因为向量检索对精确匹配（如类名、方法名）不敏感，全文检索正好补足。RRF 融合两路排名，k=60 是经验值。我还加了单文档占比控制和相邻 chunk 去重，避免检索结果被一篇文档霸榜。"

2. **引用安全三层防线**："LLM 会编造引用，这是 RAG 系统的安全问题。我做了三层：白名单校验（chunk_id 必须在检索结果中）、词法关联校验（引用内容必须与问题有词法重叠）、评分时二次校验。"

3. **可降级架构**："每一层都有降级方案。无 Key 时用 Feature Hashing 做 Embedding、用启发式规则做评分。LLM 调用失败时自动 fallback 到确定性回答。"

#### 收尾（20 秒）

> "项目用 Python 3.12 + FastAPI + PostgreSQL/pgvector + React + Docker Compose，能在 16GB 开发机上本地运行。架构上采用模块化单体和 Ports/Gateway 隔离外部能力，并用自动化测试守护 domain 层纯净度。"

### 三、需要注意的风险

虽然项目选择非常合适，但面试中有几个风险点需要提前准备：

#### 1. 面试官可能追问"为什么不用 LangChain/LangGraph"

你的项目没有引入 LangChain/LangGraph，而是自己实现了检索、工作流、LLM 调用。面试官可能问"为什么不用现成框架"。

**建议回答**：这是刻意的取舍。当前版本的目标是把 RAG、工作流、评分和画像闭环的底层机制搞透——自己实现 RRF 融合、checkpoint 轨迹、幂等推进和结构化输出校验，这样才能在面试中讲清楚每个环节的原理。后续如果流程扩展到复杂分支、多 Agent 协作或人工审批，再评估引入 LangGraph 的 StateGraph。

#### 2. "工作流"这个词可能引来追问

你项目里叫 `workflows/interview.py`，但实际是线性编排 + checkpoint 标签，不是真正的图执行引擎。如果面试官看到代码可能追问"这是 LangGraph 那种工作流吗"。

**建议回答**：诚实说明——当前工作流是面向三题模拟面试的轻量人机流程，真正的恢复依赖服务端持久化的面试状态、题目和答案，checkpoint 主要提供节点轨迹和排障证据。如果要做多轮 Agent 协作、条件分支、人工审批等复杂流程，会引入状态图引擎（如 LangGraph 的 StateGraph）。

#### 3. 测试覆盖度可能被质疑

API 层自动化测试和独立测试数据库仍然不够完整。如果面试官看 `tests/` 目录可能追问。

**建议回答**：当前优先保证核心领域逻辑、检索算法、画像规则和关键集成链路，Fake 实现隔离了外部依赖，并通过 Docker 做过完整面试闭环验收。API 层自动化、独立测试数据库、覆盖率度量是下一步质量建设重点。

---

### 四、一句话总结

> **这个项目不是"学了个 RAG demo"，而是"用后端工程师的思维把 AI Agent 的核心环节从底层重新实现了一遍"。对于 Java 后端转 AI Agent 的候选人来说，这正是面试官最想看到的东西——不是你会调多少 API，而是你理解每个环节背后的工程权衡。**
