# AgentMentor 分阶段开发计划与验收标准

## 1. 文档定位

本文档是 AgentMentor 后续开发的唯一阶段执行基线，用于将以下设计落地：

- [产品与架构设计](../design/产品与架构设计.md)
- [V1 实现规格说明](../design/V1实现规格说明.md)

后续开发遵循以下规则：

1. 必须按 Phase 顺序实施，上一阶段通过验收后才能进入下一阶段。
2. 每个 Phase 都必须产生可运行、可测试、可回退的增量交付物。
3. 验收以代码、自动化测试、运行记录和文档为依据，不以“功能看起来完成”为依据。
4. 阶段内允许调整实现细节；改变产品边界、基础设施或核心接口时，必须先更新本文档及相关设计。
5. V1 始终遵守 16GB 内存、无独立 GPU、云端模型 API 的工程约束。
6. 不为丰富技术栈提前引入 Redis、Celery、Kafka、Elasticsearch、独立向量数据库、Kubernetes 或完整监控套件。

## 2. 总体阶段图

```text
Phase 0  工程与架构底座
   ↓
Phase 1  知识库与文档入库
   ↓
Phase 2  证据化 RAG 问答
   ↓
Phase 3  可暂停恢复的面试主流程
   ↓
Phase 4  可信评分、复核与面试报告
   ↓
Phase 5  能力画像、错题与复习闭环
   ↓
Phase 6  Web 演示、离线评测与交付完善
```

依赖原则：

- Phase 1 复用 Phase 0 的配置、数据库、Port、Repository 和日志能力。
- Phase 2 只能消费 Phase 1 中状态为 `READY` 的文档和 chunk。
- Phase 3 先建立确定性的工作流骨架，再接入 Phase 2 的检索能力。
- Phase 4 在 Phase 3 的题目与回答聚合之上增加评分，不反向污染面试状态模型。
- Phase 5 只消费已确认的评分结果，争议评分不得强更新画像。
- Phase 6 不增加新的核心业务，只负责展示、测量和交付收口。

## 3. 全局完成定义

任意任务只有同时满足以下条件才算完成：

- 代码位于约定分层，且未违反依赖方向。
- 公共接口包含类型声明、输入校验和明确错误。
- 核心成功路径和失败路径有自动化测试。
- 测试不依赖开发者个人 API Key；外部模型默认使用 Fake。
- 数据库结构变更包含 Alembic migration。
- 日志包含 `trace_id`，不输出密钥或完整敏感正文。
- `.env.example`、README 或相关设计同步更新。
- 验收命令在干净环境可重复执行。
- 未引入与当前 Phase 无关的基础设施。

## 4. 全局质量门禁

每个 Phase 结束时至少运行：

```powershell
python -m ruff check .
python -m ruff format --check .
python -m pyright
python -m pytest
```

如果项目最终采用 `uv`，对应命令统一为：

```powershell
python -m uv run ruff check .
python -m uv run ruff format --check .
python -m uv run pyright
python -m uv run pytest
```

门禁要求：

- Ruff 无错误。
- 格式检查通过。
- Pyright 在项目规定级别无错误。
- 测试全部通过。
- 不允许用全局忽略或大范围 `noqa` 掩盖新问题。
- 若某项工具因环境不可用未执行，阶段状态只能标记为“有条件通过”，并记录原因和补验方式。

# Phase 0：工程与架构底座

## 5. Phase 0 目标

建立一个能够持续扩展、可测试、可迁移、可容器化的工程骨架。此阶段不实现真实 RAG 和面试业务，不调用付费模型。

阶段成果应证明：项目可以启动、数据库可以迁移、分层边界清晰、外部能力可以替换、测试体系可以运行。

## 6. Phase 0 范围

### 6.1 工程初始化

- 创建 `src/agent_mentor` 布局。
- 创建 `pyproject.toml`，统一运行依赖与开发依赖。
- 约定 Python 3.12。
- 配置 Ruff、Pyright 和 Pytest。
- 创建 `.env.example`，禁止提交真实密钥。
- 创建基础 README，包含本地启动、测试和迁移命令。
- 如果当前目录不是 Git 仓库，在用户确认后初始化 Git；Git 初始化不是业务验收的阻塞项。

### 6.2 分层骨架

建立以下目录及最小模块：

```text
src/agent_mentor/
├── api/
├── application/
├── domain/
├── ports/
├── infrastructure/
├── rag/
├── agents/
├── workflows/
├── prompts/
├── config.py
└── main.py
```

定义并测试依赖规则：

- Domain 不依赖 FastAPI、SQLAlchemy、LangGraph 和具体模型 SDK。
- Application 只通过 Port 使用外部能力。
- Infrastructure 实现 Port。
- API 只负责协议转换和依赖注入，不承载业务规则。

### 6.3 配置与日志

- 使用 Pydantic Settings 或等价方案管理配置。
- 区分 `development`、`test` 和 `production`。
- 启动时校验必要配置。
- 测试环境不得隐式读取真实 LLM Key。
- 建立 JSON 或结构化日志。
- 支持生成和透传 `trace_id`。
- 为 HTTP 请求添加统一错误响应。

### 6.4 数据库底座

- Docker Compose 启动 PostgreSQL + pgvector。
- SQLAlchemy 2 异步 Session。
- Alembic migration。
- 建立最小 `users` 表和扩展启用 migration。
- 定义事务边界和 Session 生命周期。
- 提供数据库 readiness 检查。

### 6.5 Port 与 Fake

定义最小接口：

- `LLMGateway`
- `EmbeddingGateway`
- `KnowledgeRetriever`
- Repository 基础事务抽象

提供：

- `FakeLLMGateway`
- `FakeEmbeddingGateway`
- 内存 Repository 示例

Fake 必须支持预设响应和调用记录，后续测试可验证输入，而不是只返回固定字符串。

### 6.6 API 基础

- FastAPI 应用工厂。
- `GET /health/live`。
- `GET /health/ready`。
- 统一错误模型。
- OpenAPI 元数据和版本前缀 `/api/v1`。

### 6.7 容器底座

- API Dockerfile。
- `docker-compose.yml` 包含 `api` 与 `db`；前端服务在 Phase 6 加入。
- 数据库 healthcheck。
- API 等待数据库就绪后启动。
- 声明初始内存限制或预留。

## 7. Phase 0 明确不做

- 不解析真实文档。
- 不创建向量索引业务表。
- 不实现检索算法。
- 不调用真实 LLM 或 Embedding。
- 不实现 LangGraph 面试流程。
- 不实现 React 前端。
- 不引入 Redis、任务队列或独立可观测平台。

## 8. Phase 0 交付物

- `pyproject.toml`
- `.env.example`
- `src/agent_mentor` 工程骨架
- `tests/unit`、`tests/integration` 基础目录
- FastAPI 应用和健康检查
- PostgreSQL + pgvector Compose 服务
- Alembic 配置与第一版 migration
- LLM/Embedding Port 与 Fake
- 结构化日志和统一错误响应
- Phase 0 README

## 9. Phase 0 验收标准

### 9.1 自动化验收

1. 全局质量门禁全部通过。
2. 架构测试证明 Domain 未导入禁用框架。
3. 配置测试证明测试环境不会读取真实 API Key。
4. `GET /health/live` 返回 `200`。
5. 数据库正常时 `GET /health/ready` 返回 `200`。
6. 数据库不可用时 readiness 返回非 `200`，但 liveness 仍为 `200`。
7. Alembic 能从空数据库升级到最新版本，并能回退一个版本后再次升级。
8. Fake Gateway 能返回预设结构并记录调用参数。

### 9.2 容器验收

执行：

```powershell
docker compose up -d --build
docker compose ps
docker compose exec api alembic current
```

要求：

- `api` 和 `db` 均为 healthy 或正常运行状态。
- API 可从宿主机访问。
- pgvector 扩展已启用。
- 重启 Compose 后数据卷和 migration 状态正常。
- 无真实模型 Key 时系统仍能启动和执行测试。

### 9.3 人工验收

- 新开发者只阅读 README，可在十分钟内启动基础服务。
- 人为制造一个 API 异常，响应包含 `code`、`message` 和 `trace_id`。
- 日志可按 `trace_id` 找到同一请求，不包含环境变量密钥。

### 9.4 Phase 0 退出条件

- 所有必需交付物存在。
- 自动化与容器验收全部通过。
- 未实现任何提前越界的业务功能。
- 已记录技术版本和本地运行方式。

# Phase 1：知识库与文档入库

## 10. Phase 1 目标

在 Phase 0 底座上完成“可信资料进入系统”的完整链路，使文档经过校验、解析、清洗、分块、Embedding 和索引后成为可检索数据。

本阶段只保证资料可被正确处理和管理，不生成大模型回答。

## 11. Phase 1 范围

### 11.1 领域模型和数据库

实现：

- `KnowledgeBase`
- `SourceDocument`
- `KnowledgeChunk`
- `KnowledgePoint` 基础表
- 文档状态 `PENDING/PROCESSING/READY/FAILED/ARCHIVED`
- 可信等级 `OFFICIAL/CURATED/COMMUNITY/UNKNOWN`

建立设计文档规定的唯一约束、全文 GIN 索引和 pgvector 索引。

### 11.2 文档管理 API

- `POST /api/v1/knowledge-bases`
- `GET /api/v1/knowledge-bases`
- `GET /api/v1/knowledge-bases/{id}`
- `POST /api/v1/knowledge-bases/{id}/documents`
- `GET /api/v1/documents/{document_id}`
- `POST /api/v1/documents/{document_id}/reindex`
- `DELETE /api/v1/documents/{document_id}`

上传响应使用 `202 Accepted`，处理状态可查询。

### 11.3 上传安全

- 扩展名和 MIME 双重检查。
- 默认上限 20MB。
- PDF 默认上限 200 页。
- 文件名规范化。
- 禁止执行宏、脚本和外部命令。
- 上传内容保存到受控目录或对象存储 Port，不能信任用户路径。

### 11.4 解析与清洗

V1 必须支持：

- Markdown
- TXT
- PDF
- DOCX

统一输出 `ParsedDocument`，保留：

- 标题层级。
- 页码或章节。
- 原始来源。
- 文档版本。

### 11.5 分块

- 优先按标题和段落边界切分。
- 超长段落再递归切分。
- 默认目标 400～800 中文字符。
- 默认重叠 80～120 字符。
- chunk 保存 `heading_path`、`page_number`、`chunk_index` 和 `token_count`。

### 11.6 去重、版本与幂等

- 使用 SHA-256 内容哈希。
- 相同知识库内重复内容不重复向量化。
- 内容变化创建新版本。
- 旧版本退出默认检索范围。
- 重新索引操作幂等。
- 失败时不得留下可检索的半成品 chunk。

### 11.7 Embedding

- 通过 `EmbeddingGateway` 调用。
- 批量大小默认 16～32。
- 维度必须与数据库索引配置一致。
- 支持 Fake Embedding 完成自动化测试。
- 真实 Embedding 只用于显式集成测试和演示。

### 11.8 处理方式

V1 可使用 FastAPI 后台任务或进程内任务执行入库，但业务服务必须与执行机制解耦，为以后迁移任务队列保留接口。

默认并发：

- 文档解析并发 1。
- 单文档分块顺序处理。
- Embedding 分批执行。

## 12. Phase 1 明确不做

- 不生成问答结果。
- 不实现查询改写、RRF 或 Rerank。
- 不实现面试流程。
- 不实现 OCR；扫描型 PDF 返回明确错误或“不支持”状态。
- 不引入 Celery/Redis。

## 13. Phase 1 交付物

- 知识库、文档、chunk、知识点 migration
- 文档领域模型与 Repository
- 四类文档解析器
- 分块器与清洗器
- 入库 Application Service
- 文档管理 API
- Fake 与真实 Embedding adapter
- 示例资料和入库集成测试
- 入库运行说明

## 14. Phase 1 验收标准

### 14.1 自动化验收

1. 全局质量门禁通过。
2. Markdown、TXT、PDF、DOCX 各有成功解析测试。
3. 标题路径和页码在解析、分块、持久化后不丢失。
4. 相同文件重复上传不产生重复 chunk 或重复 Embedding 调用。
5. 修改内容后生成新版本，旧版本不处于默认活动状态。
6. Embedding 中途失败时文档为 `FAILED`，不存在可检索半成品。
7. 重新索引重复调用结果一致。
8. 软删除后文档和 chunk 退出活动查询范围。
9. 非法格式、超限文件和扫描 PDF 返回明确错误码。

### 14.2 集成验收

使用 Compose 数据库和 Fake Embedding：

```text
创建知识库
 → 上传四种格式示例
 → 等待 READY
 → 查询文档详情
 → 检查 chunk 数量和元数据
 → 重复上传验证去重
 → 修改文档验证版本
 → 删除文档验证退出活动范围
```

### 14.3 资源验收

- 处理一份 20MB 以内或 200 页以内的边界文档时，API 容器不超过 2GB 内存上限。
- 连续处理示例资料时没有无界并发和明显内存持续增长。
- Embedding 批次和解析并发可通过配置调整。

### 14.4 Phase 1 退出条件

- 所有支持格式均可稳定进入 `READY` 或返回可解释失败。
- 文档版本、可信等级和来源信息完整。
- Phase 2 可以只通过 `KnowledgeRetriever` 和 Repository 使用入库结果，不需要了解解析器实现。

# Phase 2：证据化 RAG 问答

## 15. Phase 2 目标

完成“问题 → 混合检索 → 融合 → 可选重排 → 带引用生成 → 引用校验”的学习问答链路，并对知识库证据不足进行诚实降级。

## 16. Phase 2 范围

### 16.1 检索

- 查询规范化，保留 Java 类名、异常名和缩写。
- PostgreSQL 全文检索。
- pgvector 语义检索。
- RRF 融合。
- 单文档占比控制和相邻 chunk 去重。
- 可配置 Reranker，默认允许关闭。
- 按知识库、资料状态、版本、可信等级和知识点过滤。

### 16.2 回答

- 创建 ChatSession 和 ChatMessage。
- 基于最终 chunk 构造有边界的上下文。
- 模型只能引用提供的 `chunk_id`。
- 返回资料标题、章节/页码、片段、URL 和可信等级。
- 回答与引用关系持久化。
- 文档内容视为不可信数据，不允许覆盖系统指令。

### 16.3 证据不足

- 建立可配置阈值。
- 证据不足时返回 `KNOWLEDGE_EVIDENCE_INSUFFICIENT` 或受控结果。
- `allow_model_knowledge=false` 时禁止伪装成知识库回答。
- 用户允许模型补充时，明确标记“模型补充”，且不得生成虚假引用。

### 16.4 SSE

实现事件：

- `retrieval.started`
- `retrieval.completed`
- `answer.delta`
- `answer.references`
- `answer.completed`
- `answer.failed`

### 16.5 初始评测集

- 至少 30 条检索问题。
- 至少 5 条不可回答问题。
- 每条标注相关 chunk。
- 输出纯向量与混合检索的 Recall@K、MRR 和 NDCG。

## 17. Phase 2 明确不做

- 不实现面试题生成。
- 不实现评分和画像。
- 不强制上线昂贵 Reranker；可以先提供接口和 Fake。
- 不使用 LangGraph 包装普通问答。

## 18. Phase 2 交付物

- 混合 Retriever 和 RRF 实现
- 可选 Reranker adapter
- 问答 Application Service
- Chat 数据表和 Repository
- Chat API 与 SSE
- 引用校验器
- Prompt v1
- 检索评测集和基线报告

## 19. Phase 2 验收标准

### 19.1 自动化验收

1. 全局质量门禁通过。
2. RRF 对固定排名输入产生确定结果。
3. 非活动文档和旧版本不能被检索。
4. 引用不存在或不在本次上下文时响应校验失败。
5. Reranker 不可用时回退 RRF 并记录降级。
6. SSE 成功和失败路径都包含终止事件。
7. Prompt Injection 测试证明文档指令不能触发未授权工具或覆盖系统规则。

### 19.2 功能验收

- 对资料覆盖的问题，回答至少包含一个有效引用。
- 引用可定位至正确文档和章节/页码。
- 对资料未覆盖的问题，系统不伪造引用。
- 相同问题可查看检索候选、融合分数和最终引用。

### 19.3 指标验收

- 成功生成检索基线报告。
- 混合检索至少不劣于纯向量检索的 Recall@5；若未提升，必须记录失败样本和分析，不允许伪造提升结论。
- 不可回答问题的拒答行为在标注集上可计算。

### 19.4 Phase 2 退出条件

- 问答链路具备真实引用和证据不足降级。
- Retriever、Answering 和 API 相互解耦。
- Phase 3 能复用 Retriever 为出题提供资料证据。

# Phase 3：可暂停恢复的面试主流程

## 20. Phase 3 目标

建立有状态的模拟面试主流程，完成面试规划、生成题目、等待用户回答、推进题目和结束会话。此阶段先使用简化评分占位，不实现最终可信评分体系。

## 21. Phase 3 范围

### 21.1 领域与数据

- `InterviewSession`
- `InterviewQuestion`
- `UserAnswer`
- 会话状态与合法状态转换
- 答案幂等键

### 21.2 LangGraph

实现节点：

- `load_profile`：V1 初始可返回空画像。
- `plan_interview`
- `generate_question`
- `wait_for_answer`
- `persist_answer`
- `advance_question`
- `finish_interview`

实现：

- PostgreSQL checkpoint。
- `thread_id = interview_session.id`。
- interrupt 等待回答。
- resume 前的会话与幂等校验。
- 进程重启后的恢复。

### 21.3 题目生成

- 基于主题、难度、题数和 Phase 2 检索证据生成。
- 输出 `GeneratedQuestion`。
- 包含知识点、参考答案、Rubric 草案和引用 chunk ID。
- 引用必须来自本次检索结果。

### 21.4 API

- `POST /api/v1/interviews`
- `POST /api/v1/interviews/{id}/start`
- `GET /api/v1/interviews/{id}`
- `POST /api/v1/interviews/{id}/answers`
- `GET /api/v1/interviews/{id}/events`

### 21.5 占位评分

为了验证流程，可使用确定性 Fake 节点或固定“已接收”结果推进题目。占位评分不得写入正式 Evaluation 表，也不得更新画像。

## 22. Phase 3 明确不做

- 不实现 Reviewer。
- 不更新能力画像。
- 不生成复习任务。
- 不实现最终面试报告。
- 不允许占位评分被展示为真实能力结论。

## 23. Phase 3 交付物

- 面试领域模型和 migration
- LangGraph State、节点、路由和 checkpoint
- Interviewer Agent 输出契约
- 面试 API 和 SSE
- 幂等提交实现
- 工作流路由与恢复测试

## 24. Phase 3 验收标准

### 24.1 自动化验收

1. 全局质量门禁通过。
2. 状态机拒绝非法状态转换。
3. 每道题生成时引用 ID 均来自有效检索上下文。
4. 相同幂等键重复提交只产生一条 UserAnswer。
5. 每道题最多推进一次。
6. 工作流异常不导致会话误标记为完成。
7. checkpoint 中不保存完整文档或无界上下文。

### 24.2 恢复验收

```text
创建三题面试
 → 启动并生成第一题
 → 工作流 interrupt
 → 重启 API
 → 提交答案并 resume
 → 完成其余题目
 → 会话进入 COMPLETED
```

要求状态、题号和答案不丢失、不重复。

### 24.3 Phase 3 退出条件

- 三题面试能跨请求、跨进程完成。
- API、Application Service 和 LangGraph 节点职责清晰。
- 正式评分可以在 Phase 4 替换占位节点，而无需重写会话生命周期。

# Phase 4：可信评分、复核与面试报告

## 25. Phase 4 目标

将 Phase 3 的流程升级为可解释、可校验、可复核的面试评估系统，解决“LLM 随意打分”的可信度问题。

## 26. Phase 4 范围

### 26.1 Rubric

- 每道题生成四维评分标准。
- 权重总和必须为 100%。
- 明确必答知识点和可选加分点。
- Rubric 与题目和 Prompt 版本共同保存。

### 26.2 Evaluation

四个维度各 0～5：

- Correctness
- Completeness
- Reasoning
- Communication

应用层计算总分，模型不得决定最终加总。

输出必须包含：

- 覆盖点。
- 缺失点。
- 错误论断。
- 用户回答证据。
- 参考 chunk ID。
- 反馈。
- 置信度。
- 是否建议追问。
- 复核原因。

### 26.3 复核

触发条件：

- `confidence < 0.70`。
- 引用校验失败。
- 评分维度矛盾。
- 资料证据冲突。
- 接近关键分档边界且存在争议。

Reviewer 独立输出第二次评分。差异大时标记 `disputed`，不得强行生成确定结论。

### 26.4 追问

- 每道题最多一次。
- 只针对诊断价值明确的缺失点追问。
- 追问回答计入同一道题的最终评价。
- 完全正确、完全偏离、证据不足或已追问时不再追问。

### 26.5 报告

报告包含：

- 总体得分与分项分布。
- 每题 Rubric 和评分证据。
- 知识点表现。
- 错误类型汇总。
- 有争议或低置信度结果。
- 下一步学习建议。

## 27. Phase 4 明确不做

- 不更新最终画像，画像写入留到 Phase 5。
- 不使用多个模型只为制造“多 Agent”效果。
- 不隐瞒低置信度或争议结果。

## 28. Phase 4 交付物

- Evaluation 和引用关系 migration
- Evaluator、Reviewer 和 Follow-up 节点
- Rubric 与 Evaluation Pydantic 契约
- 复核路由和确定性合并规则
- 面试报告服务和 API
- 评分 Prompt v1、Review Prompt v1
- 人工评分样本集初版

## 29. Phase 4 验收标准

### 29.1 自动化验收

1. 全局质量门禁通过。
2. Rubric 权重不为 100% 时拒绝保存。
3. 四维分数越界时结构化输出校验失败。
4. 总分由应用代码计算。
5. 低置信度 Fake 结果必定进入 Reviewer。
6. Reviewer 不可用时标记 `review_pending`，不伪造复核完成。
7. 每道题最多生成一次追问。
8. 非法引用不能进入最终 Evaluation。
9. 相同答案和固定 Fake 输入得到稳定路由结果。

### 29.2 功能验收

- 不完整回答能展示覆盖点、缺失点和针对性追问。
- 正确回答不会被无意义追问。
- 低置信度评分展示复核过程和最终状态。
- 报告能够追溯到题目、答案、Rubric、评分和引用。

### 29.3 初始评分评测

- 至少准备 20 组人工标注回答。
- 能计算自动评分与人工评分差异。
- 能统计重复评分稳定性。
- 结果无论好坏均保存为基线，不在未达到预期时虚构指标。

### 29.4 Phase 4 退出条件

- 正式 Evaluation 完全替代 Phase 3 占位评分。
- 争议和低置信度结果具备明确状态。
- 报告可作为 Phase 5 画像更新的唯一输入来源。

# Phase 5：能力画像、错题与复习闭环

## 30. Phase 5 目标

让历史训练结果真正影响后续学习决策，完成“训练—评估—画像—复习—再训练”闭环。

## 31. Phase 5 范围

### 31.1 数据模型

- `AbilityProfile`
- `ErrorPattern`
- `ReviewTask`
- 乐观锁版本号
- 掌握度和复习历史

### 31.2 画像更新

- 依据设计文档中的确定性公式计算表现。
- 高置信度评分使用正常更新权重。
- 低置信度评分降低权重。
- `disputed` 或 `review_pending` 不更新掌握度。
- 保存历史成绩，不因时间衰减修改原始记录。

### 31.3 错误模式

固定类型：

- `concept_confusion`
- `missing_detail`
- `incorrect_reasoning`
- `scenario_misapplication`
- `unclear_communication`
- `no_answer`

相同知识点和错误类型在 30 天内重复出现时累计。

### 31.4 复习任务

- 首次错误 1 天后。
- 第二次错误 3 天后。
- 第三次及以上 7 天后并生成相似题。
- 复习正确后间隔乘 2。
- 再次错误时重置为 1 天。

### 31.5 个性化选题

面试规划根据以下优先级选择知识点：

1. 到期复习任务。
2. 高频重复错误。
3. 掌握度低的目标知识点。
4. 长期未训练的知识点。
5. 用户显式指定主题。

用户显式选择始终高于系统建议；系统需要说明推荐原因。

### 31.6 API

- `GET /api/v1/profiles/me/abilities`
- `GET /api/v1/profiles/me/error-patterns`
- `GET /api/v1/review-tasks`
- `POST /api/v1/review-tasks/{id}/complete`

## 32. Phase 5 明确不做

- 不使用黑盒模型直接覆盖掌握度。
- 不实现复杂推荐算法或机器学习排序。
- 不引入未经真实数据验证的遗忘曲线模型。
- 不实现社交比较和排行榜。

## 33. Phase 5 交付物

- 画像、错误模式、复习任务 migration
- Profile 与 Review Repository
- 确定性画像更新服务
- 错误模式聚合服务
- 复习计划服务
- 个性化面试规划升级
- 画像与复习 API
- 闭环集成测试

## 34. Phase 5 验收标准

### 34.1 自动化验收

1. 全局质量门禁通过。
2. 画像公式边界值、置信度和难度因子测试通过。
3. `disputed` 评分不更新掌握度。
4. 乐观锁冲突不会静默覆盖画像。
5. 相同错误在 30 天内正确累计。
6. 复习间隔按规则推进和重置。
7. 重复处理同一 Evaluation 不会重复更新画像或创建重复任务。
8. 个性化规划在固定输入下结果可解释、可重复。

### 34.2 闭环验收

```text
用户连续两次遗漏同一知识点
 → 错误模式累计
 → 掌握度变化
 → 创建高优先级复习任务
 → 下一场面试优先选择该知识点
 → 用户复习后答对
 → 更新掌握度和下次复习时间
```

前后所有变化都能追溯到 Evaluation 和 ReviewTask。

### 34.3 Phase 5 退出条件

- 画像数据能够真实影响下一场面试计划。
- 所有画像变化由确定性规则产生且有来源记录。
- 完整业务闭环可通过 API 演示。

# Phase 6：Web 演示、离线评测与交付完善

## 35. Phase 6 目标

不新增核心业务，通过最小 Web 界面、完整评测、资源验证和部署文档，将已有能力收敛为可展示、可复现、可写入简历的 V1 项目。

## 36. Phase 6 范围

### 36.1 React 最小前端

页面：

1. 知识库与文档管理。
2. 学习问答与引用展开。
3. 模拟面试与 SSE 状态。
4. 面试报告。
5. 能力画像和复习任务。

要求状态清晰、错误可见、刷新后可恢复；不追求复杂视觉效果。

### 36.2 离线评测完善

最终最低数据规模：

- 检索问题 50 条，其中不可回答 10 条。
- 问答样本 30 条。
- 人工评分样本 30 组。

对比：

- 纯向量检索。
- 混合检索。
- 混合检索 + Rerank。

输出：

- Recall@K、MRR、NDCG。
- Faithfulness 和引用准确性。
- 拒答准确率。
- 与人工评分的相关性和分档一致率。
- P50/P95 延迟和 Token 成本。

### 36.3 可观测性收口

- LLM 调用日志。
- Prompt 版本。
- Token、延迟、重试和降级统计。
- 检索候选数、引用数和分数。
- 工作流节点耗时。

V1 使用结构化日志和报告，不强制部署 Grafana。

### 36.4 完整 Docker Compose

服务：

- API
- Frontend
- PostgreSQL + pgvector

补充：

- healthcheck。
- migration。
- 演示数据。
- 生产构建前端。
- 资源限制。

### 36.5 文档与演示

- 完整 README。
- 架构图。
- 本地资源基准报告。
- 离线评测报告。
- 三段演示脚本。
- 简历项目描述。
- 常见面试追问与技术取舍说明。

## 37. Phase 6 明确不做

- 不引入新的核心业务模块。
- 不为指标好看修改或筛选评测样本。
- 不伪造线上用户量、准确率或性能数据。
- 不部署本地 LLM 作为 V1 必需依赖。

## 38. Phase 6 交付物

- React 前端
- 完整 Compose
- 演示数据初始化脚本
- 三类离线评测数据集
- 机器可读与 Markdown 评测报告
- `docs/benchmarks/local-resource-v1.md`
- 完整 README 和演示说明
- 简历与面试材料

## 39. Phase 6 验收标准

### 39.1 全链路验收

在全新环境完成：

```text
Docker Compose 启动
 → 初始化演示数据
 → 上传并索引学习资料
 → 完成一次带引用问答
 → 完成至少三题模拟面试
 → 查看 Rubric、复核和报告
 → 查看画像变化和复习任务
 → 开始下一场个性化面试
```

### 39.2 资源验收

- 验收机器：16GB 内存、无独立 GPU。
- 业务容器峰值总内存不超过 6GB。
- 稳定运行总内存不超过 4GB。
- 资料入库、问答、三题面试、报告和画像更新全部完成。
- 结果记录在本地资源基准报告中。

### 39.3 质量验收

- 全局质量门禁通过。
- 所有 migration 可从空数据库执行。
- 核心测试默认不调用真实模型。
- 评测命令可重复执行并保存版本化报告。
- README 能指导新开发者在十分钟内启动系统。

### 39.4 产品验收

- 有依据：回答和评分引用可追溯。
- 有记忆：历史评估形成画像和错误模式。
- 有闭环：画像影响复习和下一场训练。
- 有边界：证据不足、低置信度和争议结果明确展示。

### 39.5 Phase 6 退出条件

- V1 成功标准全部满足。
- 演示脚本稳定完成。
- 评测和资源数据来自真实执行记录。
- 项目可以作为简历核心项目进行讲解。

# 42. 后续执行协议

后续每次开始开发时按以下流程执行：

1. 读取当前 Phase 的目标、范围和明确不做事项。
2. 检查前一阶段验收报告和遗留限制。
3. 将当前 Phase 拆成 3～7 个可独立验证的工作包。
4. 每个工作包完成后立即运行相关最小测试。
5. Phase 结束时运行全局质量门禁和完整验收。
6. 写入阶段验收报告。
7. 只有验收通过后，才更新状态并开始下一 Phase。

若实现过程中发现设计不成立：

- 先记录证据和影响。
- 修改设计文档与本文档。
- 对受影响的已完成阶段执行回归验收。
- 不通过隐式改变范围来绕过验收标准。

本文档确认后，下一项开发任务固定为 Phase 0，不直接开始知识库、RAG、Agent 或前端功能。
