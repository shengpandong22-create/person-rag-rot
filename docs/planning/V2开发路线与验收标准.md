# AgentMentor V2 开发路线与验收标准

> 本文档用于规划 V1 之后的 Phase 7～Phase 11 开发路线。  
> V1 文档保持独立归档，不在本文中覆盖或改写。V2 的目标是在 V1 已完成的“资料入库 → RAG 问答 → 模拟面试 → 评分报告 → 能力画像 → 复习计划”闭环基础上，继续增强工程可维护性、画像驱动能力、训练趋势、复杂文档 RAG 和 Agent 工作流能力。

## 1. V2 总体目标

V1 已经证明项目能在 16GB 普通开发机上通过 Docker Compose 跑通，并形成个人 AI 面试训练闭环。V2 不再优先追求“更多页面按钮”，而是围绕以下五个方向升级：

1. 前端从单文件 Demo 页面升级为可维护的 React 工作台。
2. 训练过程从“用户选主题出题”升级为“画像驱动出题”。
3. 评分结果从“单轮报告”升级为“多轮历史和趋势分析”。
4. RAG 从“普通资料可用”升级为“能解释复杂文档处理边界和增强策略”。
5. 面试流程从“checkpoint 记录”升级为“更显式的 Agent 工作流和中断恢复”。

V2 仍然遵守 V1 的工程约束：

- 默认单用户、本机画像，不引入复杂账号系统。
- 继续保持 Docker Compose 本地部署。
- 继续控制在 16GB 普通开发机可运行范围内。
- 不为了技术栈好看引入 Redis、Kafka、Elasticsearch、Kubernetes。
- 允许通过端口抽象预留外部服务替换能力，但 V2 必须保持本地可演示。

## 2. Phase 总览

| Phase | 主题 | 主要目标 | 优先级 | 简历价值 |
| --- | --- | --- | --- | --- |
| Phase 7 | 前端组件化 + 运行态观测 | 降低前端维护成本，展示系统运行状态和降级路径 | P0 | 体现工程化、可观测性 |
| Phase 8 | 画像驱动出题 + 复习任务专项训练 | 让能力画像真正反哺下一轮训练 | P0 | 体现闭环和 Agent 个性化规划 |
| Phase 9 | 报告历史 + 多轮趋势 | 沉淀多轮训练数据，展示进步趋势 | P1 | 体现长期记忆和数据产品能力 |
| Phase 10 | 复杂文档 RAG 增强 | 增强解析、chunk、metadata、检索解释能力 | P1 | 应对企业级 RAG 追问 |
| Phase 11 | Agent 工作流显式化 + 中断恢复 | 将面试流程抽象为更清晰的节点图和恢复机制 | P1 | 体现 Agent 工程化能力 |

## 3. Phase 7：前端组件化 + 运行态观测

### 3.1 背景

V1 前端主要集中在 `frontend/src/main.jsx`。这有利于快速验证闭环，但不利于后续维护、走读和扩展。Phase 7 的目标不是大改视觉，而是先把前端拆成可理解、可维护、可扩展的结构，并补充运行态观测能力。

### 3.2 功能点

#### P7-F1：前端目录重构

建议结构：

```text
frontend/src/
  api/
    client.js
  components/
    AppHeader.jsx
    KnowledgePanel.jsx
    RagPanel.jsx
    InterviewPanel.jsx
    EvaluationPanel.jsx
    ProfilePanel.jsx
    RuntimePanel.jsx
    CommonCards.jsx
  hooks/
    useAgentMentorState.js
    usePolling.js
  utils/
    formatters.js
  main.jsx
  styles.css
```

说明：

- `main.jsx` 只负责挂载应用。
- API 调用统一放入 `api/client.js`。
- 页面区块拆成独立组件。
- 通用展示逻辑抽到 `CommonCards.jsx` 或 `utils/formatters.js`。

#### P7-F2：运行态观测面板

新增“系统运行状态”面板，展示：

- API ready 状态。
- Runtime 状态。
- LLM 是否启用。
- 当前 LLM model。
- 最近一次 RAG 是否证据充足。
- 最近一次回答是否发生 LLM fallback。
- 最近一次评分是否发生规则降级。

#### P7-F3：前端状态刷新优化

优化：

- 文档上传后的状态轮询。
- 面试状态刷新。
- 评分和画像刷新。
- 错误提示文案。

避免用户误以为系统卡死。

#### P7-F4：前端构建和 smoke check 固化

保留并更新前端构建验证：

```powershell
cd frontend
npm.cmd run build
```

如有必要，增加一个轻量 smoke 检查脚本或文档化手动验收步骤。

### 3.3 验收标准

| 验收项 | 标准 |
| --- | --- |
| 组件化 | `frontend/src/main.jsx` 不再承载全部业务 UI，核心页面区块拆到独立组件 |
| API 封装 | 前端请求统一从 `api/client.js` 发出，不在组件里散落 fetch 细节 |
| 运行态展示 | 页面能展示 health/runtime、LLM enabled、model、最近降级状态 |
| 原有功能不回退 | 上传、RAG、面试、评分、画像仍能完整跑通 |
| 构建通过 | `npm.cmd run build` 成功 |
| 文档更新 | 在 V2 验收文档中记录前端拆分结构和运行态面板截图或说明 |

### 3.4 面试得分点

- 能说明为什么要从单文件 Demo 页面拆成组件。
- 能说明 AI 应用为什么需要展示 runtime/fallback/证据充足状态。
- 能说明前端只是展示层，不承载唯一业务真相。

## 4. Phase 8：画像驱动出题 + 复习任务专项训练

### 4.1 背景

V1 已经有能力画像、错误模式和复习任务，但面试出题仍以用户输入主题为主。Phase 8 要把画像和出题链路真正打通，让系统从“问固定主题”升级为“根据薄弱点安排训练”。

### 4.2 功能点

#### P8-F1：面试计划引入画像上下文

在创建或启动面试时读取当前默认用户画像，得到：

- 低掌握度知识点。
- 高频错误模式。
- 未完成复习任务。
- 最近一轮扣分严重题目。

生成面试计划时优先考虑这些信息。

#### P8-F2：专项训练入口

从复习任务或能力画像卡片发起专项训练：

```text
点击“补强：状态建模与工作流控制”
  ↓
自动创建该知识点主题的三题面试
  ↓
检索相关资料
  ↓
生成专项题目
```

#### P8-F3：题目生成解释

每道题除了题目、参考答案、Rubric 外，增加“为什么出这道题”的解释字段：

- 来源于哪个薄弱知识点。
- 来源于哪个错误模式。
- 来源于哪条复习任务。
- 使用了哪些检索片段。

#### P8-F4：避免重复出题

在同一轮或连续多轮训练中，尽量避免同一知识点生成高度重复问题。

可先用轻量规则实现：

- 记录最近 N 道题的 normalized topic/question。
- 新题与近期题目过于相似时重新生成或选择候选 fallback。

### 4.3 验收标准

| 验收项 | 标准 |
| --- | --- |
| 画像参与出题 | 创建新面试时能看到画像/复习任务对题目主题产生影响 |
| 专项训练 | 从某个薄弱知识点或复习任务能直接发起专项面试 |
| 出题解释 | 前端展示“为什么出这道题”，且能关联画像、错误或复习任务 |
| 去重 | 连续三题不应完全相同；连续两轮训练不应总是同一题 |
| 降级可用 | 画像为空时仍能按用户主题和检索片段生成题 |
| 测试覆盖 | 增加画像驱动选题、专项训练、题目去重的单元测试 |

### 4.4 面试得分点

- 能说明项目不是普通题库，而是“基于个人画像的训练规划”。
- 能解释画像如何影响下一轮训练。
- 能解释冷启动时画像为空如何降级。

## 5. Phase 9：报告历史 + 多轮趋势

### 5.1 背景

V1 可以展示当前一轮报告，但长期学习价值需要多轮趋势支撑。Phase 9 的目标是让系统从“单轮评分”升级为“持续训练记录”。

### 5.2 功能点

#### P9-F1：报告历史列表

新增报告历史查询能力：

- 按时间倒序展示最近 N 次面试报告。
- 展示主题、难度、总分、状态、完成时间。
- 支持点击查看报告详情。

#### P9-F2：多轮趋势

基于历史报告和画像事件展示：

- 总分趋势。
- 四维评分趋势。
- 低掌握度知识点变化。
- 高频错误变化。

#### P9-F3：训练摘要

生成面向用户的训练摘要：

```text
最近 5 轮中，总分从 42/60 提升到 51/60；
completeness 维度仍低于平均；
建议下一轮继续训练“RAG 检索增强生成”和“状态建模与工作流控制”。
```

#### P9-F4：报告详情结构优化

报告详情中逐题展示：

- 题目。
- 用户答案。
- 参考答案。
- 四维得分。
- 扣分原因。
- 缺失要点。
- 关联引用。
- 下一步建议。

内容较长时前端折叠展示。

### 5.3 验收标准

| 验收项 | 标准 |
| --- | --- |
| 历史查询 | 能查询并展示多轮 interview report |
| 趋势展示 | 至少展示总分和四维评分趋势 |
| 逐题详情 | 每道题有标题 + 回答 + 得分 + 解析结构 |
| 空状态 | 没有历史报告时展示清晰引导 |
| 性能 | 个人本地数据规模下页面打开无明显卡顿 |
| 测试覆盖 | 增加报告列表、趋势计算、空状态测试 |

### 5.4 面试得分点

- 能说明“长期记忆”不是只存聊天记录，而是沉淀可分析的数据。
- 能说明为什么报告历史对训练闭环有价值。
- 能说明趋势计算应该由应用层规则保障，而不是完全交给 LLM。

## 6. Phase 10：复杂文档 RAG 增强

### 6.1 背景

面试官如果偏企业落地，常会追问复杂文档 RAG：PDF 表格、扫描件、标题层级、代码块、跨页上下文、chunk 粒度、召回不足等。Phase 10 的目标不是一次做完整企业级 RAG 平台，而是在 V1 基础上补足最容易被追问的能力边界和代表性增强。

### 6.2 功能点

#### P10-F1：文档解析 metadata 增强

每个 chunk 尽量保留：

- document_id。
- source filename。
- heading path。
- page number。
- block type。
- chunk index。
- content hash。

block type 可先支持：

```text
paragraph
heading
code
table
list
unknown
```

#### P10-F2：结构化 chunk 策略

增强 chunking：

- 标题层级不丢失。
- 代码块尽量不拆断。
- 表格可独立成 chunk。
- 长段落按长度切分。
- 保留 overlap。

#### P10-F3：复杂文档测试集

建立小型测试语料：

- Markdown 标题层级文档。
- 含代码块文档。
- 含表格文档。
- 普通 PDF。
- DOCX 文档。

每类文档至少有一个可验证查询。

#### P10-F4：检索解释增强

RAG 返回结果中增加或优化：

- vector rank。
- text rank。
- fused rank。
- score。
- heading path。
- page number。
- block type。

前端可展示“为什么召回这段”。

#### P10-F5：证据不足处理

当召回不足时：

- RAG 回答明确提示证据不足。
- 面试题生成避免把证据不足内容包装成确定知识。
- 可建议用户补充资料。

### 6.3 验收标准

| 验收项 | 标准 |
| --- | --- |
| metadata | chunk 中能看到来源、标题路径、页码或块类型等 metadata |
| 结构保留 | 代码块、表格、标题层级至少不会被完全打散 |
| 检索解释 | RAG 引用能展示排名或来源解释 |
| 测试语料 | 有覆盖 Markdown/PDF/DOCX/表格/代码块的最小测试集 |
| 证据不足 | 召回不足时系统显式降级，不强行编答案 |
| 测试覆盖 | 增加解析、chunk、metadata、检索解释相关测试 |

### 6.4 面试得分点

- 能说清楚企业 RAG 的难点不只是“向量库”，而是解析、结构、metadata、chunk 和召回评估。
- 能说明 V1 和 V2 的边界：V1 解决闭环，V2 增强复杂文档处理。
- 能解释为什么暂不引入 Elasticsearch 或专用 OCR，而是先用 PostgreSQL 能力和轻量解析增强。

## 7. Phase 11：Agent 工作流显式化 + 中断恢复

### 7.1 背景

V1 已经有 `WorkflowCheckpointModel` 和面试节点函数，但流程仍主要由 `InterviewService` 编排。Phase 11 的目标是把 Agent 工作流进一步显式化，让“可恢复、多步骤、可观测”的能力更清楚。

### 7.2 功能点

#### P11-F1：工作流节点抽象

将面试流程抽象为明确节点：

```text
LoadProfileNode
PlanInterviewNode
RetrieveEvidenceNode
GenerateQuestionNode
WaitUserAnswerNode
PersistAnswerNode
EvaluateAnswerNode
UpdateProfileNode
PlanNextRoundNode
```

不要求一步到位引入重型框架，可先用轻量 Python 类或函数式节点实现。

#### P11-F2：恢复当前面试

支持用户刷新页面或重新打开页面后恢复：

- 当前 session。
- 当前 question。
- 已提交 answers。
- 当前 workflow checkpoint。
- 是否等待回答。

#### P11-F3：事件流增强

统一关键事件命名：

```text
workflow.started
workflow.checkpoint_saved
question.generated
answer.persisted
evaluation.completed
profile.updated
workflow.completed
```

用于日志、SSE 或前端运行态展示。

#### P11-F4：异常恢复策略

定义并实现常见异常处理：

- 题目生成失败：规则 fallback。
- 答案重复提交：返回已有结果。
- 评分失败：规则评分或 review_pending。
- 画像更新失败：保留 Evaluation，不污染画像。

#### P11-F5：工作流审计视图

前端或接口提供一个轻量“工作流轨迹”视图：

- 节点名称。
- 时间。
- 输入摘要。
- 输出摘要。
- 是否 fallback。
- 错误信息。

### 7.3 验收标准

| 验收项 | 标准 |
| --- | --- |
| 节点显式化 | 面试流程能通过节点/事件清楚表达，而不是散落在服务方法里 |
| 中断恢复 | 刷新页面后能恢复当前题和已答状态 |
| checkpoint 可用 | `WorkflowCheckpointModel` 能支撑恢复和审计 |
| 事件统一 | 关键 workflow event 命名统一，并可在日志或前端看到 |
| 异常策略 | 生成题目、提交答案、评分、画像更新都有明确 fallback 或保护 |
| 测试覆盖 | 增加恢复、重复提交、异常 fallback、checkpoint 的测试 |

### 7.4 面试得分点

- 能说明 Agent 不是“一个 prompt”，而是多节点、有状态、可恢复、可观测的工作流。
- 能解释 checkpoint 和 idempotency 在 Agent 工程里的价值。
- 能说明异常失败时如何保护长期画像不被污染。

docs/acceptance/phase-10.md
docs/acceptance/phase-11.md

## 9. V2 总体验收标准

V2 完成后，系统应达到：

1. 前端结构清晰，核心页面区块组件化。
2. 页面能展示运行态、LLM 状态和降级信息。
3. 能从能力画像或复习任务发起专项训练。
4. 出题能解释“为什么问这道题”。
5. 能查看多轮训练报告和趋势。
6. RAG 引用能展示更丰富的来源 metadata。
7. 复杂文档处理边界有测试和文档说明。
8. 面试工作流支持刷新恢复。
9. 关键 workflow 事件可观测。
10. 后端测试、Ruff、前端构建通过。

## 10. V2 简历表达升级方向

V2 完成后，简历描述可以从 V1 的“闭环跑通”升级为：

```text
基于 FastAPI + PostgreSQL/pgvector + React + DeepSeek API 实现个人 AI 面试训练助手，支持学习资料入库、全文/向量混合检索、RAG 引用溯源、画像驱动出题、可恢复 Agent 工作流、Rubric 可信评分、多轮趋势报告和复习任务闭环；通过 Docker Compose 在 16GB 本地开发机部署，并设计 LLM fallback、幂等提交、checkpoint、引用白名单和画像防污染机制。
```

面试展开时可以重点讲：

- RAG 为什么前置。
- 混合检索和 RRF 怎么做。
- 画像如何反哺出题。
- 为什么要有 checkpoint 和 idempotency。
- 如何避免低可信评分污染长期画像。
- 复杂文档 RAG 的边界和后续增强路线。

## 11. 开发顺序建议

推荐顺序：

1. 先做 Phase 7，降低前端复杂度，并补充运行态观测。
2. 再做 Phase 8，让项目最核心的“个人画像闭环”真正成立。
3. 然后做 Phase 9，让项目具备长期训练价值。
4. 接着做 Phase 10，应对企业 RAG 追问。
5. 最后做 Phase 11，把 Agent 工作流表达得更完整。

如果时间有限，优先完成：

1. Phase 8：画像驱动出题。
2. Phase 9：报告历史和趋势。
3. Phase 10：复杂文档 RAG 增强。

因为这三项最能拉开和普通 RAG Demo 的差距。
