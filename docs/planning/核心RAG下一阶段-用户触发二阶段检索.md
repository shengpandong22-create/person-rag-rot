# 核心 RAG 下一阶段：用户触发的二阶段扩展检索

## 选择结论

下一项核心 RAG 优化固定为“用户显式触发的二阶段扩展检索”。首次检索和回答保持生产
默认不变；当用户认为证据不足时，可以选择“扩大检索 / 再搜一次”，系统保留原 Top-6，
再补充少量来自不同关键章节的证据，并明确展示新增引用。

本计划当前只确定方向和验收边界，不授权直接修改生产默认。

## 为什么选择它

现有可复现实验证明：

- Development 中6/25个正样本在 candidate 阶段已经丢失，排序和 Gate 无法补救；
- heading supplemental 的 `fixed@7` 在专项 Development 中将联合召回从60%提升到100%；
- 但无条件消费会让平均上下文从6块增加到11块，触发率100%，不适合作为默认路径；
- 基于现有 Evidence Gate 的自动触发只触发20%，没有恢复任何4个缺失正例；
- 分数差、标题覆盖和通用 presence 特征尚未形成稳定的自动触发器。

因此，不继续制造一个未经证明的自动 trigger，而是把触发权交给用户。这样既保持主 Top-6
单调安全，也能在真正需要时使用已经证明存在召回增益的 supplemental 通道。

## 用户可见效果

演示流程应当非常直观：

1. 用户用低词面重叠的改写问题提问；
2. 首轮回答显示当前引用和“证据可能不完整”的边界；
3. 用户点击“扩大检索”；
4. 原引用保持不变，界面新增命中的章节和引用；
5. 系统基于扩展证据重新回答，并标明哪些证据来自第二阶段。

相比后台阈值微调，这个变化可以直接展示“为什么第一次没有答全、第二次新增了什么证据”。

## 固定技术边界

- 原 Top-6 不删除、不改序；
- 不调整 RRF 权重、Embedding、Evidence Gate 或生产阈值；
- supplemental 最多7块，并优先不同 heading path；
- 第二阶段必须由用户显式触发，不自动执行；
- 第二阶段引用必须进入同一引用白名单和 provenance 校验；
- 请求、触发原因、新增 chunk、延迟和上下文增量必须记录；
- 首轮与二阶段回答在 UI/API 中可区分；
- 不把已消费的 acceptance/holdout 用于调参。

## 实施顺序

1. 先定义 API 契约、trace 字段和上下文预算，不改检索算法；
2. 在非盲 Development 上复用 heading supplemental 作为能力上界，验证主 Top-6 单调性；
3. 增加用户触发的 service orchestration，默认关闭；
4. 增加引用白名单、幂等和重复触发测试；
5. 增加前端“扩大检索”入口与新增证据标记；
6. 用演示 fixture 对比首次回答与二阶段回答；
7. 通过 regression 后，再决定是否建立新的独立验收集。

## 资格指标

- 原 Top-6 保留率 = 100%；
- 用户触发后联合 relevant-source recall 明显高于首次检索；
- 新增上下文不超过7块；
- 新增相关 evidence 消费精度可单独报告；
- 引用 provenance 合法率 = 100%；
- 困难负例不得因扩展检索自动变成肯定回答；
- P95 二阶段额外延迟和上下文 Token 增量必须可见；
- 重复点击不得重复追加相同 chunk 或生成并发竞态。

## 明确不做

- 不恢复 Relation-Value V3/V4；
- 不继续扫描自动 trigger 阈值；
- 不把 `fixed@7` 直接设为所有请求的默认上下文；
- 不在同一阶段修改 rerank、RRF、Embedding 或 Gate。
